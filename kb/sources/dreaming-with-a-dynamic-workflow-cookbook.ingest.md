# Ingest: Dreaming with a dynamic workflow

## Classification

This is a vendor cookbook: an executable notebook recipe with its full agent prompts, a nightly cron script, one worked example run on eleven synthetic transcripts, and summary cost figures for a larger run. It reports what the authors built and ran, not a controlled study, so it is a practitioner report. The quality claim rests on an undisclosed fixed-fact recall check.
Author: Anthropic (Claude Cookbook, dated 2026-11-02). The authors are authoritative about the platform mechanics: Managed Agents memory stores, workflow runs, mount limits and permissions. They are vendor-positioned on cost and quality and present no comparison with other memory designs.

## Summary

The recipe builds a "dream": an offline background pass that turns an agent's finished session transcripts into a wiki-style memory store that later sessions mount read-only. A Sonnet lead agent receives a plain-language request and writes a Managed Agents dynamic workflow. In the first phase, one Haiku analyzer per transcript, running in groups of about 20, reads the transcript in full. It then checks existing memory claims against that transcript (Verify), adds exact identifiers, commands, dated staleness notes and process lessons (Enrich), and maintains small linked Markdown files with frontmatter, `[[slug]]` links and a shared `_index.md` (Organize). In the second phase, a single organizer runs after every analyzer has finished. It merges duplicates, retires files with `MOVED TO` stubs, records dated supersessions or `CONFLICT:` lines, and completes the index. The prompts carry an explicit concurrency discipline and a prompt-injection posture: transcripts and memory files are treated as data, tools are file-only, the network allowlist is empty and consumers mount the store read-only. A cron script repeats the pass nightly on newly finished sessions. Reported costs are $0.36 and 2.5 minutes for the eleven-file example, and about $8 and ten minutes for fifty long transcripts. The cost-reducing settings are reported to keep "about the same share of a fixed list of facts"; that comparison is made within one fixed pipeline. The recipe states plainly that there is no review by default and that raw records default to a temporary directory.

Nothing keeps that evidence beside the claims afterwards. ## Learning Claims (our opinion)

On its own terms, the mechanism is cross-session adaptation through an external file store. Agents leave transcripts. A nightly batch extracts dated facts, commands and process lessons, then checks them against stored memory. Later sessions read the result. No weights change, and the consuming agent never writes to the store.

Against the [theory-builder definition](../theory/definitions/theory-builder.md), the conditions have different support:

- **Localized content** is met by design. Memory is small named files with one-sentence index entries and dated fact lines. A wrong fact can be pointed at and revised without rewriting the store, so the store is moderately [addressable](../theory/definitions/addressable-theory.md).
- **Consumption** is specified but not demonstrated. The store is mounted, and `_index.md` may be loaded into the system prompt, but the source shows no session whose decision changed because of a stored fact.
- **Criticism** is content-directed but narrow. Verify compares stated claims with one transcript, downgrades overconfident claims and fixes or notes contradictions. The organizer marks unresolved conflicts rather than guessing. The worked run shows one such act: the organizer resolved a `make test` conflict as version-dependent and marked that resolution as inference. The only criticism available, however, is comparison of transcript testimony with memory text. Analyzers have file tools only and cannot run a command to test whether a stored fact still holds. A stale fact is detected only if a later transcript happens to contradict it.
- **Iteration** is supported by the mechanism. Downgrades, staleness notes and conflict marks persist in the same store and are what the next night's Verify reads. No multi-night run is shown.

Results persist across runs and sessions, which is the high end of the persistence grade. The method texts, however, are outside the loop. The analyzer and organizer prompts are operator-edited files that no part of the dream criticizes or revises, so the system is not reflective in our sense. Under [learning inside a fixed decomposition](../theory/learning-inside-a-fixed-decomposition-inherits-its-mistakes.md), the effective update space is the store's text. One transcript per analyzer, transcript-only evidence, the wiki file form and the model assignments are fixed outside it. The reported tuning, which kept a similar share of a fixed fact list at lower cost, is improvement inside that decomposition. It is not evidence that per-transcript fan-out, the wiki form or discarding transcripts is the right choice.

Learning, meaning improved capacity for future action, is not established. The only quality measure is recall of a fixed fact list, which shows retention, not changed behavior. The source therefore supports the plausibility of the mechanism and the existence of specific criticism acts. It neither supports nor puts in question Commonplace's account of when stored theory improves later work. It does add one distinction worth keeping: a dream that discards its episodes can criticize only claims that a new episode happens to touch.

## Extractable Value

1. **The default configuration does not retain the oracle that Verify depends on.** The recipe gives transcripts authority during extraction, then leaves the exported copies in a temporary records folder and never consults them again; the original sessions survive on the platform but outside the loop. This is a concrete vendor case for the retaining-episode-evidence note: without retained episodes, criticism of a stored claim waits for a new episode to touch it. It is also a candidate for comparing offline consolidation designs, alongside the Mt. Moon correction and Letta-style retained history. [quick-win]
2. **A layered concurrency guarantee for parallel writers to one memory store.** The guarantee has four parts: re-read before edit, targeted index edits, read-back verification because "a write that reports success can still be replaced", and link-not-merge during the parallel phase, with merges deferred to a single-writer phase. This is a reusable pattern for any Commonplace workflow in which several workers update shared indexes, and it names the guarantee rather than the channel. [experiment]
3. **Architecture-enforced data/instruction separation for consolidation workers.** The pattern combines several measures. Transcript text never enters a prompt and is opened by a read tool; workers hold only file tools; the network allowlist is empty; prompts state that inputs are data; and output is mounted read-only. The recipe also names the residual risk: loading store text into a system prompt lets injected text "steer every session". This bounds when an always-loaded index is safe. [just-a-reference]
4. **Concrete lifecycle markers for conflicting facts.** A plain later correction keeps both dates and sources. An unresolved disagreement gets a `CONFLICT:` line. A single session's passing remark never overrides a recorded project decision. `MOVED TO` stubs serve as non-destructive retirement where no delete tool exists. These are precise operating rules for the retire/supersede requirement. [just-a-reference]
5. **The orchestrator's report is checked against platform records.** The notebook counts analyzed transcripts from thread records, prints the workflow the lead agent wrote, and reports "where the run differed from what the message asked". This is a small, cheap check on a model-authored orchestrator. [just-a-reference]

## Limitations (our opinion)

The quality evidence is thin and self-referential. "About the same share of a fixed list of facts" names neither the list, the scoring method nor the variance, and it compares only cost-saving variants of one pipeline. It does not show that the store improves later sessions; per [evaluate memory by effects, not by existence](../theory/agent-memory-requirements/evaluate-memory-by-effects.md), recall of planted facts is a retention measure, not an effect measure. The worked example uses eleven synthetic transcripts written for the cookbook. Their difficulties, a staleness change, buried details and overlapping topics, were designed to be ones the prompts handle, so they show survivorship of the intended path rather than real failure modes.

The Verify step's authority is weaker than its name suggests. A Haiku model compares memory with one transcript and has no way to run a command against the project. "Verified" in the store therefore means "consistent with something an agent saw once", and the store does not distinguish this from stronger verification. Combined with no default review and no retained transcript evidence beside the store, an error introduced one night can be re-checked only if a later session happens to contradict it. The recipe partly acknowledges this: "Agents should re-check any fact that matters."

The capture is the full cookbook page, but the helper module, the notebook cells and the scoring for the fact list are not in it. Platform limits such as 64 concurrent threads, 500 mounted files and a 4,096-character `instructions` cap are point-in-time research-preview facts that later releases may change. The recipe also positions itself against Anthropic's own Dreams preview; vendor interest favors showing the platform's flexibility over comparing it with simpler designs, such as a single sequential analyzer or appending raw transcripts with search.
