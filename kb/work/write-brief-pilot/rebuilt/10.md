# Brief: Designing a memory system for LLM-based agents

## Governing question

What must an agent memory system actually do, and why do those requirements belong together? The question is asked from the effects memory must have on the agents and processes that consume it. Where retained state lives, and which pipeline produced it, are secondary.

## Audience and reader update

The readers are agents and maintainers who design, evaluate, or compare memory systems. That covers Commonplace's own memory work and the review of external systems in `kb/agent-memory-systems/`. This note is the entry point for the agent-memory area. The agent-memory tag head calls it the starting point. Several documents rest on it:

- The requirements directory (`agent-memory-requirements/`) says it expands this note's inventory.
- The reference coverage map and gap plan say they implement or close its requirements.
- The agent-memory-system review type distils it into review-time section specs.
- The trace-learning survey turns its repeated techniques into this needs map.

After reading, the reader should hold four things:

1. Memory is judged by contextual competence, not persistence.
2. Memory design is a context-engineering problem because retention is cheaper than use.
3. The requirements come from consumers who fail in different ways.
4. There is a concrete, operation-organized inventory to check a design against, and it is not a build order.

## Target claim or purpose

This is a synthesis note (`synthesis` trait), cited as a unit, with a descriptive topic title rather than a claim title. It works as a requirements map, not a layer architecture. It should do three things.

First, derive the pressure categories a realistic memory system must meet, each step motivating the next:

- start with consumers;
- treat memory as context engineering;
- use retained-artifact fields to say what is governed and how it acts;
- go beyond retrieval;
- set the boundary of what the memory system governs.

Second, route to the requirements inventory, organized by memory operation and cross-mapped to the pressure categories.

Third, separate the stable requirements from implementation-specific sequencing and from secondary adoption properties. Close with the open problems.

The core thesis sits in the opening: design memory from its effects, and measure success by contextual competence. Remembered material earns its place when it helps an agent answer, act, create artifacts, or update behavior under bounded context. Link the discoverable/composable/trusted note as the direct statement of that criterion.

## Must keep

- The opening thesis and the explicit framing: this is a requirements map, the inventory is a checklist of capabilities and failure modes, and it is not a build sequence.
- The provenance statement. The derivation starts from first principles, then was checked against the Agent Memory Systems review collection and revised where reviewed systems exposed missing pressure: packaging, activation, authority, lifecycle, compiled-view drift, and effect-based evaluation. Keep the external check against the adaptation survey, which asks where optimization happens, while this note asks what should make a learned artifact governed as memory.
- **Consumers section.** The named consumers (acting agents, context schedulers, learning loops, reviewers, maintainers, governance processes, work surfaces) and their distinct failures. Keep the conclusion that memory cannot collapse into one retrieval interface.
- **Context-engineering section.** Retention is cheap and use is expensive. The pressure is selection and shaping, not storage scarcity. Memory is crosscutting across the execution substrate, the context engine, and the learning loop. Link the crosscutting-concern note.
- **Retained-artifact fields.** Storage substrate, representational form, lineage, and behavioral authority, each linked to its definition. Keep the insistence that form and authority are separate fields. Keep the decision-rationale example that is a knowledge artifact in one consumption path and a system-definition artifact in another. State the definition of symbolic, and codification as a form move, not automatically an authority move. Keep the error-correction-asymmetry grounding with both halves: bookkeeping is more reliable on a symbolic substrate, and codifying a learned rule also makes its errors propagate more reliably.
- **Beyond retrieval.** Durable behavior-changing artifacts are part of the memory problem. Link raw accumulation and storage-versus-activation. High-authority behavior-changing memory at scale needs symbolic artifacts whose contracts, activation, lineage, lifecycle, authority, and evaluation are part of the memory system.
- **The boundary.** All behavior-shaping persistent state is broader than what the memory system governs. The boundary is explicitly an architectural choice, not a universal claim about what memory is. A regression test or an `AGENTS.md` rule stays execution substrate unless it carries accumulated project knowledge governed as a learned constraint.
- **The inventory.** Keep the cross-mapping of each pressure category to the requirement notes, with every existing requirement link. Child notes point back to this note as the place that "places" or "derives" them, so no requirement should drop out of the map. Keep the pointer to the reference coverage map for the Commonplace implementation mapping.
- **Secondary properties.** Native work-environment fit, cost-model flexibility, portable degradation, and inspectable generated surfaces, clearly subordinate to the requirements. Keep the ByteRover and Hindsight examples of packaging becoming architectural when many clients must be served. The portable-context-layer ingest extends this section.
- **Partial memory subsystems.** Vector database, transcript archive or summarizer, always-loaded profile or self-editing prompt, wiki or rules engine, and reusable memory package. Say what each leaves to surrounding workflows. Keep the conclusion that a realistic architecture names which requirements it handles internally and which it delegates.
- **Build order is implementation-specific.** Point to the Commonplace gap plan as one project's mapping. Sequencing comes from validated usefulness in the running system.
- **Open problems.** Structural pattern detection across sessions, with the drift example of stale pricing tables, runbooks, and templates. Weak discovery extraction: surface candidates, don't graduate them automatically. The domain-dependent boundary between learned memory and work-surface authority. Learned memory-management policy as oracle-dependent, placed on the bitter-lesson boundary of relaxing where feedback is good and keeping artifact-side control where it is weak.

## Exclusions

- No layer architecture, reference implementation, or build sequence. Commonplace's current coverage and gap plan live in `kb/reference/`; link them, don't restate them.
- Do not expand individual requirements. Each has its own loadable note, and this note explains only why they belong together.
- No per-system review detail beyond the few illustrative examples. System characterizations belong in the review collection.
- No claim that symbolic artifacts are universally superior, and no universal definition of "memory".
- Do not reproduce the adaptation survey's taxonomy. The comparison note handles that translation.

## Scope, modality, and terminology

The pressure derivation is argued as general design theory for LLM-agent memory under bounded context. The boundary and the inventory's organization are marked as design choices. Secondary properties are desirable, not required. Open problems are stated as open, without hedging elsewhere.

Use the registered vocabulary exactly: context engineering, representational form (natural-language, symbolic, distributed-parametric, mixed), storage substrate, lineage, behavioral authority, knowledge artifact versus system-definition artifact, codification. Keep "contextual competence" as the success criterion throughout. Use "memory system" for the governed subset and "behavior-shaping substrate" for the broader set; do not interchange them.

The `synthesis` trait waives body composability, so inline restatement of cited claims is expected.

## Reserved decisions

- Adding, removing, merging, or renaming requirements. That changes the requirements directory, the review type's distilled contract, and the coverage map together.
- Reorganizing the inventory by something other than memory operation.
- Recasting the note as a claim-titled note or a layer architecture.
- The observability and tool-loop tag heads describe this note as covering hidden fallback paths and degraded execution as extraction targets. The current body carries no such passage. Whether to restore that content or correct those glosses is an operator decision, not an editor's.
