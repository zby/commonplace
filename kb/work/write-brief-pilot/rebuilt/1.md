# Brief: Context-operation interface bounds context policy

## Governing question

When a system improves how it selects context — a learned memory controller, a better host-side assembler, a model that pages more cleverly — what has that improvement shown, and what has it not? Specifically: can gains from a better policy over a fixed set of context operations establish that the operation set itself is adequate?

## Audience and reader update

Readers are agents and maintainers who design agent memory or context-assembly architectures, and who read or run evaluations of "learned context management" systems. Several source ingests and system reviews (ACM, AgeMem, Scroll, Virtual Context, lambda-RLM, the RLM practitioner account, EvoOntology, ContextPilot) cite this note as the place that separates the operation interface from the policy using it. After reading, the reader should stop treating a policy win as evidence that the interface was sufficient, and should know which architecture coordinates an evaluation must report before its result can be interpreted.

## Target claim or purpose

A title-as-claim note. The claim: holding retained substrate, model, and resource budget fixed, the context-operation interface — its operation semantics, addressable units, permitted compositions, and the boundary where a view becomes model input — bounds which active-context projections any policy can realize. A policy only selects among legal traces. It can raise how often, how reliably, or how cheaply useful traces are chosen, but it cannot add a view the interface excludes, and its success does not show excluded views are unnecessary. Present this as the context-projection instance of the more general claim that learning inside a fixed decomposition inherits that decomposition's omissions.

## Must keep

- The layer separation: retained substrate versus active context, with retained controller state distinguished from projected state, and a pointer to the general scheduling/context/state separation.
- A precise definition of the interface and of the controller (receiving model, learned controller, host/proxy, or mixed).
- The `Reach(I, S, x; M, B)` formalization, with `B` spelled out as covering context size, model calls, time, and tool use; traces that may mutate retained state; "projection" explicitly not a lossless mathematical projector; and the three ways a view falls outside reach (missing operation, unaddressable distinction, forbidden composition).
- The link to access burden versus transformation burden: finding material is not turning it into the needed view.
- The premise-change rule: adding tools, observations, computation, capability, budget, or operation-definition rights is no longer "a better policy over the same interface."
- The architectural contrast among RLM (open programmatic), lambda-RLM (typed combinators), and ACM (two fixed operations, learned invocation), flagged as source-described, not verified or ranked.
- Controller placement and persistence horizon as coordinates separate from structural reach.
- The evaluation reporting list and the three ways to test interface adequacy (rival interface, another constraint-changing intervention, or an exclusion argument). Downstream notes on end-to-end access evaluation and oracle-dependent memory policy rely on this section.
- The Scroll and Virtual Context reviews as code-grounded evidence links.

## Exclusions

- No ranking of interfaces and no claim that open-ended programming interfaces are better; restriction can buy reliability, safety, inspectability, trainability, latency, or cost.
- No causal effect estimates for any coordinate.
- Nothing past exposure: whether delivered context is activated or changes behavior belongs to the storage/activation note.
- No claim that a legal trace will be found or produced reliably.
- Do not import the empirical figures from source ingests (EvoOntology, ContextPilot) into the note body; those ingests carry their own scoping.

## Scope, modality, and terminology

The core bound is universal and structural — effectively a definitional consequence once the fixed premises are stated; state the premises so the claim is exact rather than hedged. Evidence claims about the named systems are existential and source-bounded. Use "context-operation interface", "projection", "structural reach", "legal trace", "controller/policy", "retained substrate", and "active context" consistently; do not slide between "reach" and "achieved coverage". Keep the Scope section explicit that structural reach is not achieved use.

## Reserved decisions

- Whether to add new system witnesses to the body (e.g., EvoOntology, which one ingest proposes adding) — the operator decides, and any addition must keep the fixed outer decomposition and ablation limits visible.
- Renaming the note or its core terms, since tag heads, ingests, and reviews link it by its current handle and description.
- Any move toward recommending a particular interface design.
