1. [governing claim] Designs an ideal memory system for agentic systems.
2. [constraint] Grounds the design in the KB's existing theory and in the comparative review of 11 systems.
3. [governing claim] Core premise: store everything (all interaction session logs, all intermediate artifacts, all observations), because symbolic storage is cheap and text storage is a solved problem.
4. [governing claim] The hard problem is not storage but finding the right information at the right time under bounded context.
5. [scope] Presents "store everything" as a working hypothesis, not a proven conclusion.
6. [constraint] States what "store everything" trades: storage costs for indexing overhead, search pollution risk, and potential privacy exposure; the bet is that selective retrieval can manage what aggressive storage introduces.
7. [governing claim] Storage is aggressive, complete, and low-ceremony; retrieval/activation is where the design intelligence lives.
8. [constraint] States that this inverts the emphasis of most memory system designs, which spend effort on what to store and how to compress.
9. [constraint] Builds on the premise that context efficiency is the binding constraint.
10. [constraint] Builds on the premise that storage does not imply activation: relevant knowledge can be present and still not surface, and the bottleneck is whether the workflow asks the right questions.
11. [constraint] Builds on the premise "store more than you load": raw traces are valuable for learning and audit but should not automatically become the next call's context.
12. [constraint] Builds on the premise that memory must serve action, not just retrieval: preferences, procedures, and judgment precedents, not just facts.
13. [constraint] Builds on the agency trilemma: no system combines high agency, high throughput, and high curation quality.
14. [constraint] Builds on lifecycle separation: knowledge, self-knowledge, and operational artifacts have different metabolic rates, and flat memory predicts search pollution and insight trapping.
15. [constraint] Builds on navigability vs retrieval: vector search optimizes for QA; articulated link networks optimize for reasoning.
16. [constraint] Builds on the premise that automated synthesis is the open frontier: extraction is automated everywhere, synthesis nowhere at production quality.
17. [constraint] Builds on the premise that agent statelessness makes routing architectural: every session is day one, and routing infrastructure is permanent prosthetics.
18. [constraint] Addresses the missing session-log capture.
19. [constraint] Addresses automated memory evolution (existing notes updating when new notes arrive).
20. [constraint] Addresses promotion heuristics (a pathway from observation to durable knowledge beyond human review).
21. [constraint] Addresses temporal reasoning (a queryable model of how knowledge changes over time).
22. [constraint] Treats session interaction logs as a primary input and rich, underexploited substrate.
23. [constraint] Identifies what session logs contain: decisions made, corrections, discoveries, preferences, procedures, and questions asked (as activation cues for future sessions).
24. [constraint] Places the design challenge in the retrieval/activation layer: finding the relevant precedent from long-past sessions, surfacing an earlier correction when the same mistake is about to recur, and graduating a pattern observed across sessions into an explicit preference.
25. [constraint] Drives the design by how memory is used, not just how it is stored.
26. [constraint] Covers the "why did we do it this way" use case: session logs as decision provenance.
27. [constraint] Presents session logs and ADRs as complementary: logs give complete provenance (including what was discarded) and answer unanticipated "why" questions; ADRs give distilled decisions and answer "why" efficiently.
28. [constraint] States the bridge: session logs make ADR writing cheaper, and ADRs make session logs navigable by pointing back to the sessions where the decision was made (an ADR is a distilled index into session logs).
29. [constraint] Generalizes beyond ADRs: any "why" question has an answer distributed across session logs, and the memory system's job is to make it findable without someone first writing it down manually.
30. [restraint] Does not present the memory system as a replacement for standard project structure (code, tests, documentation, CI configuration have their own homes).
31. [constraint] States the boundary principle: the memory system stores what project artifacts don't preserve — the reasoning, context, and process knowledge that produced the artifacts.
32. [constraint] Assigns homes consistent with the boundary table: code in the repository; API docs in project docs; architecture decisions in ADRs plus session logs; alternatives considered, and what was tried and abandoned, in session logs; user preferences and recurring corrections in the memory system; evolved operational procedures in the memory system, eventually project docs.
33. [constraint] States that the memory system is strongest where project artifacts are weakest: process knowledge, negative results, implicit preferences, and decision context.
34. [constraint] States a graduation pathway: some memory-system knowledge becomes project artifacts (a recurring procedure becomes a documented workflow, a preference becomes a linting rule), while session logs remain the substrate that keeps full provenance.
35. [constraint] Addresses the layered structure for stored-everything plus selective loading.
36. [constraint] Addresses how raw session logs relate to the library layer and what the extraction bridges are.
37. [constraint] Addresses whether there should be intermediate representations between raw logs and library notes (compressed episodes, indexed observations, fact extractions).
38. [constraint] Addresses which retrieval methods serve action-capacity, not just QA (cue-based rather than query-based retrieval).
39. [constraint] Addresses whether the system can pre-generate activation cues from session logs, as a question set future sessions match against.
40. [constraint] Addresses how to avoid the expertise gap (the person who needs activation scaffolds is least able to construct them).
41. [constraint] Addresses which extraction operations can run over session logs (preference mining, procedure extraction, correction consolidation, discovery flagging).
42. [constraint] Addresses which oracles are available (corrections are relatively clear signals; discoveries and preferences are harder to evaluate).
43. [constraint] Addresses whether promotion heuristics such as "seen twice on different dates" can work over session logs.
44. [constraint] Addresses whether "stores what project artifacts don't preserve" is a sufficient boundary, or has edge cases.
45. [constraint] Addresses which graduation pathways exist: when a session-log pattern becomes an ADR, a documented procedure, a linting rule, or a test.
46. [constraint] Addresses how the memory system relates to existing manual distillation processes (ADRs, writing conventions): complement, replace, or feed into.
47. [constraint] Addresses how much of the retrieval policy should be inspectable (explicit rules) versus learned from usage patterns.
48. [constraint] Addresses whether inspectable rules as the default with learned overrides for specific domains gets the best of both.
