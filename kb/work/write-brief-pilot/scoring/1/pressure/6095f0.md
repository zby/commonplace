# A context-operation interface bounds the projections its policy can realize

Retained state and active context are different runtime layers. Here, the retained substrate is projectable state available outside a bounded model input; retained controller state is tracked separately when it selects projections but is not itself projected into that input. Active context is what one bounded invocation actually receives. This follows the broader separation between [state retention and context assembly](./agent-runtime-analysis-should-separate-scheduling-context-state.md). A **context-operation interface** is the operations and permitted compositions through which a controller locates, materializes, transforms, and exposes retained state as active context. Its addressable units and exposure boundary are part of the interface. A controller or context policy chooses whether, when, and how to use that interface; it may be the receiving model, a learned controller, a host or proxy, or a mixed arrangement. Holding the retained substrate, model, and resource budget fixed, the interface bounds the projections that policy can realize.

Let `I` include the operation semantics, addressable units, composition rules, and the boundary where a view becomes model input. For retained state `S`, task and run signal `x`, fixed model or models `M`, and fixed budget `B`, define `Reach(I, S, x; M, B)` as the active-context views obtainable through legal interface traces. `B` includes the applicable active-context, model-call, time, and tool-use limits. A trace may locate, expand, transform, summarize, filter, delete, or expose retained material. It may also update retained state before exposure. “Projection” therefore means the task- and state-conditioned view delivered to the model, not a lossless or non-mutating mathematical projector. A required view lies outside `Reach` if producing it needs an unavailable operation, an unaddressable distinction, or a forbidden composition. In particular, [access and transformation impose distinct burdens](./access-burden-and-transformation-burden-are-distinct-query-dimensions.md): finding retained input does not imply that the interface can turn it into the view the call needs.

A policy selects legal traces, so it induces achieved coverage or a distribution within structural reach. A better policy may choose useful traces more often, sequence them more reliably, or reduce their cost. Those gains do not add a view outside `Reach`, nor do they show that excluded projections are unnecessary. This is the context-projection instance of the more general result that [learning inside a fixed decomposition inherits its omissions](./learning-inside-a-fixed-decomposition-inherits-its-mistakes.md). If an intervention adds observations, external computation, tools, model capability, budget, or permission to change operation definitions, then a premise has changed. It is no longer only a better policy over the same interface.

## The interface is the controller's action space

In reinforcement-learning terms, the interface is the action space of the controller that chooses context operations, together with the transition rules that say what each action does to retained state and to the view being built. The context policy is the policy over that action space. The view delivered to the receiving model is the part of the state this claim is about. `Reach` is the set of views reachable from `S` under that action space within the horizon and cost limits in `B`. When operations are stochastic, as model-written summaries are, `Reach` is the support of the reachable views rather than one deterministic set.

Stated this way, the claim is the familiar one: optimizing a policy changes which reachable states it visits and how often, but not which states are reachable. Gains from better invocation timing, abstention, or sequencing are gains in achieved coverage. Adding an operation, making a new distinction addressable, or permitting a new composition changes the action space, and so changes the decision problem the policy is optimized in. A return curve for one action space is therefore silent about the returns available under an action space nobody trained on. The argument does not depend on the training method: it holds for reward-driven RL, distillation, prompting, or hand-tuning, because each only changes the policy.

Two features of context control differ from a textbook RL setup. First, the action space can be compositional. When actions are programs, as in RLM below, the reachable set is very large and a policy explores only a small part of it. Policy improvement can then look like new capability even though every newly produced view was already in `Reach`. Second, context operations usually share one action space with task actions such as searching or answering. Not managing context is then a real choice, and a context operation costs the task action it displaced.

## Architectural contrasts

Different composition languages make the interface variable concrete. A [practitioner account of recursive language models](../sources/recursive-language-models-what-finally-gave-me-the-aha-moment.ingest.md) describes model-authored programmatic exploration and transformation, with results exposed through printed output or a returned answer. The paper-described [lambda-RLM](../sources/the-y-combinator-for-llms-solving-long-context-rot.ingest.md) replaces arbitrary programs with a small typed combinator language. Paper-described [agentic context management](../sources/acm-agentic-context-management-for-long-horizon-tasks.ingest.md) (ACM) fixes two memory operations and trains when to invoke or abstain from them. These interfaces permit different legal traces even though each constructs bounded model context.

| | RLM (practitioner account) | λ-RLM (preprint) | ACM (preprint) |
|---|---|---|---|
| Operation interface | Model-written Python in a persistent REPL over a `context` variable; recursive sub-model calls; truncated printed output or a returned variable | Fixed typed combinators (`SPLIT`, `MAP`, `FILTER`, `REDUCE`, and others) run as one pre-built program; model calls only at bounded leaves | Two tools: `manage_context` summarizes earlier turns and archives the raw messages under an identifier; `query_memory` retrieves from the archive |
| Controller and action space | The receiving model; each action is a program, so the action space is open-ended and compositional | The model picks a task type from a fixed menu; a deterministic planner then fixes branching, leaf size, and composition | A trained agent chooses each turn among the two context tools and task actions such as search or answering |
| How the policy is improved | No training; prompting and scaffold | No training; the restriction sits in the interface | Teacher-guided on-policy distillation that labels both when to manage context and when to abstain |
| What the source reports about performance | A worked demonstration on one counting problem against a progression of simpler architectures; no controlled evaluation | More accurate than standard RLM in 29 of 36 model–task comparisons (four long-context tasks, nine open-weight models), with 3–6× lower latency among recursive methods; standard RLM's wins fall mostly on strong models or code QA | With Qwen3.5-9B, pass@1 over ReAct rises on BrowseComp-Plus (0.570 → 0.635 with the tools, 0.727 after training), DeepSearchQA (0.367 → 0.405 → 0.425), and SWE-Bench Verified (0.489 → 0.508 → 0.530); peak context mostly falls while tool calls often rise; a 4B model that stops after about two turns does not benefit |
| What the reported result compares | No matched comparison of interfaces | Two interfaces, with controller placement changed at the same time | Adding the interface against ReAct and threshold-summary baselines, then policy training inside the fixed interface |

The performance row repeats what each source reports; the results were not re-run here. The rows are not comparable to one another, because tasks, models, and metrics differ. Read against this note's claim, they test different things. ACM's post-training gain is the case the claim is about: policy improvement inside a fixed action space. It shows that learned timing and abstention helped on these benchmarks; it does not test whether another operation set would do better. λ-RLM is the only one of the three that compares rival interfaces, and there the smaller action space wins most comparisons. That fits the claim, which does not rank interfaces: a restricted action space can be easier to use well. Standard RLM's remaining wins, where adaptive code navigation matters, fit the reading that the combinator set excludes views some tasks need. The paper cannot attribute those wins to reach alone, because it changes controller placement together with the interface.

Who selects a projection is a separate coordinate. In the RLM account the model selects its view; in ACM a trained controller chooses fixed operations. A host or proxy can instead assemble a view before the receiving model sees it, while a mixed push/pull arrangement can combine preloaded material with model-requested expansion. These placements can coexist with different operation vocabularies, so controller placement does not by itself determine structural reach. Within-run, cross-restart, and cross-task retained state instead describe how long prior state can condition selection. Changing a retained invocation policy is not by itself a change to operation semantics or composition rules.

## Evaluation consequence

An evaluation of controller improvement should report the retained substrate and addressable units; operation semantics and composition rules; controller placement and projection boundary; mutable policies or artifacts and their persistence horizon; model; and resource budget. It should identify which coordinates stayed fixed and which changed. In RL terms, a learning curve should come with the action space it was trained in. Gains with one fixed operation set show that a policy was useful in the tested regime. They do not establish that excluded operations are unnecessary. Testing interface adequacy requires a rival operation/composition interface (an action-space comparison, not another policy), another constraint-changing intervention, or an argument that projections excluded by the interface cannot improve the objective.

## Scope

Structural reach is not achieved use. Exact retained material can coexist with a lossy or missed active projection. A legal trace may never be discovered or produced reliably, and a delivered view may still fail to affect behavior. The claim here ends at exposure into active context; [storage, read-back, and contextual activation remain distinct](./knowledge-storage-does-not-imply-contextual-activation.md).

The claim does not rank interfaces. A restricted interface may trade admitted transformations for reliability, safety, inspectability, trainability, latency, or cost. An open-ended programming interface remains bounded by its primitives, sandbox, permitted compositions, model competence, and budget. The system contrasts show that these architecture coordinates vary across described systems. The reported results compare bundles of coordinates, not single coordinates, so they do not estimate the causal performance effect of changing any one of them, and they leave open which interface is preferable under a given set of operational constraints.
