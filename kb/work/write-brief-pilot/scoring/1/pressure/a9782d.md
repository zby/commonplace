# A context-operation interface bounds the projections its policy can realize

Retained state and active context are different runtime layers. Here, the retained substrate is projectable state available outside a bounded model input; retained controller state is tracked separately when it selects projections but is not itself projected into that input. Active context is what one bounded invocation actually receives. This follows the broader separation between [state retention and context assembly](./agent-runtime-analysis-should-separate-scheduling-context-state.md). A **context-operation interface** is the operations and permitted compositions through which a controller locates, materializes, transforms, and exposes retained state as active context. Its addressable units and exposure boundary are part of the interface. A controller or context policy chooses whether, when, and how to use that interface; it may be the receiving model, a learned controller, a host or proxy, or a mixed arrangement. Holding the retained substrate, model, and resource budget fixed, the interface bounds the projections that policy can realize.

Let `I` include the operation semantics, addressable units, composition rules, and the boundary where a view becomes model input. For retained state `S`, task and run signal `x`, fixed model or models `M`, and fixed budget `B`, define `Reach(I, S, x; M, B)` as the active-context views obtainable through legal interface traces. `B` includes the applicable active-context, model-call, time, and tool-use limits. A trace may locate, expand, transform, summarize, filter, delete, or expose retained material. It may also update retained state before exposure. “Projection” therefore means the task- and state-conditioned view delivered to the model, not a lossless or non-mutating mathematical projector. A required view lies outside `Reach` if producing it needs an unavailable operation, an unaddressable distinction, or a forbidden composition. In particular, [access and transformation impose distinct burdens](./access-burden-and-transformation-burden-are-distinct-query-dimensions.md): finding retained input does not imply that the interface can turn it into the view the call needs.

A policy selects legal traces, so it induces achieved coverage or a distribution within structural reach. A better policy may choose useful traces more often, sequence them more reliably, or reduce their cost. Those gains do not add a view outside `Reach`, nor do they show that excluded projections are unnecessary. This is the context-projection instance of the more general result that [learning inside a fixed decomposition inherits its omissions](./learning-inside-a-fixed-decomposition-inherits-its-mistakes.md). If an intervention adds observations, external computation, tools, model capability, budget, or permission to change operation definitions, then a premise has changed. It is no longer only a better policy over the same interface.

## The interface is the controller's action space

For a reader who works on reinforcement learning (RL) for agents, the claim is a reachability statement about a sequential decision problem. Treat the controller that chooses context operations as the policy. Its actions are legal operation invocations with their arguments, and composition rules say which action sequences are legal. The operation semantics are the transition function over retained state and the view being built. The addressable units fix which distinctions an action can name. The exposure boundary determines what counts as the view delivered to the receiving model, and the budget `B` caps episode length and resource use. The reward is task outcome, measured downstream of exposure.

Under that mapping, `Reach` is the set of views reachable by some legal action sequence within budget. It is a property of the action space and transitions, not of the policy. Training the controller by RL, distillation, or prompting changes which trajectories it samples. It cannot put probability on a view outside `Reach`. So the best value any policy can attain is capped by the best view in `Reach`, and a learning curve that plateaus inside a fixed interface cannot tell a weak policy from a limiting action space. This is the familiar RL point that optimality is relative to the action set, applied to context construction. Action-space design stays a modeling decision outside the optimization, and a result obtained by optimizing inside one action space says nothing about rival action spaces.

Two features of context control sharpen the mapping:

- **Actions shape the controller's own observations.** When the controller is also the receiving model, each context operation changes what that model observes on its next step. The problem is then partially observable with observation-changing actions, so the interface bounds both what the controller can do and what it can later see.
- **Parameter updates can move the premise.** The rule above separates policy change from interface change. An update that alters an operation's behavior, such as training weights shared by the controller and a summarizer or querier model, changes operation semantics and therefore `Reach`. In that case a gain is not evidence of policy improvement alone.

A restricted action space can still be the better choice. RL practitioners trade expressivity against search difficulty, sample efficiency, and safety when they design an action space, and context interfaces face the same trade. The claim here is only that gains from optimizing the policy do not settle that trade.

## Architectural contrasts

Different composition languages make the interface variable concrete. The table places three source-described systems on the same coordinates. The results column repeats what each source reports about its own design. The rows use different tasks, models, and metrics, so the numbers do not compare across rows, and the table does not rank the systems.

|---|---|---|---|---|
| RLM, [practitioner account](../sources/recursive-language-models-what-finally-gave-me-the-aha-moment.ingest.md) | Arbitrary model-written code in a persistent REPL over a reference to the prompt; sub-agent calls; printed output truncated by the scaffold; answer returned as a variable | The receiving model | No measurement. A worked walkthrough of one letter-counting problem on which direct generation, RAG, ReAct, and CodeAct fail or scale poorly | Illustrates an open interface; it tests neither the interface nor a policy |
| lambda-RLM, [paper](../sources/the-y-combinator-for-llms-solving-long-context-rot.ingest.md) | Fixed library of typed, pre-verified combinators (split, map, filter, reduce, and others) over the prompt stored in a REPL; neural calls only at bounded leaves | The model picks a task type from a fixed menu; a deterministic planner sets the rest | Beats standard RLM in 29 of 36 model-task accuracy comparisons (four long-context tasks, nine open-weight models) with 3-6x lower latency among recursive methods. It wins every weak-model comparison but only 6 of 12 strong-model ones; free-form RLM wins most often on code QA | A comparison across interfaces, which is the kind of evidence a fixed-interface study lacks. It also moves control authorship from model to planner, so it does not isolate the operation set |
| ACM, [paper](../sources/acm-agentic-context-management-for-long-horizon-tasks.ingest.md) | Two tools: summarize and archive earlier turns, and query the archived raw turns by identifier | A controller model trained to invoke or abstain | Adding the two tools to a ReAct agent raises pass@1 from 0.570 to 0.635 on BrowseComp-Plus; training the controller within those tools raises it to 0.727. Smaller training gains on DeepSearchQA (0.405 to 0.425) and SWE-Bench Verified (0.508 to 0.530). Peak active context generally falls while tool calls often rise | Separates an interface-change gain from a policy-training gain. The training gain holds the two tools fixed, so it shows a useful policy within that action space, not that the two-tool split is adequate |

Source wording for the rows: the RLM account says the model "can write code to programmatically explore, and create new transformations of the prompt" (verbatim). In lambda-RLM, "The model is asked to choose a task type from a fixed menu based on a lightweight symbolic probe of the prompt" (verbatim). ACM's controller "jointly learns when to invoke context management and when to refrain from doing so" (verbatim), and its post-trained row reads "+ ACM 0.727 46.2 54k 0.425 58.8 41K 0.530 79.3 50K" (verbatim).

In RL terms, the lambda-RLM tier pattern fits the action-space trade above: the smaller typed action space helps most where the model is a weak free-form controller, and the free-form space recovers ground where a strong model can use its extra expressivity. The paper compares two whole architectures, so this is a consistent reading, not a measured effect of the operation set alone. ACM's numbers give the opposite case: part of the reported gain comes from adding actions and part from optimizing within them.

Who selects a projection is a separate coordinate. In the RLM account the model selects its view; in agentic context management a learned controller chooses fixed operations. A host or proxy can instead assemble a view before the receiving model sees it, while a mixed push/pull arrangement can combine preloaded material with model-requested expansion. These placements can coexist with different operation vocabularies, so controller placement does not by itself determine structural reach. Within-run, cross-restart, and cross-task retained state instead describe how long prior state can condition selection. Changing a retained invocation policy is not by itself a change to operation semantics or composition rules.

## Evaluation consequence

An evaluation of controller improvement should report the retained substrate and addressable units; operation semantics and composition rules; controller placement and projection boundary; mutable policies or artifacts and their persistence horizon; model; and resource budget. It should identify which coordinates stayed fixed and which changed, including whether any trained parameters also run inside an operation. Gains with one fixed operation set show that a policy was useful in the tested regime. They do not establish that excluded operations are unnecessary. Testing interface adequacy requires a rival operation/composition interface, another constraint-changing intervention, or an argument that projections excluded by the interface cannot improve the objective. In RL terms, a policy ablation does not substitute for an action-space ablation.

## Scope

Structural reach is not achieved use. Exact retained material can coexist with a lossy or missed active projection. A legal trace may never be discovered or produced reliably, and a delivered view may still fail to affect behavior. The claim here ends at exposure into active context; [storage, read-back, and contextual activation remain distinct](./knowledge-storage-does-not-imply-contextual-activation.md).

The claim does not rank interfaces. A restricted interface may trade admitted transformations for reliability, safety, inspectability, trainability, latency, or cost. An open-ended programming interface remains bounded by its primitives, sandbox, permitted compositions, model competence, and budget. The system contrasts show that these architecture coordinates vary across described systems, and they report each source's own results. Only the ACM results separate an interface change from a policy change, and none of the sources varies one coordinate while holding all the others fixed. The contrasts therefore leave open which interface is preferable under a given set of operational constraints.
