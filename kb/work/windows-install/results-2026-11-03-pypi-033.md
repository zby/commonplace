## Workjig recovery fixture

The handoff's [fixture](../framework-delivery/workjig-030-recovery-fixture.py), copied unchanged to the scratchpad and run with the installed tool's `Scripts\python.exe`, **failed**: line 54, `PermissionError: [Errno 13] Permission denied` from `lock.read_bytes()` inside `with hold(records):`.

Cause: Workjig 0.3.0's Windows backend (`workjig/platform.py`) locks byte 0 of `.lock` with `msvcrt.locking`, which is a mandatory byte-range lock. While the lock is held, a read of that byte through another handle is refused. On Linux, `fcntl.flock` is advisory, so the same read succeeds. The fixture's in-hold read assumes advisory locking.

A diagnostic copy, in the scratchpad only, recorded the in-hold read instead of asserting it and left every other check unchanged. It exited 0:

- `empty` and `interrupted` cases, two repetitions each: `Run()` rejected the records with "run record is missing"; the lock bytes were unchanged before and after `hold()`; `busy()` was true only while held; no `run.json` appeared.
- The in-hold read was refused in all four repetitions, including the empty file.
- `fresh-run`: `hold()` raised `RunBusyError` while `Run()` held the lock; `run.json` was created.
- `fresh-hold-then-run`, two repetitions: `Run()` raised `RunBusyError` while `hold()` held the lock, then succeeded after release.
- Workjig 0.3.0 from the tool's `site-packages`, no `direct_url.json`, temporary root removed.

So Workjig's recovery behaviour passes on Windows, and the prepared fixture does not pass as written. Whether to make the fixture platform-aware, or to treat the refused read as a Workjig concern, for example for tools that inspect `.lock` during a run, is a decision for framework-delivery. Workjig was not changed.
