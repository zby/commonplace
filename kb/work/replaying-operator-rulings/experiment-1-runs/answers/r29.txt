# Three changes to the deliberative learning definition

## 1. Restate condition 2 as an override test, and fix the deterministic-check note

**Change.** Replace "It is not bound to one measure fixed beforehand" with this: *something inside the named boundary can decide, for a stated reason about future work, to retain or reject a change against what any fixed check says, and can revise the check itself.* Then rewrite "A deterministic check is a degenerate on-balance judgment." A fixed check should count only when the loop that applies it can also judge whether it suffices. Merely holding open the claim that the measure is enough should not count.

**Reason.**
- As drafted, the note says "a change kept because a validator passed meets the condition." That contradicts condition 2 and the "Retention bound to a fixed measure" exclusion. It also contradicts checks case 4 (repairer alone: outside on J) and the Recuris placement.
- Any builder of a gated pipeline can say their gate is "the only reasonable measure." The note would then let almost every benchmark-gated system in.
- The checks already found the test that discriminates: does the score decide what is retained, and who inside the boundary may decide otherwise? The definition should state that test.

## 2. Say what "each change" quantifies over

**Change.** In condition 2, replace "Each change" with *each change the claim treats as learned (a candidate learning change) to the named store*. Add that other writes, such as logs, attempt records and caches, neither qualify nor disqualify the system. They are simply outside the claim.

**Reason.**
- Real systems write many things without judgment. Under "each change," KSI's placement flips depending on whether its attempt log counts, which the checks flag as unresolved.
- Read literally, the quantifier would also exclude Commonplace itself. That defeats the stated purpose of covering all the learning in Commonplace.
- Someone applying this to other people's systems needs to know which writes to inspect before any condition can be checked.

## 3. Make the system boundary an explicit, checked part of every claim

**Change.**
- Replace "the outermost loop that the system runs itself" with a rule. A placement holds only for a stated boundary and store. People or programs count as inside the loop only if their judgment is the step that retains changes to that store.
- Require claims to report which boundary was used. A human-inclusive placement is a different claim from an autonomous one.
- Restate the PRODIGY example accordingly. PRODIGY plus Minton passes only for a store that includes the utility formula Minton revised. It does not pass for the rule store that PRODIGY alone selected from.

**Reason.**
- Without such a rule, any fixed-measure system becomes "deliberative" once you draw the boundary around its designers. The PRODIGY sentence currently does this without naming the store, which makes the term trivially satisfiable.
- The checks already impose this discipline: "do not credit an automated loop with judgments its designers make elsewhere," and in case 5 the deployment verdict does not count for the weights. The definition should say it.
- Boundary-relative reporting also keeps Warp-style "human reviewers included" placements from being read as autonomous ones.
