## 1. Make condition 2 a retention decision, not an on-balance verdict of improvement

**Change.** Reword condition 2 along the lines of the checks' J: *"The loop itself decides, by weighing reasons about future work, whether to keep each change. The decision is not bound to a measure that the named system cannot question."* In the definition, use "on-balance" only for the later verdict on whether a change was learned. In the "deterministic check" note, cut the unconditional sentence "a change kept because a validator passed meets the condition." Say instead that validator-gated retention meets the condition only if the named system can question whether the validator suffices. Also replace the link example, since case 4 shows that resolving a link does not settle whether it resolves to the intended page. Add one sentence to the note: a retention decision under an Open verdict is a decision, not an on-balance claim.

**Reason.** The linked note defines an on-balance judgment of improvement as "every reasonable measure favors the successor." But the draft says Open is the usual verdict for a recent change, and that keeping such a change is "a decision." So as written, most of Commonplace's retention fails condition 2, including ADR 085's deletion rule, which explicitly commits "without claiming it won that comparison." The checks already use the looser J, so the definition and the checks currently disagree.

## 2. Scope "each change" to the changes the claim is about

**Change.** Say the conditions apply to the changes a learning claim concerns, that is, the candidate learning changes in the named store. Writes kept by default, such as logs, attempt records and ingests, are not deliberative learning. But they do not disqualify the learning that happens alongside them in the same store. Add a sentence under "The system, the store and the loop" requiring a claim to name which changes it covers. Then resolve the open question in the checks by recording KSI's "distilled guidance, not the attempt log" as the intended reading.

**Reason.** Commonplace itself appends and logs without per-write judgment. Read literally, "each change" therefore excludes the very system the term exists to cover. The checks already flag this quantifier as unsettled, and the KSI placement flips depending on how it is read.

## 3. Demote "legible store" from a condition to a reported property

**Change.** Drop condition 1 from membership. Report legibility as a property or named kind, for example "legible deliberative learning," which is the kind Commonplace practises. Keep the note on why legibility makes per-change judgment and criticism practical. In the checks, make S a reported column, and change case 5 to "outside on J."

**Reason.** S never does exclusionary work in the checks: every "Outside" placement (cases 2, 4, 5, 7 and Recuris) already fails J or C. So S only narrows the term without separating any case the definition needs to separate. Under the stated preference for generality, that is the clearest feature to move from membership to a reported property. It also leaves room for judgment-driven loops over less legible stores, such as researchers choosing between checkpoints, without changing any placement the KB relies on.
