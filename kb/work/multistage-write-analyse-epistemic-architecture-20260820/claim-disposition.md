# Claim disposition: analyse an external system's epistemic architecture

This is a source-first disposition for a new instruction. It fixes the instruction's practical purpose and the commitments that a later skeleton may realize. It is not instruction prose.

## Disposition vocabulary

- `keep` — required in the current instruction as part of its practical purpose, execution boundary, decision procedure, output contract, or verification.
- `merge` — preserve the commitment, but fold it into a named kept commitment instead of giving it a second section or independent explanation.
- `remove` — omit it from the instruction; retain it only as workshop evidence or discard it as irrelevant to execution.
- `defer` — keep it outside the current instruction and current drafting stage; a later trial, handoff, or separately authorized artifact owns it.

Source warrants below refer to sections of `brief.md` and `reconstruction.md`. Labels in square brackets are the reconstruction's source labels. `write-instruction.md` supplies the authoring constraint that repeated manual cases license abstraction, while cold trials test the resulting procedure.

## Selected practical purpose

**Practical purpose:** When an agent or maintainer is asked whether or how an external memory subsystem or whole agentic system produces knowledge, direct the executor to build an evidence-bounded analysis of epistemic objects and routes, distinguish content generation from warrant and later use, and return scoped route-level findings rather than a system-wide epistemic grade.

This is one type-appropriate instruction purpose. The artifact tells an executor what analysis to perform and what output makes that analysis complete. It does not try to establish a transferable theory claim, describe one external system, rank products, or modify another review workflow.

Its operative path is explicit manual invocation or retrieval by a trigger-focused description during external-system analysis. Its output informs a review; it does not itself accept the external system's claims. The procedure must remain collection-neutral so it can operate on either a memory subsystem or a whole agentic system without depending on either review collection.

## Authoring decisions resolved

### Meaning of “produces knowledge”

Do not make “produces knowledge” a system-wide scalar or membership label. At route level, the phrase may be used only when the route creates truth-apt content not already present as such in its inputs and the evidence licenses reliance on that output over a named scope:

- an entailed output requires warranted premises plus a warranted derivation within the declared interpretation or formal domain;
- an ampliative output requires a truth-apt candidate plus an evidence-consuming acceptance transition with a named criterion, intended use, and scope.

Report the two cases with their specific verbs: **derives warranted content** and **produces an accepted ampliative claim**. Report imported content as **acquired**, not produced. Reshaping, retention, retrieval, operational use, and direct policy adaptation do not qualify by themselves.

For an ampliative route, acceptance is the warrant-bearing boundary for this architectural classification. Integration is a separate fact about retention, connection, accumulation, or later use and is always reported separately. This choice does not assert infallibility or philosophical truth; it bounds what the inspected architecture warrants the reviewer saying.

**Warrant:** `brief.md` §§ Intended practical purpose, Required distinctions, Required instruction behavior; `reconstruction.md` §§ Reconstructed governing result, Transformation classes, Warrant/lifecycle/authority, Explicit unresolved markers [Brief; Discovery lifecycle; Warrant granularity].

### Lifecycle presentation

Use a separate compact lifecycle disposition keyed to each ampliative candidate's object ID and relevant route IDs. Do not repeat the whole lifecycle inside every authority-route row. The disposition must expose every phase and its evidenced state, acceptance criterion and scope, integration consumer, and missing evidence. The route ledger remains the record of checks and forces; the lifecycle record remains the record of a candidate's progress across those routes.

For acquisition, reshaping, entailed derivation, and direct adaptation, record that the discovery lifecycle is not applicable and give the relevant lineage, derivation, or update route instead. This avoids forcing non-ampliative transformations into a conjecture lifecycle while keeping coverage auditable.

**Warrant:** `brief.md` §§ Required distinctions, Required instruction behavior; `reconstruction.md` §§ Discovery lifecycle, Minimum output schema, Explicit unresolved markers [Brief; Discovery lifecycle; ARC case].
