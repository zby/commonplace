# Close the conjectural-learning workshop through staged rewrites

Commissioned by the operator on 2026-09-21: remove the experiment handover,
identify documents needing substantial editing or replacement, and prepare
their rewrites inside this workshop before migrating the library. This plan
governs workshop preparation. Applying changes to library, article, instruction,
type, or runtime files remains a later commission.

## Starting point

The [definitions](./definitions/) and [companion](./notes/commonplace-studies-conjectural-learning-through-retained-theories.md)
are the settled basis. The [stability test](./stability-test/strain-report.md)
found no necessary definition changes or flips among the fourteen boundary
cases. Reconstruction from retained criticism and reconstruction from inputs
and outcomes are now distinct comparisons; experiment choices do not block
the ontology migration. RSI material was checked for compatibility. No peer
experiment design is to be changed or handed new work by this plan.

The remaining problem is the library's dependence on the old ontology. A
global rename would preserve wrong membership claims: addressability and
retained theories were required, unsuccessful revision counted as learning,
and reconstruction was excluded. Rewrite those claims before changing names.

## 1. Identify the substantial changes

The first inventory is in [rewrites/README.md](./rewrites/README.md). It names
the old documents, why a local rename is insufficient, and what should survive.
It separates replacements already drafted here, substantial rewrites still
needed, bounded semantic edits, and historical wording to preserve.

Before drafting each item, read its current text and inbound uses. Confirm
whether its contribution still warrants a standalone document. A merge or
retirement is preferable to rewriting an argument whose only job was to
justify the classical import. Record the disposition beside the inventory
entry; do not create replacement prose merely to preserve a file count.

The inventory is a triage, not a closed list. Add a consumer when inspecting
it reveals an old membership condition or load-bearing attribution. Search
exact old paths and fragments as well as prose names. Mere occurrence of the
old term does not require a rewrite; source titles and historical statements
keep their meaning.

## 2. Draft the substantial rewrites here

Use [rewrites/](./rewrites/README.md) for new drafts, preserving the source's
repository-relative path beneath it. Existing definition and companion drafts
stay in their current locations as the single working copies. Record source
version, proposed destination, disposition, and status when drafting starts.
Resolve draft links to existing workshop or library files; record proposed
final names separately until they exist.

Work in dependency order:

1. Resolve the old definitions' remaining content and the lineage note. Check
   the builder definitions without silently changing what counts as a builder.
2. Rewrite the evidence and conjecture notes and decide the reconstruction
   proposal's fate. Preserve the evidence ladder, capacity distinction,
   causal-use requirement, and the limits on what each comparison identifies.
3. Stage the operational vocabulary consumers together: the analysis skill
   and its result type must describe the same classification. This is an
   ontology update, not a redesign of their pipeline or persisted schema.
4. Draft the lead article and affected supplement sections after the note
   basis is coherent. Keep this as a separate writing pass, as the migration
   notes require. Preserve the exporter example, maintenance costs, and
   independently adopted research hypotheses. The three mechanism conjectures
   do not automatically replace the program's sufficiency, comparative, and
   reflection hypotheses.

At each step, settle the contribution and destination before expanding prose.
If a rewrite requires changing an adopted definition, name the decision-record
test and affected cases and return that choice to the operator. A new research
question becomes a bounded gap, not an expansion into experiment design or a
new literature-review project.

## 3. Review the package before migration

Read the staged definitions, notes, operational wording, and article account
together. Check the [decision record](./definition-decision-record.md): six
tests, fourteen cases, and the adopted capacity, observer-access, and RSI
decisions. Learning needs improved capacity; comparison arms are arrangements,
not assertions about unseen processing. Reflection still requires causal
self-representation. Surviving criticism can change reliance without changing
theory text. EITHER and FORTE remain bounded repair precedents.

Read each intended destination's collection and type contract before authoring
its draft. Validate staged files by explicit path. Review changed source claims
against retained support; the stability probes are not experimental evidence.

Prepare one concrete migration inventory: each original is kept with bounded
edits, replaced, merged, renamed, or retired; each surviving claim has a
destination; each old path and fragment has a disposition. Include instruction
and type consumers, `AGENTS.md`, navigation, redirects, and affected test inputs.
Name peer-workshop dependencies separately. If a reference there would break,
identify the minimal reference repair for the migration commission rather
than redesigning the peer's experiment.

Report simplification using the [migration accounting](./migration-map.md):
words removed, retained, and added, and both definition-file and defined-concept
counts. The two old definition files also contain tentative/addressable
definitions; the three new files must not be called a file-count reduction.
Explain which apparatus disappears and whether the acceptance criterion is
met. Any unresolved interpretation of that criterion belongs in the package
presented to the operator.

## 4. Apply the reviewed migration under its commission

Once the operator commissions migration against the concrete package, apply
the staged substantive changes, then bounded terminology and reference updates.
Check originals against the versions used for drafting so concurrent edits
survive. Use repository relocation and retirement procedures; keep relocation
commits pure and update links, fragments, redirects, and indexes for the final
destinations. Source-native and historical claims keep their original meaning.

Validate changed artifacts and navigation with the relevant Commonplace
commands. Run software tests if executable code, test fixtures, or test inputs
change; Markdown data changes use artifact validation. Recheck the consumer
inventory for unresolved current-ontology uses, allowing historical and
source-native wording. No experiment is run by this plan.

## 5. Close only after the results have destinations

Retain the stability finding and relevant decisions in the decision record
during drafting. At final closure, carry binding vocabulary into the adopted
definitions and record the migration's decisions and change accounting in its
commits. Give any still-needed source comparison or unresolved theoretical
claim a library destination or a reasoned disposition. Do not create an ADR
solely to narrate the migration.

Delete consumed stability probes and scaffolding after checking that no unique
decision, source limitation, or live claim depends on them. The probes need
not become experiment designs. Once every item is promoted, incorporated, or
deliberately declined, delete this workshop and remove its active-index entries.
Workshop closure creates no redirects for temporary workshop URLs. Unresolved
migration work keeps the workshop open; finishing the plan or drafts alone
does not close it.
