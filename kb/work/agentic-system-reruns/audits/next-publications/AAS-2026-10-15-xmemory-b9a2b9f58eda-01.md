## Consequential discrepancies and public qualifications

### 1. Hierarchy use is retained, with a more precise graph distinction

The old account calls the hierarchy an access structure and warns about missing message-level edges. The new account does not discard hierarchical retrieval: synthesis, “From stored hierarchy to an answer,” describes live theme membership, representatives and episode selection. It distinguishes these live files from diagnostic GEXF export.

At the current pin, `src/core/memory_system.py:2004-2043` constructs empty `message_ids` without an episode `messages` attribute. More decisively, `update_hierarchy_graph`, around lines 2120-2155, explicitly sets `new_messages = []` before `incremental_update`. New `memory.md`, `MEM-OBJ-memory-graph`, states that shipped updates pass no message nodes and that batch-local endpoint maps limit edges. The synthesis says export does not prove complete synchronized abstraction. This preserves the historical caution without treating the exported graph as the adaptive reader's substrate. No coverage regression established.

### 2. Retrieval efficiency is not presented as verified uncertainty reduction

The historical account emphasizes context efficiency and adaptive selection. The new synthesis appropriately narrows stronger claims. Direct inspection of `evaluation/locomo/xMemory_search_framework.py:1190-1289` confirms a fixed `base_H_ep = H_sem_only`, per-candidate `episode_ids=[eid]`, `ig = H_before - H_after`, thresholded inclusion and a first-candidate fallback. It does not score the growing selected episode set on each iteration.

The public synthesis explicitly calls the score mean generated-token negative log probability, identifies negative thresholds and fallback, distinguishes scoring context from final answer input, and withholds verified uncertainty reduction, original-expansion utility and answer improvement. Its overview description independently withholds verified fidelity, uncertainty reduction and improvement. These qualifications are already public; this audit is not supplying a missing caveat.

### 3. Pull retrieval versus internal update supply is not a hidden host integration claim

The old account reports pull-only public retrieval and no ambient host-agent wrapper. The new synthesis retains requested QA retrieval as pull, while distinguishing automatic retained-input supply to internal update-model calls. It also says facade calls do not automatically run the complete driver maintenance sequence. That is a change of analytical granularity, not an assertion that an external host now automatically recalls memory. No new deployment integration or observed execution is claimed.

### 4. The separate model judge exists; the omission is already disclosed

Read the complete current `evaluation/locomo/metrics/llm_judge.py`. It consumes saved question/reference/response records, skips category 5, asks `gpt-4o-mini` for a JSON label, maps `CORRECT` to 1 and other labels to 0, writes labels and prints category accuracy. This is separate from the commented judge call in `evals.py`.

Report verification discloses that analyst route records do not separately characterize this executable judge. The public synthesis repeats the finding in its answer/evaluation paragraph and limitation table, explicitly prohibiting an inference that no judge ships. The inspected standalone file reports scores; it supplies no automatic memory-revision consumer. Accept the narrower lexical-route account, not complete evaluator comparison or model-judged correctness/provenance coverage. To remove this limit requires accepted route records characterizing the standalone judge and its consumers; not a hold on the existing qualified account.
