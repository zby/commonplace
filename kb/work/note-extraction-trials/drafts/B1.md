# Frontloading can specialize an instruction to known inputs

Suppose an instruction says, “List the files in `kb/notes/`, then choose the file that best answers the user's question.” If the directory contents will remain stable through the call, the listing can be computed before the question is known. The resulting instruction reads, “Choose the file that best answers the user's question from this list: …” The filenames are settled; their relevance is not.

Partial evaluation gives a precise account of that split. In programming, a *partial evaluator* takes a program and the inputs already known, called *static* inputs. It produces a *residual program* that takes only the remaining, *dynamic* inputs. The requirement is that running the residual program on the dynamic inputs gives the same result as running the original on both sets of inputs.

Dividing the work into stages explains why the listing can be produced early. The partial-evaluation framing identifies what remains: an instruction specialized to this directory snapshot, not merely a listing passed to another worker. Since instructions and filenames can both be represented as text, the listing can replace the lookup directly in the prompt. It is the *whole revised prompt*, not the listing, that plays the role of the residual program.

The analogy describes the substitution; it does not guarantee the same choice of file. Natural-language instructions do not specify an exact interpretation, even when the listing is unchanged. The practical gain is that the model can judge relevance without spending context on the lookup, not that the two prompts are provably equivalent or that the call must run faster.
