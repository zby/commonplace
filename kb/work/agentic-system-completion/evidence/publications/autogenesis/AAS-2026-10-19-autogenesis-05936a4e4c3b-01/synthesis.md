# Autogenesis synthesis

## Bounded synthesis

### From request to model-directed work

Autogenesis is an enclosing multi-agent runtime with an internal capability-generation and optimization plane. It claims to complete user tasks through tools, delegated agents, skills and connectors, and to repair missing or weak capabilities. This account covers its shipped Gateway, direct Python drivers, workflow/canvas execution, retained state and extension admission at commit `5b070d5cd497e951a188a01409138e8b530eaf4a`, with an analysis cutoff of 2026-10-19. SRC-1 supplies source-code implementation and prompt/design evidence. No target execution, task trace or causal experiment was supplied or performed. External services, dependency internals and excluded gitlinks are not frozen. The [source register](boundary.md#source-register) fixes those limits; neither source inspection nor the independent verifications establishes successful operation.

A Gateway submission returns task and conversation identities before execution. A worker invokes MetaAgent through a runtime that owns the agent reference, mailbox, outstanding actions and reply. Each round rebuilds context and capability schemas, then streams a configured model. The model chooses actions; code routes them, applies hooks and limits, executes capability managers and constructs the terminal response. The ordinary configured endpoint is `google/gemini-3.1-pro-preview`, not an immutable weight/build identity. Provider training and actual endpoint resolution remain uninspected. See [RT-RTE-gateway-task](runtime.md#rt-rte-gateway-task) and [RT-CMP-model-manager](runtime.md#rt-cmp-model-manager).

Delegation gives a child a fresh context with selected task text, existing files and explicit restrictions or target defaults. The child's returned message crosses back, not its complete transcript. Shared workspace, services and registrations remain shared effects. Parent allowlists are not intersected with child grants on this path. A skill call instead returns method text and resource information to the calling model; it does not start a separate worker. These distinctions determine both evidence transfer and context size: separate work keeps internal child history out, but the parent must explicitly package requirements and evidence for subsequent workers. See [RT-RTE-child-delegation](runtime.md#rt-rte-child-delegation), [RT-RTE-skill-delivery](runtime.md#rt-rte-skill-delivery) and [WF-RTE-ui-verification](workflow.md#wf-rte-ui-verification).

Dispatch rejects names outside the round's assembled routing table. That invariant does not confine arbitrary shell or generated Python effects. The agent's read-only deny set covers five named mutating tools, not Bash; Bash uses its own permission registration, and the default imported configuration permits full access. Without a bound peer sandbox it launches a local subprocess. No deployed isolation or exploit is demonstrated. Workflow steps call managers directly, direct model chat omits agent task/review gates, and ProceduralAgent runs a procedure rather than the model-round loop. Controls must therefore be stated per route, not as universal runtime guarantees. See [RT-RTE-direct-agent](runtime.md#rt-rte-direct-agent), [RT-RTE-workflow-execution](runtime.md#rt-rte-workflow-execution) and [RT-RTE-model-chat](runtime.md#rt-rte-model-chat).

### Retaining experience for the next decision

The strongest supported experience-fed contribution is a complete automatic path from lifecycle records to retained summaries and later model input. Hooks project task/action/results into resident recent history. On overflow, code removes the oldest chunk, supplies it and the previous summary to a model, and stores any nonempty summary. Empty output restores the chunk. Later agent requests select recent records and working summaries by session identity and count windows. The summary also reaches the next summarization call. This is wired trace learning in the write-route sense: experience produces retained behavior-shaping material. It is not evidence of learning as improved capacity for future action. See [MEM-RTE-history-compaction](memory.md#mem-rte-history-compaction), [MEM-RTE-tiered-context](memory.md#mem-rte-tiered-context) and the independent [profile verification](profile-verification.md#verification).

The selection is chronological rather than task-relevance ranking. Count limits do not bound tokens, and final-result text has a separate, unbounded-by-fetch-count inclusion. Nonemptiness is not a fidelity check. Successful compaction replaces raw detail without a per-summary assertion-to-event map; bounded summary storage eventually discards older chunks. Exact semantic preservation remains indeterminate without an input/output pair. The retained text supplies context, not verified facts or enforced conduct. See [MEM-OBJ-working-memory](memory.md#mem-obj-working-memory), [EPI-RTE-history-compact](epistemic.md#epi-rte-history-compact) and [EPI-RTE-summary-retain](epistemic.md#epi-rte-summary-retain).

Persistence has distinct consumers. Tiered memory writes JSON/HTML displays, but its inspected built-in backends do not reload session tiers from disk after eviction or new-instance construction. Todo plans do reload JSON and supply same-ID Markdown automatically during context construction, independently of the memory switch. Conversation events reopen in the shipped client, not in a tiered-memory loader. Knowledge corpora reload on explicit queries and return lexically ranked document bodies in result data; a workflow must map those data to any later model. These are separate routes, not interchangeable evidence of cross-restart model recall. See [MEM-ABS-tiered-reload](memory.md#mem-abs-tiered-reload), [MEM-RTE-todo-context](memory.md#mem-rte-todo-context), [MEM-RTE-conversation-replay](memory.md#mem-rte-conversation-replay) and [MEM-RTE-corpus-retrieval](memory.md#mem-rte-corpus-retrieval).

### Checking a product and deciding to finish

The representative shipped request is a React shopping site whose acceptance conditions require working browser interactions after deployment. It is an intended workflow over implemented mechanisms, not a completed episode. MetaAgent is directed to delegate implementation, obtain the deployment's actual URL, pass that exact URL to a browser agent, and optionally send requirements, artifacts and browser evidence to a reviewer. Reported defects should lead to parent-directed repair, redeployment and renewed checking. A redeploy may change the URL and invalidate earlier evidence. The reviewer is instructed to recommend continuing when only curl or bundle evidence exists, but its verdict is advisory text. See [WF-RTE-ui-verification](workflow.md#wf-rte-ui-verification).

This workflow distinguishes product repair from runtime self-change: fixing a cart or image does not itself improve Autogenesis's capability organization. It also distinguishes requested acceptance from runtime return. Deployment success means a running-status record, not demonstrated checkout behavior. Normal agent completion uses done_tool, but limits and no-progress stops can end work earlier. MetaAgent has a repeated-batch path that marks done while reporting incompleteness. Gateway's task.completed event therefore certifies a return, not successful storefront delivery. Browser/reviewer checking is not a mandatory generic completion gate. See [RT-RTE-gateway-task](runtime.md#rt-rte-gateway-task).

There are nevertheless concrete narrow checks. Exact-match benchmarking computes equality against supplied references; it does not validate reference truth or identify the answer-producing mechanism. Workflow evaluation admits records only after version/run/hash/terminal-status consistency checks, requires retained real runs for successes, and rejects duplicate run evidence. Its health summary aggregates current-version evidence, but quality scores remain caller-supplied and the inspected consumer does not automatically roll back from that summary. These are distinct licenses: reference comparison, evidence-ledger admission and advisory assessment, not a universal factual acceptance process. See [EPI-RTE-exact-match](epistemic.md#epi-rte-exact-match) and [EPI-RTE-workflow-evaluation](epistemic.md#epi-rte-workflow-evaluation). Generated factual novelty and accepted domain knowledge remain undetermined without proposition-bearing outputs linked to inputs and checks; this is not an absence claim about unassessed domain evaluators.

### Changing capabilities and carrying changes forward

Autogenesis has implemented improvement-directed self-change capacity, beyond producing external work products. A successful generator or optimizer can trigger software validation/promotion, register changed capability source, retain archives and a manifest, and expose supported capabilities to later dispatch. The generic smoke check runs after live loading, is optional—including through an explicit false forwarded by Gateway—and need not invoke the changed component or compare its output to the requested OK text. It consumes response success and constraint status. Rejection can revert or unload registration, not undo arbitrary import-time or external effects. Prompt requests for explicit user approval are not an enforced approval rendezvous. See [RT-RTE-extension-admission](runtime.md#rt-rte-extension-admission), [RT-BAP-capability-load](runtime.md#rt-bap-capability-load) and [RT-CLM-evolution-guidance](runtime.md#rt-clm-evolution-guidance).

Memory source admission has a consequential exception: class registration stores instance=None, so lifecycle hooks and prompt reads skip that configuration until a separate build or supplied-instance path provides a live instance. Archiving source and executing a constructor do not establish later memory delivery or session migration. Separately, the creator's renderer guidance conflicts with consumption: overriding _render changes persisted views, not inherited get selection. The memory evaluator also uses mismatched interface assumptions, and its named probes were not located in bounded searches. These findings qualify that specific improvement pathway without negating working built-in memory or other live capability changes. See [MEM-RTE-memory-admission](memory.md#mem-rte-memory-admission) and [MEM-CLM-memory-guidance](memory.md#mem-clm-memory-guidance).

Workflow checkpoints carry another bounded form of reuse. Resume checks runtime-major and workflow name/version, and rejects unequal nonempty program hashes. A supported hashless migration path instead stamps the current hash and can cache completed work without verifying its original executable identity. Neither branch establishes output truth or exactly-once external effects. Canvas JSON reuse and capability-version checkpoints are different retained artifacts, not generic agent mailbox or memory restoration. See [RT-RTE-workflow-execution](runtime.md#rt-rte-workflow-execution) and [EPI-OBJ-checkpoint](epistemic.md#epi-obj-checkpoint).

The theory-builder findings remain independent. For the formulated evolution method, condition 1—localized content—is wired in prompt/playbook text. Condition 2—meaning-dependent consumption—is requested but unobserved. Condition 3—content-directed criticism—is prescribed, with no supplied challenged claim, result, blame assignment and revision episode. Condition 4—retained criticism shaping a next round—is likewise prescribed, not observed. The ordinary skill projection additionally filters out the orchestrator-tagged evolution playbook, although evolution guidance is directly present in the prompt. These limits do not erase the localized method or generator capabilities. See [RT-RTE-extension-admission](runtime.md#rt-rte-extension-admission) and [RT-RTE-skill-delivery](runtime.md#rt-rte-skill-delivery).

Criticism of a consumed theory improving future capacity is unestablished. Reflection is afforded by source/configuration representations that can guide changes to the represented capabilities; an exercised bidirectional episode is unobserved. The computational task/delegation/admission routes do not establish autonomous theory building: computation performing every criticism and retention operation has not been shown. Reflective theory building is also uninspected as an exercised property. For self-improvement, the boundary is Autogenesis's capability organization, the horizon is later calls/sessions, and the independent objective is successful user-task execution. Wiring supports improvement-directed change, but no supplied episode closes objective-bearing evidence shaping an update through later operation causally depending on it. Thus exercised self-improvement and successful improvement are not established, separately from wired trace learning and self-change capacity. See [RT-RTE-extension-admission](runtime.md#rt-rte-extension-admission) and [MEM-CLM-memory-guidance](memory.md#mem-clm-memory-guidance).

For the shopping-site scenario, the supported assessment is capacity to orchestrate implementation and evidence handoffs, with model-owned acceptance and no demonstrated delivery. A linked browser/deployment/review trace would establish exercised verification; independent acceptance results would support bounded delivery claims. For capability improvement, an objective-bearing failure, selected revision, live registration, later invocation and controlled outcome comparison would change the present attribution. Building a usable memory instance, correcting renderer/reader guidance and aligning evaluator probes would repair specific downstream gaps, but would still not prove benefit. No target source was read for this synthesis; its account uses the supplied records. Both independent verifications declare no blockers or additional limits ([report verification](report-verification.md#verification), [profile verification](profile-verification.md#verification)).
