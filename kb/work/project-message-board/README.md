# Cross-harness handoffs as project work becomes actionable

Posed by the operator on 2026-11-27. For roughly ten to twenty agents on one project, how does a decision or change made in one task reach another before its next affected action? **Cross-harness use is the first requirement:** a successor must be able to pick up a handoff without the original session. Start with ordinary project handoffs and workflow stops. A message board is a candidate, not the intended result. This commission does not authorize a swarm, a scheduler or replacement of the live mailbox.

The [unresolved frontier](../../reference/definitions/unresolved-frontier.md) is work some currently available actor or process can take a workable step on now. Before two writers agree who will stage a shared file, deciding the split is actionable for them; staging under the proposed split is not. A handoff can preserve the blocked action and the reason to reconsider it without putting it on the frontier. When the decision arrives, check what it actually settled: staging may now be possible, still need another input, belong to the other writer, or no longer be needed. Being actionable neither sets priority nor grants permission.

Test two different filters on existing project records: *What decision can I make now?* and *What should I reconsider because this decision was made?* The second can return blocked or obsolete candidates. Neither the records nor a filtered inbox are the frontier itself.

That pair needed neither a permanent agent account nor the recipient's harness name. It does not tell us how the recipient knew to look. The operator reports that the mailbox works poorly. Before attributing that to the format, recover a missed or costly exchange: could the sender name the destination, could both parties see the same files, did the recipient know when to check, and could it find the reply among unrelated traffic? An unanswered file alone does not establish a missed message. If no failed exchange can be recovered, label the diagnosis unconfirmed.

## What does the computational model predict?

Start with the [five historical cases](./examples.md), not the candidate protocol. In the [bounded-context orchestration model](../../theory/bounded-context-orchestration-model.md), a caller selects work from known state and collects results from calls that do not affect each other before they all return. The trace investigation (case 5) could be such a call. The staging agreement (case 1) could not be obtained that way: the other writer had its own commission and could accept or reject the split independently. A human's new direction (case 3) was not even a pending question. Treat those posts as external events. Reading a snapshot of the board can give the *next* call a fixed input; it cannot make the live project a closed world.

This distinguishes two jobs called scheduling. [Ordinary host-language code](../../theory/the-practical-scheduler-is-the-host-language.md) can choose the next Workjig call after a reply has been observed. It cannot notice the reply when that code is not running. For each case, ask **who observes the external change, and before which action must they observe it?** Compare delivery guarantees, not [channels alone](../../theory/agent-orchestration-needs-coordination-guarantees-not-just.md): a post being available, a writer reading it before staging, and both writers agreeing are three different outcomes. If an answer does require further model work, [continuing the conversation or preparing a fresh call](../../theory/conversation-vs-prompt-refinement-in-agent-to-agent-coordination.md) is a separate choice: record what unfinished work a restart would lose before requiring session resumption.

## Compare a handoff with a shared feed

Start with the staging case. In the task handoff, point to the pending ownership decision and say what action it prevents. Have a successor in another harness find the decision at the point it would otherwise stage the files. Replay both acceptance and a different ownership split: in the second trial the successor must not stage the files just because a reply arrived. Check whether the handoff and the existing mailbox suffice before testing a board.

For the board comparison, try one project feed. Let a writer post a body under a project-local task label, optionally address another task, and reply by a stable post ID. Let a reader see notices for everyone and exchanges involving its task, and retrieve the parent of a reply. Treat the label as a return address, not proof of authorship. Prefer the identifier in the task commission; when none exists, try an explicitly supplied role or label. Test two independent tasks choosing the same label as well as a successor deliberately reusing one. Those cases need different outcomes.

Compare this with the unchanged mailbox on the same exchange. Have two different harnesses in sibling worktrees use only the documented project entry point and their task briefs. One posts a question, the other finds it among posts from unrelated tasks and replies, and a fresh session continuing the first task finds the answer. Include a project-wide notice and two simultaneous posts. Record where the state lives, when each reader checks, what survives restart, any lost or ambiguous post, and every operator relay or harness-specific setup step. Do not count an explicit check as automatic notification.

Remove one field or operation at a time. If a documented shared location and check occasion fix the exchange with ordinary files, keep those rather than adding a service. Require a demonstrated failure before adding accounts, per-reader cursors, channels, acknowledgments or push delivery. Task scheduling and private email delivery are outside the test.

## Which coordination features must a harness supply?

Synchronization is the first design question. Test whether a cooperating harness needs only two capabilities: receive a task address and board location in its ordinary task brief, and run a board read or post whose result the agent can see. Neither a permanent account nor the ability to inject text into a running session is a prerequisite. The commission says whether this task may consult the board at all.

Separate three delivery cases:

- **Waiting for a reply:** try a bounded wait from the last observed board position. Post the reply between the read and the wait. The wait must return the existing reply rather than block until another message arrives. One-shot polling and a blocking command should agree about what is pending.
- **Busy:** at an agreed point, such as before publishing work affected by the answer, check again. If that is too late, record the actual deadline missed. A harness hook that offers a notice on the next turn is an optional improvement; terminal output alone does not demonstrate that the model saw it.
- **Not running:** keep the post available to a successor under the same task address. If delivery cannot wait until the next ordinary invocation, identify who may start one, under what budget, and how two notices for the same task avoid starting competing workers. This is a scheduling decision, not a property of posting.

For a Workjig trial, let the **workflow** own the address and the inbox check between steps. If a worker needs an answer, it can return a blocked result (a proposed workflow outcome, not a Workjig feature); the controller can end the worker, retain what action is blocked, and reconsider it when the reply arrives. End the workflow if the action is no longer needed; include the reply in a later worker's inputs only if another call is warranted and authorized. This follows the existing split: [Commonplace decides whether to launch; Workjig executes the call](../../reference/adr/119-analysis-workers-launch-through-workjig.md). In a [review with captured inputs](../../reference/review-architecture.md), do not let a board update silently change the evidence mid-call. Do not wake a closed workflow merely because it has unread mail.

Try the same question and reply with an interactive task and with a workflow across two short-lived worker calls. Include a reply posted while no worker is alive. Record separately when the board stored it, when the controller noticed it, and when a worker actually received it. The deciding question for a scheduler is whether the project needs a maximum delay when **neither a worker nor its controller is running**. If so, a persistent watcher or periodic invocation must be owned somewhere; a harness hook alone cannot meet that requirement.
