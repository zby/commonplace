# Claim disposition: the context-operation interface bounds context policy

### 1. The interface bounds reachable projections

- **Claim:** Holding the retained substrate, model, and resource budget fixed, a context-operation interface bounds the active-context projections a policy can realize, so improving the policy can improve selection within that set but cannot by itself expand or validate the interface.
- **Relation to the user-supplied target:** This is the authoritative intended contribution and directly answers the governing question.
- **Evidential basis:** The brief fixes the contribution; the reconstruction supplies the `Reach(I, S, x; M, B)` inference, the fixed-decomposition premise, and proposition-relative system contrasts.
- **Existing artifact:** No existing durable artifact states the context-specific reachable-projection claim, including operation semantics, allowed composition, and the exposure boundary, adequately. `kb/notes/learning-inside-a-fixed-decomposition-inherits-its-mistakes.md` supplies the more general learning boundary but not this application.
- **Disposition:** `central contribution`
- **Applicable target path:** `kb/notes/context-operation-interface-bounds-context-policy.md`
- **Citation/revision boundary:** The target will be citable as the context-projection instance of the general fixed-decomposition result without making readers import a survey, a controller-training claim, or a performance ranking.

### 2. Context-operation interface is a local operational definition

- **Claim:** A context-operation interface comprises the operations and allowed compositions through which a controller locates, materializes, transforms, and exposes retained state as active context.
- **Relation to the user-supplied target:** The definition fixes the central claim's independent variable and prevents interface from being collapsed into either retained storage or controller behavior.
- **Evidential basis:** The definition is authoritative user direction in the brief; the reconstruction makes its components explicit across the comparison corpus.

- **Relation to the user-supplied target:** This is a premise for distinguishing the retained substrate from the active-context projection.
- **Evidential basis:** The reconstruction's retention-versus-active-context distinction and its cross-system storage/assembly examples.

### 4. Storage fidelity does not establish projection fidelity

- **Claim:** Exact retained material can coexist with an active view that omits or transforms a task-relevant distinction, so fidelity of storage does not establish fidelity of the projection delivered to the model.
- **Relation to the user-supplied target:** This is the storage-side consequence of making the projection boundary explicit.
- **Evidential basis:** The reconstruction's ACM, Virtual Context, Letta, OpenViking, and Playground cases, together with the stored/read-back distinction.
- **Existing artifact:** `kb/notes/knowledge-storage-does-not-imply-contextual-activation.md` adequately states the general storage-to-context gap; the term “projection fidelity” is a local application of that established distinction.
- **Disposition:** `cite existing`

- **Citation/revision boundary:** The existing note owns the general retention/read-back claim, while the current target can use it as a premise without absorbing the later context-to-action argument.

### 6. Access and transformation are distinct burdens

- **Relation to the user-supplied target:** This explains why two interfaces with similar retrieval can admit different projections when their transformation operations differ.
- **Evidential basis:** The reconstruction's access-versus-transformation distinction and the RLM, lambda-RLM, and Virtual Context contrasts.

- **Evidential basis:** The reconstruction's lambda-RLM tension, RLM/Scroll bounds, and the brief's explicit exclusion of a programmable-interface superiority claim.
- **Existing artifact:** The RLM/lambda-RLM comparison states restriction differences and the cited sources report practical tradeoffs, but no existing artifact warrants a universal ordering—and none is needed.
- **Disposition:** `support/example/scope only`
- **Applicable target path:** `kb/notes/context-operation-interface-bounds-context-policy.md`
