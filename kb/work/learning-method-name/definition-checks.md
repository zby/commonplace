# Step 1: checks for deliberative learning

Tested against the [workshop draft](./draft-definition.md), not an adopted library definition. Revised on 2026-11-21 by Fable (claude-fable-5-2) after the operator ruled that a fixed measure is a special case of the second condition and named the two kinds single-loop and double-loop, and updated on 2026-11-21 by Neon (gemini-4-neon) for the reliance wording, graded attribution, and Gödel-machine boundary cases (cases 13–16). The stipulations of cases 1–12 are unchanged; the version before the fixed-measure ruling is in commit `3f4e48736`. [What the ruling changed](#what-the-ruling-changed) lists the placements that moved. Keep the numbered cases and their assumptions stable when testing new wording. A change that flips a placement deserves an explanation. Run the checks on the named system and store; do not credit an automated loop with judgments its designers make elsewhere.

## Stipulated cases

The three conditions are **S**: what is learned is held in the contents of a readable store, and the system learns by changing those contents; **J**: a judgment made in the loop makes each change to the store, and a single fixed measure counts as such a judgment; **C**: the judgment is held as a conjecture, and evidence from later use can count against a change that was made, so that the system changes the store again—being displaced by a higher-scoring alternative is not enough (attribution is graded, from coarse stack rollback at the minimum to localized blame in an addressable store). A change is an edit to the store's contents, including an edit to what later work loads or selects ([note](./positions/changes-to-the-store-not-reliance.md)). Membership requires all three. For the [kind of learner](./rulings.md#settled-double-loop-ruling), ask separately: can the named system revise the criterion that governs future decisions of this class? A different verdict under the same criterion is not a different criterion. If the case does not specify that capacity, report the kind as undetermined. No case assumes improved capacity unless it specifies the comparison.

| # | System, store and decision | Expected result and discriminator |
|---|---|---|
| 1 | A team keeps a routing rule after weighing saved searches against misrouting. Later failures can lead it to revise the rule. | Inside: S, J, C. Kind undetermined. Revised weights on saved searches versus misrouting for subsequent cases would show criterion revision; correcting this routing rule alone does not. If later work is worse, the team made a bad judgment about the rule; it did not cease to use the process. Human judgment counts, but is not autonomous. |
| 2 | A service appends every interaction to a searchable log. A later tool can edit the log, but no judgment selects which entries to keep. | Outside: nothing judges, so S alone does not give J. Keeping everything is not a fixed measure, because no judgment depends on the entry. Editable storage is not evidence for C. |
| 3 | The team in case 1 still weighs the reasons, but no later round can challenge its decision or act differently in response to an error. | Outside on C, despite S and J at admission. Contrast an irreversible deletion whose lesson can still change the next deletion: C concerns correction of the judgment, not restoration of the file. |
| 4 | A link repairer keeps a patch exactly when its fixed validator passes. Separately, the maintaining team reviews where that test suffices, changes the validator after bad repairs, and weighs ambiguous repairs itself. | Repairer alone: passes S and J, since the validator is a fixed measure. Outside on C: as stipulated, evidence against a kept patch reaches only the team. Team plus repairer, for its repair rules: inside on S, J, C, and double-loop, because the team changes the validator. A deterministic check can settle whether a link resolves; it cannot establish by itself that it resolves to the intended page. |
| 5 | A team judges whether to deploy a better model release, but the training run retains only numeric weight updates under a fixed loss. | Training run and its weights: outside on S. The fixed loss would pass J. The deployment verdict is not the step that made a weight update. To classify the team, specify its own store and loop instead. |
| 6 | A team keeps an unexplained prompt variant after weighing mixed outcomes and revisits the choice on new evidence. By stipulation it never formulates or criticizes a claim about why the prompt works. | Inside on S, J, C; the kind is undetermined because reconsidering a prompt need not revise how later prompts are judged; outside the builder definition on content-directed criticism. Neither an explanation of the prompt nor a measured downstream gain is required for process membership. |
| 7 | An automated builder criticizes what a retained theory says but must select the highest-scoring revision. | Builder inside. Deliberative learner: passes S and J; C depends on what the score takes in. See the joint check below. |
| 8 | As in case 7, but the same loop can reject the score winner for a stated reason about future work and can later correct that judgment. | Both definitions are met. A standing exception already allowed by the criterion can defeat this score winner without changing the criterion. Double-loop only if the system can revise what counts for later theory choices; the stipulation leaves that open. |
| 9 | A search keeps the highest-scoring prompt variant on a fixed benchmark. A new variant replaces the kept one only by scoring higher on that same benchmark. | Outside on C. The earlier choice is overwritten, never found wrong: no later evidence bears on the kept variant. S and J pass. |
| 10 | As in case 9, but kept variants are scored again on tasks that arrive later, and a variant is dropped when its score on them falls below the threshold. | Inside, single-loop. Later evidence counts against a particular kept variant. Nothing in the loop can ask whether the score is the right one. |
| 11 | A problem solver stores a new rule for every subgoal it solves and never removes one. | Outside: no judgment decides what is added, so there is none for later evidence to count against. |

**Joint check for case 7.** Hold the boundary fixed: the running program, not the team that chose its score. It stores a written theory (**localized content**); uses a prediction to choose an action (**consumption**); names the faulty premise and proposes a correction when the prediction fails (**criticism**); and carries a selected revision informed by that criticism into the next round (**iteration**). These are the four [builder checks](../../theory/definitions/theory-builder-checks.md), not four ways of reading a score. For the learning draft, the theory passes S, and selection by the score passes J as a fixed measure. C turns on a detail the case leaves open:

- **7a. The score is a fixed test that takes in nothing new.** The failed prediction produces a candidate, but it is not evidence in the retention step. Yesterday's winner is displaced only when a candidate scores higher, as in case 9. Outside on C.
- **7b. The failed prediction counts in retention**, because it enters the score or removes the criticized theory from the candidates. The kept theory can then lose because of evidence against it, as in case 10. Inside, single-loop. Neon reads case 7 this way: the failed prediction triggers replacement.

So case 7a with case 6 still witnesses overlap without containment, and the excluding condition is now C, not J. Case 7b is a builder that is a single-loop deliberative learner. This is Fable's reading of the tightened condition 3 and has not been read independently. The cases neither redefine the builder nor decide which definition should lead the program.

## Case 12 — keeping a current decision: the OASIS arrival sequencer

[Rao and Georgeff (1995)](../../sources/bdi-agents-from-theory-to-practice.ingest.md) describe a sequencer that chooses a landing schedule using a cost function. A change in wind need not reopen that choice: the sequencer can keep the schedule while the next aircraft can still meet its assigned time. The feasibility check can overturn a particular commitment. The question for the definition is **what changes as a result**.

- **Name the current schedule as the store.** There is an identifiable decision to inspect (S), a test for keeping it (J), and later evidence that can defeat that decision (C). Read without a distinction between finishing the current job and improving capacity for future work, the three conditions could count ordinary replanning as single-loop learning. Rejecting a schedule after the wind changes need not even mean the original choice was mistaken.
- **Name the scheduling procedures as the store.** The plans are legible, but the reported feasibility check decides whether to keep *this schedule*, not whether to retain or correct a procedure for subsequent scheduling. The paper does not show J or C for that store in the sequencer's own loop. Developers adding plans during debugging would change the system boundary.

**Expected placement:** the described episode demonstrates commitment management, not learning a scheduling procedure. This is not a claim that no BDI architecture learns. Evidence that would change the placement: the sequencer retains a revised feasibility rule because of what happened here, applies it to a later scheduling decision, and can correct that retention judgment in light of later outcomes. The distinction is what carries into the later decision, not whether a process restarted or how long a schedule persisted.

## Cases 13–16 — later evidence, graded attribution and the Gödel-machine line

These cases test what later evidence must be able to do, graded attribution, and the double-loop boundary developed in [what later evidence can overturn](./what-later-evidence-can-overturn.md).

| # | System, store and decision | Expected result and discriminator |
|---|---|---|
| 13 | **[Darwin Gödel Machine](../../sources/darwin-godel-machine-open-ended-evolution-self-improving-agents.ingest.md)** (archive of self-modifying agents). Every compiling agent stays in the archive; benchmark score measured once at admission weights parent selection. | Outside on C. Passes S (inspectable agent code) and J (the benchmark score sets how often an agent is selected). No post-admission evidence updates an agent's own score. Its sampling weight falls in two ways, and neither is evidence about the agent: higher-scoring agents enter the archive, and its own count of functioning children grows, even if none of them scores higher. The count allocates exploration: "this parent has been explored enough" is not "its descendants turned out poorly". Case 14 differs on exactly that point, so the pair is the sharper test of C. Correction from Astra, checked against the ingest. |
| 14 | **[Huxley-Gödel Machine](../../sources/huxley-godel-machine-human-level-coding-agent-development.ingest.md)** (archive of agents weighted by descendant performance). An admitted agent's selection weight drops when its descendants perform poorly. | Inside, single-loop. Passes S and J, and passes C because descendant outcomes supply new evidence from after admission that directly lowers how often the ancestor is selected, even if no other branch improves. Shows that evidence for C need not re-run the admission test. Single-loop for archive parent selection: new descendant scores change the weights assigned to parents, not the rule for assigning weights. Edits inside an agent do not revise that archive rule. |
| 15 | **Classical [Gödel machine](../../theory/goedel-machines-are-a-proof-governed-case-of-self-modification.md)** (proof-governed self-modification). Stores readable code `p`, injects live observations via `state2theorem` against an unknown environment prior `µ ∈ M`, and rewrites any sub-policy, heuristic evaluator, or proof searcher upon proving higher expected terminal utility `u`. | Inside, **double-loop capable**. Readable code passes S; proof decides the switch (J); later observations can end a trial (C, §6.1 item 2). Crucially, §6.1 item 4 permits revision of the utility function and target theorem under the old standard. A successor that changes the ranking of future alternatives changes the criterion. No cheap policy gate or observed successful rewrite is required to establish the architectural capacity. |
| 16 | **Schmidhuber's [incremental self-improvement](../../sources/on-learning-how-to-learn-learning-strategies.ingest.md)** (probability distribution over actions). Keeps modifications only while payoff per time since the modification exceeds the prior baseline; otherwise pops the stack and restores the earlier state, with no challenger needed. | Outside on S (opaque probability distribution), inside on C at the coarse attribution minimum. Demonstrates that evidence from after a change can reverse it without a challenger and without condemning the original trial, and shows what Condition 1 adds: an addressable store enables localized blame instead of blind stack rollback. |

## Case 17 — EURISKO changes how it judges heuristic generalizations

**Inside, double-loop for deciding which generalizations of heuristics to keep.**
In [Lenat's H12′ episode](../../sources/eurisko-learns-new-heuristics-and-domain-concepts.ingest.md#quotes)
(*Heuretics*, pp. 89–90), replacing AND with OR made a heuristic fire its
preliminary relevance check more often without finding more occasions when
it was actually useful. Dropping H12′ on that evidence reversed the addition of one readable
heuristic (S, J, C). That alone would be single-loop behavior.

EURISKO also generated restrictions that would have kept H12′ from
surviving. It tried several and retained one against replacing AND with OR
in a heuristic's If slot. The distinction is what happens to the *next*
generalization: its form now counts against it before its own performance
record is available. The restriction was tried probabilistically, not imposed
as an unconditional veto. Lenat attributes this step to EURISKO, not to a
programmer. The episode shows a change in this working criterion, not a
rewrite of EURISKO's overall worth function or proof of improved performance.

## Applying the checks to surveyed systems

These are contrasting cases from the [historical eighteen-system survey](../../articles/which-existing-self-improving-systems-are-theory-builders.md), not a new survey or a count of today's systems. The selection deliberately distinguishes an admission gate, a benchmark used for evaluation, and human approval. Use the survey's accounts and local source records, not the mere presence of an LLM, a benchmark, or a human. These are judgments about the described protocol, not reproduced results.

The account supports discretionary selection but says little about how reviewers resolve competing reasons. | Later feedback can prompt another edit to the same skill. A traced reversal of an earlier edit is not reported. | Consistent with membership at the human-inclusive boundary. Kind undetermined: trace a change to the reviewers’ standard for subsequent edits, not just a rejection under the existing standard. Not an autonomous admission loop. No downstream gain established. |

The expectation that most admissions would be bound to benchmark scores is **not borne out by these selected examples**. Only Recuris is bound to a fixed gate, and after the ruling that makes it single-loop at most, not excluded. This selection cannot estimate the proportion among eighteen. Two questions now do the sorting. For membership, ask whether later evidence can count against a change that was made. For the kind, ask whether the named system can change the criterion by which subsequent changes are judged.

## What the ruling changed

| Case | Before | After | Why |
|---|---|---|---|
| 4, repairer alone | Outside on J | Outside on C | The validator now passes J. Evidence against a kept patch reaches only the team. |
| 5, training run | Outside on S and J | Outside on S | The fixed loss now passes J. |
| 7, automated builder | Outside on J | 7a outside on C; 7b inside, single-loop | Selection by score passes J. The placement depends on whether the score takes in later evidence. |
| Recuris | Outside on J | Undetermined on C | The fixed gate passes J. |

The fixed-measure ruling changed membership as shown above. The later
criterion-revision ruling does not change S, J or C. It changes case 15's
kind and withdraws unsupported double-loop labels in cases 1, 6 and 8.

**Paired checks for the ruling** (hypotheticals, not reported runs):

| Same starting system | Applies the criterion | Revises the criterion |
|---|---|---|
| Gödel machine evaluating self-rewrites | Proves the same target theorems faster. | Proves it should install a utility function that ranks future alternatives differently. Both switches need proof under the old standard; only the second exercises double-loop capacity. Neon's qualification: the old function licenses a successor only when the successor serves it better, for example by being cheaper to evaluate under bounded computation. So this revision is the formal counterpart of the third row: a stand-in is replaced while the objective it serves stays fixed. |
| Commonplace judging instruction edits | Rejects a long edit under its brevity rule. | Finds that short instructions repeatedly omit necessary exceptions and changes the rule for future edits. A language model explaining the failures without authority to change the rule is not enough. |
| Learner with a cheap policy gate and a fixed objective | Drops a routing rule because its queue-time score falls. | Replaces queue time as the test for future routing rules because short queues can still miss deadlines. The objective need not change. |

## What the checks expose

- **C now does the excluding that J used to do.** Cases 4, 7a and 9 pass J and fail C. The line between displacing an earlier edit and finding evidence against it carries the weight. Fable, Astra and Neon each drew it in the same place; no reader outside the workshop has checked it.

- **Which writes count as changes?** The draft says “each change.” The same KSI protocol logs every attempt and selects distilled claims. If the named store is the entire KB and every write must qualify, KSI's placement changes. A claim about the distilled guidance should not silently become one about every write in the KB. Specify whether the quantifier covers candidate learning changes or all writes to the named store.
- **Which comparison supports “learned”?** Suppose a routing rule saves search time on later matched tasks, with no change on an independently reasonable measure of answer accuracy. This is better on one measure and tied on another, not learned under the strict test. A success after a concurrent solver upgrade without a matched baseline does not even establish that limited gain. Neither case invalidates the decision to try the rule.
- **What could change these readings?** For Recuris, show a permitted in-loop change to the admission rule. For KSI, show that a fixed score rather than distillation ultimately selects every claim, or that earlier guidance cannot be reconsidered. For Warp, trace the authority and reasons at acceptance and subsequent correction. Those observations test different conditions; a higher aggregate score would not substitute for any of them.
