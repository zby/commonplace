# Trace the epistemic routes

Establish whether and how the selected target acquires or produces truth-apt content, checks it, grants reliance and lets it affect later behavior.

Treat `runtime` as a provisional account: it orders this job but is not an
inspection limit, and the memory analyst works separately.

## Trace and assess

Follow the epistemic type's five blocks, material-route boundary, content and
update relations, ledger values, checking order and assessment limits. Use
its empty-ledger form for a target that only stores or serves content.
Record `not determinable` where accessible evidence cannot individuate
truth-apt content. Declare new records with `EPI-`; keep supplied `RT-` IDs
for the same referents. Flag a needed supersession or defective supplied fact
beside the affected finding, with evidence.

Check frozen CLI dispatch, hooks, registered tools and exposed operations
against runtime routes. Trace evaluation, cleanup, rejection and withdrawal
through results and consequential consumers, including operations runtime
omitted. Name a target and its domain before judging an evaluator. For a
deterministic text transformation, trace a concrete input through inspected
code; the deduction uses the implementation evidence layer and needs no
target execution.

Cite your declarations, supplied runtime records, boundary sources and peer
declarations in refusal feedback. Assess distributed-parametric state only
from accessible sources and supplied execution evidence. Retain independent
route/property conclusions and bounded uncertainty; no single score or
unqualified system-wide verdict follows.
