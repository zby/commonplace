# xMemory synthesis

## Bounded synthesis

xMemory is a conversation-memory system whose shipped workflow builds retained memory, organizes it into a hierarchy, retrieves selected material and generates answers. This account covers the library **and** its LoCoMo construction, reader and evaluation drivers at Git revision `1a4f9dd8abd7f2da86bfe6afe4293a1ea1c63608`, with applicability cutoff 2026-10-15. SRC-1 is the frozen repository. Evidence consists of inspected implementation, shipped prompts and attributed README claims, not execution traces or causal experiments. External model artifacts, provider internals, the paper and release-hosted prebuilt memories are outside the frozen evidence. The whole-system boundary is functional coverage, not an exhaustive audit of every branch ([boundary](boundary.md#boundary-and-evidence), [Source register](boundary.md#source-register)).

### From conversation to reusable memory

An operator starts construction; software workers format conversation messages under a caller-chosen namespace. A model can decide episode boundaries, and an explicit flush closes remaining material. Episode generation retains both a derived title/content summary and the original message dictionaries. This preserves a route back to source conversation rather than replacing it with a summary. It does not authenticate the conversation's external truth. Smart segmentation also does not enforce a universal configured maximum: its branch bypasses the maximum-size `elif`, and detector failure can leave the buffer growing ([RT-RTE-conversation-admission](runtime.md#rt-rte-conversation-admission), [MEM-OBJ-original-messages](memory.md#mem-obj-original-messages), [MEM-OBJ-episode-content](memory.md#mem-obj-episode-content)).

Episode creation schedules background semantic extraction. In prediction-correction mode, selected prior statements and the new episode title guide a predicted conversation; a second call compares that prediction with originals and proposes valuable information missing or misrepresented in it. Cold start instead extracts from episode content. Alternative per-episode extraction is configurable. The substantive contribution is evidence-directed generation followed by durable reuse: prior memory affects extraction, and new statements can affect future prediction, maintenance and answers ([RT-RTE-semantic-admission](runtime.md#rt-rte-semantic-admission), [EPI-RTE-comparison-extraction](epistemic.md#epi-rte-comparison-extraction)).

The name prediction-correction is stronger than the established repair semantics. Conversion retains statement text and source episode IDs, but not a challenged-statement target, prediction or criticism rationale; confidence is assigned as a constant. A same-type embedding-similarity gate rejects candidates as duplicates, then the default save path appends rather than replacing contradicted statements. Similar corrections can be rejected and dissimilar contradictions can coexist. These are source-level possibilities, not measured frequencies. Operational insertion is not evidence-consuming truth acceptance, and no checked entailment or accepted ampliative claim is established by these routes ([MEM-OBJ-semantic-content](memory.md#mem-obj-semantic-content), [EPI-RTE-duplicate-check](epistemic.md#epi-rte-duplicate-check), [EPI-RTE-semantic-disposition](epistemic.md#epi-rte-semantic-disposition), [EPI-RTE-semantic-retention](epistemic.md#epi-rte-semantic-retention)).

The construction driver then waits, snapshots incremental batches, updates themes and exports a graph. Numerical policies attach, split and merge groups; a model generates theme summaries. Text, membership and vectors have separate effects: summaries supply scoring context, membership filters candidates, and vectors/adjacency influence ranking. The exported graph is a diagnostic artifact, not the adaptive reader's substrate. Fresh maintenance managers can regenerate a small theme from only new-batch member text while retaining older membership IDs. Thus neither a saved summary nor a graph export proves a complete, synchronized abstraction of retained evidence ([RT-RTE-hierarchy-admission](runtime.md#rt-rte-hierarchy-admission), [MEM-OBJ-theme-summary](memory.md#mem-obj-theme-summary), [MEM-OBJ-theme-topology](memory.md#mem-obj-theme-topology), [MEM-OBJ-memory-graph](memory.md#mem-obj-memory-graph)).

### From stored hierarchy to an answer

The representative shipped workflow reloads constructed memory, searches, hydrates selected originals, answers and writes a QA result file. Conversation-level executor tasks process questions sequentially within each conversation; these are software workers, not independently delegated agents. The README explicitly selects `adaptive_hier`; the CLI default is baseline. Baseline and lightweight search are material alternatives, and the facade does not automatically run the driver's entire maintenance sequence ([workflow account](workflow.md#workflow-account), [RT-RTE-baseline-search](runtime.md#rt-rte-baseline-search)).

Adaptive retrieval embeds the question, forms a semantic pool, selects theme/semantic representatives and probes episode candidates. Its quantity called entropy is mean negative log probability of generated tokens. Each candidate is compared against a fixed semantic-only baseline, not against the accumulated selected set. Negative thresholds and a first-candidate fallback further qualify the README's claim that expansion happens only when reader uncertainty falls. Original-message expansion is inferred from summary-level scoring, without testing originals. Themes enter scoring but not the final answer prompt. This implements score-guided context selection, not verified uncertainty reduction or final-answer improvement ([RT-RTE-adaptive-reader](runtime.md#rt-rte-adaptive-reader), [RT-CLM-retrieval-purpose](runtime.md#rt-clm-retrieval-purpose)).

The answer model receives a fresh prompt containing the question, selected semantic/episode text, timestamps and any hydrated originals. It does not inherit scoring generations or obtain model-dereferenceable store pointers. Context management therefore consists of selected-input calls, condensation and explicit reload, rather than an accumulating agent transcript. Selection counts are not input-token guarantees. Original-message limits apply to episode blocks only when positive; zero does not disable originals after expansion is flagged. Baseline Chroma results do not set that expansion flag. Retained prose has model-interpreted contextual force, while code enforces inclusion and exclusion; delivery proves neither compliance nor truth ([RT-BAP-memory-reader](runtime.md#rt-bap-memory-reader), [memory annotations](memory.md#annotations)).

Delivery means writing the result artifact, not passing an answer-acceptance gate. Answer-generation errors can become empty saved responses; an escaping worker exception prevents the normal save call. Separate offline `evals.py` scoring compares responses with dataset references using lexical metrics and skips category 5. References are recorded after answering, not supplied as a retrieval oracle. A separate executable model judge exists but is incompletely characterized by the analyst inventory; the commented judge call in `evals.py` is not evidence that the repository has no judge. Neither the characterized lexical route nor the verifier's additional judge finding establishes automatic memory revision ([workflow account](workflow.md#workflow-account), [EPI-RTE-lexical-evaluation](epistemic.md#epi-rte-lexical-evaluation), [report-verification limits](report-verification.md#limits)).

### What the implemented progression establishes

For conversation-to-later-QA reuse, the strongest supported result is an automatic trace-fed write/retention/later-consumer chain: conversational turns become durable summaries, statements and derivative themes that later generation and selection can consume. Requested QA retrieval is pull; automatic supply of selected retained inputs to update-model calls is a distinct internal push, not unsolicited foreground delivery. The unresolved question is whether these changes improve future capacity, preserve meaning or improve answers. Wired trace learning in the memory-route sense does not answer that question, and no supplied comparison establishes benefit ([RT-RTE-conversation-admission](runtime.md#rt-rte-conversation-admission), [RT-RTE-semantic-admission](runtime.md#rt-rte-semantic-admission), [RT-RTE-hierarchy-admission](runtime.md#rt-rte-hierarchy-admission), [profile verification](profile-verification.md#verification)).

The accepted runtime does not establish a condition-by-condition theory-builder assessment. Its evidence-directed comparison route is a partial contribution, but it does not establish formulated content-directed criticism with blame and a retained criticism result shaping another round. Consequently a complete theory-builder attribution, or an attribution of improved future capacity specifically to criticism of a consumed theory, is not supported. Reflection, autonomous theory building and self-improvement are independently unestablished at this boundary, not disproved by missing runs. Software-owned admission alone does not establish those properties; retained subject-matter updates alone do not establish reflective method revision. No exercised self-improvement attribution can be made without evidence that subsequent operation causally depends on an improvement-directed organizational change ([EPI-RTE-comparison-extraction](epistemic.md#epi-rte-comparison-extraction), [epistemic bounded conclusion](epistemic.md#bounded-conclusion), [RT-RTE-provider-admission](runtime.md#rt-rte-provider-admission)).

For durable construction and later correction, the account is weaker. Task exhaustion is not successful task completion; the driver ignores the wait result before maintenance, and episode-file existence is its success predicate. Repository writes can precede index failure, buffers clear before successful persistence, and no atomic all-layer commit is established. Explicit deletion likewise leaves hierarchy files, independent reader caches and running writers uncoordinated. These conditions prevent interpreting either construction success or backend deletion flags as an end-to-end guarantee ([RT-RTE-hierarchy-admission](runtime.md#rt-rte-hierarchy-admission), [RT-RTE-conversation-admission](runtime.md#rt-rte-conversation-admission), [MEM-RTE-memory-withdrawal](memory.md#mem-rte-memory-withdrawal)).

The assessment would change with traced construction/reload/answer runs linking retained versions to actual consumers; paired extraction outputs checked against originals; interventions comparing the same reader with and without adaptive selection or prediction-correction; and fault/replay/deletion tests covering all stores and caches. Benefit attribution would require independently varying the mechanism claimed to help. Enforced input budgets, full-member summary refresh, coordinated withdrawal and explicit correction targets would change the relevant architectural limits, but their effectiveness would still require evidence. These are discriminating evidence or system changes, not conclusions supplied by the present source account.
