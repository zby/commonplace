# Echel synthesis

## Bounded synthesis

### Capture product meaning, then choose work

Echel is a product-memory and context-engineering system, not the enclosing agent runtime. This account covers the shipped repository at `aee36de4d2d1c404fb36e9ad68cc0a920784ee61`, with an analysis cutoff of 2026-10-15. SRC-1 supplies inspected implementation, declared methodology and an attributed synthetic benchmark result. No target commands, tests or examples were executed. Hermes internals, provider behavior and deployed identity controls are outside the evidence. The [boundary and Source register](boundary.md#source-register) identify the frozen source; the account below uses accepted records, without additional source inspection.

The architecture has two consequentially separate storage and workflow families. Current CLI initialization creates a canonical schema-versioned project and proposed raw-idea claim under `.echel/records`, with colon-namespaced identities. The work/context/run commands instead use legacy `FileStore` project, knowledge and work shapes with uppercase IDs. Even the shared project filename does not make the envelopes compatible. Thus the shipped CLI does not establish a continuous fresh-init-to-agent journey. The supported execution sequence starts with existing legacy state, which the in-repository initialization API can create. See [RT-RTE-idea-init](runtime.md#rt-rte-idea-init), [RT-RTE-file-workflow](runtime.md#rt-rte-file-workflow) and the [workflow account](workflow.md#workflow-account).

Within that starting condition, the caller decomposes work and supplies objectives, acceptance criteria, verification commands and explicit knowledge relationships. Echel checks referenced records exist and persists the work packet; it does not thereby approve their truth. Its legacy stage gate checks accepted/validated knowledge kinds, but permits a force bypass, and knowledge writes can directly use caller-selected accepted status. These are caller-driven commands, not an autonomous scheduler or a model-generated implementation plan ([RT-RTE-file-workflow](runtime.md#rt-rte-file-workflow)).

### Select context and delegate execution

On a context or run request, deterministic code reloads the work and selects knowledge by `relates_to` membership, plus open findings affecting those related IDs. Text supplies the objective, acceptance and verification directions, knowledge statements with status/confidence, and finding statements. It omits source references and much metadata. Status is displayed, not an accepted-only filter: proposed, rejected or stale related knowledge can reach the prompt. Complete selected dictionaries remain available in JSON context output; the narrower rendering is what `run` sends. This supports relationship-bounded context construction, not the public claim of the smallest trustworthy context ([RT-OBJ-compiled-context](runtime.md#rt-obj-compiled-context), [RT-RTE-compile-run](runtime.md#rt-rte-compile-run), [EPI-CLM-trustworthy-context](epistemic.md#epi-clm-trustworthy-context)).

This is requested read-back, not unsolicited memory injection. Echel implements no token-budget trimming, recursive dependency expansion or context compaction in this compiler. Excluded records remain on disk and may be reachable through tools. Each invocation recompiles current files; it does not recall an already delivered prompt. Hermes window management and internal delegation remain uninspected ([RT-RTE-compile-run](runtime.md#rt-rte-compile-run), including its memory annotation).

By default, `run` persists a preview command rather than launching an agent. Explicit execution starts one synchronous Hermes subprocess at the workspace directory, with rendered context, an optional model label and requested terminal/file toolsets. Hermes owns subsequent model/tool decisions. Requested toolsets and a working directory are not an Echel sandbox or per-tool approval gate. The implementation skill asks agents to verify and return knowledge proposals separately, but automatic loading and compliance are unestablished. Echel does not pin an exact model artifact or expose model-parameter updates ([RT-RTE-compile-run](runtime.md#rt-rte-compile-run), [RT-BAP-context-prompt](runtime.md#rt-bap-context-prompt), [RT-BAP-implementation-skill](runtime.md#rt-bap-implementation-skill), [RT-CMP-runtime-model](runtime.md#rt-cmp-runtime-model)).

### Return a process result, then check separately

A returned Hermes exit code becomes completed/failed run status. Run JSON retains the command, context digest and last 4,000 stdout characters, not a full session or stderr. Delivery means this record is persisted and emitted; it does not close the work item, accept implementation quality or promote knowledge. Missing Hermes can fail before persistence; a returned nonzero exit can persist a failed Run while the CLI returns zero. Callers must distinguish CLI return from task outcome ([RT-RTE-compile-run](runtime.md#rt-rte-compile-run), [MEM-OBJ-run](memory.md#mem-obj-run), [workflow account](workflow.md#workflow-account)).

The caller separately invokes verification. Echel executes stored command strings as argv at the workspace, independently of Hermes toolsets. Exit codes produce passed/failed Evidence records; only a checksum of combined output survives, not the diagnostic bytes. The semantic strength of a check belongs to the supplied executable, not to the runner. Failure neither rolls back effects nor schedules another agent attempt; launch exceptions can interrupt after earlier commands have acted. Recovery and acceptance remain caller responsibilities ([RT-RTE-verify-work](runtime.md#rt-rte-verify-work), [MEM-OBJ-evidence](memory.md#mem-obj-evidence)).

### Review and revise retained knowledge through a different plane

Canonical services provide a stronger local review protocol: a proposed claim, decision or learning can receive accepted/rejected status with a caller-supplied human-labelled principal, capability and rationale. This is structural authorization under trusted principal provisioning, not authenticated human identity. It also does not require an evidence-consuming semantic criterion, intended use and scope. Legacy writes, direct schema-valid canonical writes, imports and migration edits do not universally traverse this service. Consequently an accepted label neither proves truth nor establishes that only approved verified discoveries reach execution ([RT-RTE-knowledge-decide](runtime.md#rt-rte-knowledge-decide), [EPI-RTE-portable-import](epistemic.md#epi-rte-portable-import), [EPI-RTE-schema-migration](epistemic.md#epi-rte-schema-migration), [EPI-CLM-approved-discoveries](epistemic.md#epi-clm-approved-discoveries)).

Retained canonical state has concrete later effects. Clarification uses active claim kinds, including proposed claims, to suppress fixed questions. Maturity requires accepted claim kinds and checks active linked finding severity. Human-labelled profile changes select among shipped requirement policies. Findings can block maturity; reviewed backward revision can mark accepted protected knowledge stale along explicit `informs`/`supports` edges, retaining reasons and removing accepted eligibility. It does not infer falsity, generate replacements or revoke legacy prompts. Duplicate accepted kinds can leave some findings outside maturity assessment, and advance apply does not reassess all supporting claim/finding revisions ([MEM-RTE-clarification-read](memory.md#mem-rte-clarification-read), [MEM-RTE-policy-revision](memory.md#mem-rte-policy-revision), [MEM-RTE-finding-maintenance](memory.md#mem-rte-finding-maintenance), [MEM-RTE-staleness-propagation](memory.md#mem-rte-staleness-propagation), [EPI-RTE-maturity-advance](epistemic.md#epi-rte-maturity-advance)).

Canonical query provides a separate requested consumer route: a disposable SQLite/FTS index selects lexical hits or bounded relationship paths, then reloads canonical records and checks freshness. Reasons remain readable, but freshness and provenance are not semantic endorsement, and this service is not wired into the legacy Hermes compiler. Journals, staged bytes and migration backups support recovery; cleanup, cache discard and guarded byte restoration are distinct from knowledge withdrawal ([MEM-RTE-canonical-query](memory.md#mem-rte-canonical-query), [MEM-OBJ-disposable-index](memory.md#mem-obj-disposable-index), [MEM-OBJ-recovery-state](memory.md#mem-obj-recovery-state), [MEM-RTE-storage-maintenance](memory.md#mem-rte-storage-maintenance)).

### What the progression establishes

The strongest supported contribution is implemented retained-state control: work relationships bound supplied context, and canonical criticism/status changes can alter later question selection and maturity eligibility while preserving reasons. Those are real consumer paths, not merely stored labels. Whether criticism of a consumed theory improved future-action capacity remains unestablished: no exercised criticism-to-revision-to-later-capacity comparison is supplied. Raw run/evidence retention does not establish an automatic durable behavior-shaping derivation and later consumer; a canonical learning record's name and evidence IDs do not close that chain ([MEM-BAP-canonical-gates](memory.md#mem-bap-canonical-gates), [MEM-OBJ-run](memory.md#mem-obj-run), [MEM-OBJ-evidence](memory.md#mem-obj-evidence), [EPI-OBJ-learning](epistemic.md#epi-obj-learning)).

Theory-building, reflection, autonomy and self-improvement are separate questions. The accepted account establishes no formulated theory route meeting conditions 1–4; it does not turn stored assertions into theories, delivery into content-dependent consumption, finding labels into content-directed criticism, or retained results into a demonstrated next round. Reflection and autonomous content criticism are likewise not established. Caller-controlled execution and review should not be described as autonomous orchestration. At this boundary, self-improvement is not demonstrated: profile selection changes policy and contributor changes could alter machinery, but evidence-responsive determination, admission into live organization and subsequent operation causally depending on an improvement-directed update are not traced. These limits do not establish universal absence, especially inside the excluded model runtime ([epistemic bounded conclusion](epistemic.md#bounded-conclusion), [EPI-RTE-profile-selection](epistemic.md#epi-rte-profile-selection), [RT-RTE-source-admission](runtime.md#rt-rte-source-admission)).

For a scenario with prepared legacy state and caller-owned sequencing, source supports context construction, external execution and separate evidence capture. For a fresh idea progressing through approved discoveries into future agent work, the canonical/legacy break and missing promotion bridge prevent the same conclusion. No scenario success rate or context benefit is established. The kernel evaluator measures synthetic SQL, bypassing the full canonical query chain; its attributed local result cannot establish end-to-end latency or agent improvement. Product-evaluation doctrine explicitly reserves success claims for later evidence ([MEM-CLM-kernel-scope](memory.md#mem-clm-kernel-scope), [EPI-RTE-kernel-gate](epistemic.md#epi-rte-kernel-gate), [EPI-CLM-evaluation-contract](epistemic.md#epi-clm-evaluation-contract)).

A compatible init-to-work/run path would change the composition finding. An inspected bridge from verification and reviewed discoveries into subsequently consumed project memory would change the loop account. Traced evidence-consuming decisions and later operations would establish exercised reliance; a comparison varying the relevant context or revision mechanism independently would be needed for component-level benefit attribution. Authenticated principals and coverage of alternate writes would be needed for broader approval guarantees. These are conditions for revising this assessment, not claims that the changes already exist.
