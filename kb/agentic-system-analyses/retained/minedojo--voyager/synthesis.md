# Voyager synthesis

## Bounded synthesis

### From exploration task to executable action

Voyager's strongest supported contribution is an implemented path from Minecraft task experience to retained executable capabilities with later consumers. Its Python driver selects tasks, requests JavaScript, executes it, obtains a task judgment and retains successful programs for future prompting and execution. That is improvement-directed adaptation beyond a single response, without a client-side model-weight update. Whether the retained changes actually improve future capacity remains unestablished. See [RT-RTE-learning-loop](runtime.md#rt-rte-learning-loop), [RT-RTE-skill-admission](runtime.md#rt-rte-skill-admission) and [RT-CLM-lifelong-learning](runtime.md#rt-clm-lifelong-learning).

This account covers the shipped enclosing runtime at commit **55e45a880755d0c8c66ca7fb5fe7962ac8974f89**, with applicability cutoff **2026-10-14**. The frozen source, SRC-1, includes learning and inference drivers, prompts, retained libraries and the Minecraft execution bridge. Evidence consists of inspected implementation, declared design and attributed reports in that repository. No supplied execution trace, target execution or causal experiment establishes activation or benefit. External game, model-service and dependency implementations are not frozen. The [boundary and Source register](boundary.md#source-register) specify this distinction; the independent checks accepted the [reports](report-verification.md#verification) and [memory classifications](profile-verification.md#verification) with local limits.

The representative workflow is one task episode inside `learn()`, beginning with the automatic first task, “Mine 1 wood log.” This is a source-supported sequence, not an observed successful episode. The caller controls connection, models, checkpoints, modes and limits. Python owns progression among curriculum, action, critic and skill-description calls; these are sequential specialized calls, not independently scheduled worker agents. Task selection combines hardcoded initial and inventory-pressure branches with model or human dispatch. Even manual curriculum mode leaves inventory overrides operative. See [RT-RTE-task-selection](runtime.md#rt-rte-task-selection) and the [workflow account](workflow.md#workflow-account).

The action model receives instructions, primitive descriptions and retrieved skill code, alongside task/context and selected observations. Its response is parsed into function declarations and an invocation of an async main function taking `bot`. This is a local output-shape check, not enforcement of the prompt's primitive-only or no-infinite-loop policies. Python passes the result to a Node/Mineflayer server, which evaluates it with the loaded programs in process scope and can change the game world. Direct environment calls bypass the action parser and task-selection machinery. No sandbox or equivalent capability reduction is applied around the inspected evaluation; external deployment containment remains uninspected. See [RT-OBJ-program-code](runtime.md#rt-obj-program-code), [RT-RTE-environment-step](runtime.md#rt-rte-environment-step) and [RT-BAP-action-guidance](runtime.md#rt-bap-action-guidance).

### From final-state judgment to retained capability

After execution, Python records events and updates chest state, then requests a critic judgment. The automatic critic checks selected final-state observations against the named task and context. Its success boolean can end the rollout and, in learning, permit skill admission. Its critique guides another action request. Execution errors veto automatic success before a model judgment, but manual critic mode can approve independently of that veto. There is no independent expected-answer artifact or program-correctness oracle. See [RT-RTE-task-judgment](runtime.md#rt-rte-task-judgment).

This is evidence-consuming **task acceptance**, not merely retention. Its license is nevertheless narrow: meeting task requirements under the critic's observation heuristics does not show that the program caused the state, will replay safely or transfers. Inventory can pre-exist; server assistance can give items or teleport before final observation. Observation transformations also matter: the exposed inventory can be an open container's contents, and curriculum rendering can infer an underground biome from missing surface block types. Different consumers need not receive equivalent world-state reports. See [EPI-RTE-observation-context](epistemic.md#epi-rte-observation-context) and [EPI-CLM-self-verification](epistemic.md#epi-clm-self-verification).

For successful nondeposit tasks in learning, the manager retains the last program, generates a separate description, embeds that description and writes active code/description state plus archival text files. The task judgment precedes description generation and does not validate the description's fidelity. Direct manager calls can bypass the learning driver's success gate. Same-name admission replaces active content while preserving versioned files; it is not a regression comparison or transactional rollback. Later task failure does not automatically withdraw that skill. Critic rationale and full task provenance are not structured fields of the retained entry. See [RT-RTE-skill-admission](runtime.md#rt-rte-skill-admission), [MEM-OBJ-skills-code](memory.md#mem-obj-skills-code), [MEM-OBJ-skill-description](memory.md#mem-obj-skill-description) and [EPI-RTE-skill-description](epistemic.md#epi-rte-skill-description).

Two later-consumer paths distinguish the design. Requested semantic retrieval ranks descriptions and returns actual code to the action model, normally at most five entries, without a local score threshold or token budget. Independently, **every active skill definition**, plus primitives, enters each execution's programs string. Prompt top-k therefore limits model visibility, not executable availability. Invocation still depends on the generated program and JavaScript semantics; supplying definitions does not show that they ran. See [MEM-RTE-skill-retrieval](memory.md#mem-rte-skill-retrieval) and [RT-BAP-skill-execution](runtime.md#rt-bap-skill-execution).

### What crosses attempts, tasks and restarts

Voyager replaces its action context after executed attempts rather than accumulating a conversation or asking a model to compact it. Current observations, last code and latest critique enter the new two-message frame; older diagnostic turns do not automatically reload. Task context plus regex-extracted unmet requirements refresh retrieval. Separate critic, QA and description calls receive selected inputs rather than the whole action history. Curriculum adds progress-dependent filtering and a five-pair QA display cap. These boundaries reduce what each invocation sees, but establish no general action-context token bound. See [MEM-RTE-context-refresh](memory.md#mem-rte-context-refresh).

Other retained state has different authority and maintenance rules. QA answers are generated on misses and reused through exact task-question or semantic question lookup, without a truth-acceptance gate. Curriculum display filters unsuitable-answer strings, but task-context lookup does not apply those filters. Chest maps merge observations and remove explicitly invalid positions; omission from a new scan does not remove old information. Accepted task strings update completed/failed histories, whose cleaned membership and count shape later curriculum disclosure and inference sequencing. Raw event files reload into accounting, including a learning-limit counter, not an action transcript. An encountered-block set survives observations within one bot lifetime but has no established disk reload. See [MEM-RTE-qa-cache](memory.md#mem-rte-qa-cache), [MEM-RTE-chest-update](memory.md#mem-rte-chest-update), [MEM-RTE-progress-update](memory.md#mem-rte-progress-update), [MEM-RTE-event-replay](memory.md#mem-rte-event-replay) and [MEM-OBJ-block-records](memory.md#mem-obj-block-records).

Delivery also has separate horizons. Task acceptance is not completed durable publication, and publication is not successful reuse. Learning returns accumulated task histories and active skills on its iteration-limit exit. Its action retry bound applies to completed steps, not hanging requests or arbitrary JavaScript. Rollout exceptions have a learning-owned reset path, but proposal and admission lie outside that handler. Inference can load a caller-selected library and execute supplied or model-decomposed subgoals; it does not admit new skills and lacks learning's enclosing recovery/global limit. Repeated failure or duplicate subgoals can stall its completed-count index. See [workflow delivery](workflow.md#what-counts-as-delivery) and [RT-RTE-task-inference](runtime.md#rt-rte-task-inference).

### Assessment at this boundary

For open-ended exploration, the supported architecture links task evidence to persistent capability selection and later executable authority. Skill, chest and outcome-history writes each provide automatic trace-fed durable behavior-shaping paths. This supports implemented adaptation, not measured learning gain. For imported-library task execution, loading and consumption are supported, but historical provenance, index consistency and transfer performance are not. The README's comparative and forgetting-mitigation claims remain attributed reports, not findings from inspected benchmarks. See [RT-RTE-skill-admission](runtime.md#rt-rte-skill-admission), [MEM-RTE-chest-update](memory.md#mem-rte-chest-update), [MEM-RTE-progress-update](memory.md#mem-rte-progress-update) and [EPI-CLM-skill-transfer](epistemic.md#epi-clm-skill-transfer).

These properties must remain separate:

- **Learning:** retained capability changes and later consumers are wired; improved capacity for future action is unestablished. A discriminating later-task comparison would change this assessment.
- **Theory-builder conditions 1–4:** the accepted runtime does not classify these programs as formulated explanatory theories or establish each condition. Executable encoding alone establishes neither theory content nor its absence. Critic delivery does not establish content-directed theory criticism, and retaining its resulting program does not by itself establish theory iteration.
- **Improvement through criticism of a consumed theory:** no supported critique/revision/capacity comparison establishes this. The implemented request to revise action code is a narrower finding.
- **Reflection and autonomy:** automatic task/action/judgment progression is wired in configured auto modes; manual modes are genuine alternatives. This does not establish reflective self-representation or an autonomous theory builder. The reports leave those properties unestablished rather than inferring them from the word “critic.”
- **Self-improvement:** over future Minecraft tasks and resumed use, success-conditioned skill retention supports a **dispositional improvement-directed self-change pathway**. Task evidence conditions an update to retained code, and that code has live prompt and execution channels. Subsequent operation causally depending on the admitted change is unestablished; exercised self-improvement and successful improvement therefore remain unestablished independently.

These distinctions follow [RT-RTE-skill-admission](runtime.md#rt-rte-skill-admission) and the [epistemic bounded conclusion](epistemic.md#bounded-conclusion), not a system-wide epistemic grade. Inspectable linked production/reuse traces would establish activation; comparisons varying retained changes would address benefit and attribution. Checks of program replay, description fidelity and failure-triggered withdrawal would alter the current task-acceptance versus reusable-capability assessment. A theory account would additionally need inspectable theory content, consumption, content-directed criticism and retained consequences for another round.
