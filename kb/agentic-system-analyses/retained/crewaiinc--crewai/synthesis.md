# CrewAI synthesis

## Bounded synthesis

### From a request to agent work

CrewAI is an enclosing runtime: it schedules tasks and owns model/tool execution, while exposing standalone agents and programmable Flows. This account covers the shipped open-source framework at commit `3da2d4e9932b5f2fa9aa73ea9245e0f8b5c154f8`, with an applicability cutoff of 2026-10-15. Its basis is SRC-1 implementation and attributed doctrine/design in the [Source register](boundary.md#source-register). No execution trace, successful test result or causal experiment was supplied. Hosted CrewAI implementations, downstream application policy and external model, embedding and storage internals are not frozen evidence. Whole-system target scope does not imply exhaustive inspection of every adapter or retained-state consumer. No additional source reads were performed for this synthesis.

CLI and generated-project drivers lead to Crew or Flow execution. In ordinary Crew kickoff, code advances the configured task list; an agent model chooses intermediate actions. Hierarchical mode assigns scheduled tasks to a manager, rather than letting that model replace the scheduler. Task preparation supplies selected prior outputs, memory, knowledge, tools and training instructions. Standalone Agent kickoff owns a separate preparation/finalization route. Flow instead selects Python methods from start/listener/router conditions and invokes their bodies directly; these bodies need not use an agent loop. See [RT-RTE-crew-kickoff](runtime.md#rt-rte-crew-kickoff), [RT-RTE-agent-kickoff](runtime.md#rt-rte-agent-kickoff) and [RT-RTE-flow-execution](runtime.md#rt-rte-flow-execution).

The model/tool loop uses native tool calling when supported and otherwise ReAct parsing. Registered before-tool hooks can veto calls on the inspected native and synchronous/asynchronous ReAct paths; post-tool hooks can change observations. This is conditional protocol enforcement, not an operating-system sandbox or universal mediation. Direct Python calls, callbacks and Flow bodies can bypass those helpers. Deployed credentials and service permissions were not supplied. See [RT-RTE-tool-dispatch](runtime.md#rt-rte-tool-dispatch) and [RT-CLM-tool-veto](runtime.md#rt-clm-tool-veto).

### Delegation, checking and delivery

The representative [workflow](workflow.md#workflow-account) follows connected conditional branches of a hierarchical Crew with ordered synchronous tasks: the manager delegates to a configured coworker, receives its answer, and submits a candidate to a configured Task guardrail. It is a code-supported workflow, not an observed successful run. Recipient preparation limits the available coworkers. Delegation passes a newly constructed task and selected context to the chosen agent, not the manager's entire transcript. The coworker retains its own instructions, retrieval and tools. The helper calls agent execution directly, so constructing the delegated Task does not independently run the outer Task guardrail/callback/file lifecycle. See [RT-RTE-agent-delegation](runtime.md#rt-rte-agent-delegation).

The scheduled Task's guardrail can accept, replace or reject the manager's candidate. Rejection causes bounded re-execution with validation-error context, potentially repeating delegation and tool effects. Exhaustion raises instead of advancing. Crucially, Crew executor memory submission precedes this gate; rejection does not retract that memory or earlier tool effects. Standalone finalization checks before its kickoff-output memory save. Ordered checks and later payload-changing hooks also prevent treating an accepted candidate as an immutable final artifact. These are configured progression controls whose factual license depends on the supplied evaluator, not built-in truth certification: [RT-RTE-output-guardrail](runtime.md#rt-rte-output-guardrail), [RT-CLM-output-validation](runtime.md#rt-clm-output-validation).

After task progression, Crew selects the last truthy raw task output as its top-level result and includes all task outputs and token usage. Aggregate hooks can still replace the payload. The selected nonstreaming workflow drains background writes and returns an API result; optional files are separate local artifacts. Neither return nor write draining establishes correct output, successful persistence or external receipt. See the [workflow delivery account](workflow.md#progression-and-delivery).

### What later work receives

With memory configured, task completion can feed task description, role, expected result and output into statement extraction. Explicit API/tool writes bypass extraction but still enter encoding. Encoding embeds content, rejects near duplicates, resolves organization and may ask a model to keep, update, delete or insert against similar records. Fully supplied fields with no sufficiently similar records allow insertion without model analysis; extraction failure can retain the whole input blob, and consolidation failure defaults to insertion. Software admits these transformations without a separate human approval of each derived statement. See [MEM-RTE-memory-encoding](memory.md#mem-rte-memory-encoding), [EPI-RTE-consolidation-check](epistemic.md#epi-rte-consolidation-check) and [EPI-RTE-plan-application](epistemic.md#epi-rte-plan-application).

Retained text, symbolic selection/provenance fields and dense embedding state have different consumers. Built-in memory uses vector storage with filesystem backing; arbitrary supplied backends remain unresolved. Consolidation compares at most the first 200 characters of each old record's content. Its update reconstruction can reset source/private fields to defaults, while plan reasons need not persist or reach later readers. This is an implementation-supported counterexample to invariant privacy/provenance, not an observed leak. See [MEM-OBJ-memory-content](memory.md#mem-obj-memory-content), [MEM-OBJ-memory-metadata](memory.md#mem-obj-memory-metadata), [MEM-OBJ-memory-vector](memory.md#mem-obj-memory-vector) and [MEM-CLM-retention-limits](memory.md#mem-clm-retention-limits).

Before later work, runtime task preparation requests recall from the task description with limit five; modern standalone preparation requests twenty. A foreground model can instead request Search memory. Recall waits for pending saves, then selects and ranks records through embeddings, filters and semantic/recency/importance scoring. Deep recall conditionally adds model query analysis and budgeted exploration, but its final result remains ranked records, not an accepted synthesized answer. Search memory can request twenty per query without a global twenty-result cap. These are count limits, not hard token budgets. See [MEM-RTE-memory-recall](memory.md#mem-rte-memory-recall).

Automatic preparation supplies selected memories to the later model without its own request; the recall service itself fulfills a runtime request. Model-requested Search memory is a separate request path. Formatted matches expose content, score, categories and non-null metadata, but omit explicit evidence gaps, source/private fields and match reasons. Delivery therefore does not establish downstream awareness of caveats, semantic reliance or compliance. Scores measure relevance, not truth probability. Scope/source controls do not establish authenticated tenancy. See [EPI-RTE-memory-selection](epistemic.md#epi-rte-memory-selection) and [MEM-BAP-memory-context](memory.md#mem-bap-memory-context).

Knowledge ingestion separately admits configured source chunks and later supplies selected snippets to task prompts. It acquires content with unresolved source warrant; storage and retrieval do not make it a produced finding. Static skills instead disclose configured instructions by catalog label, with no established automatic skill-writing route. Overflow summarization replaces non-system history with model text while preserving system messages and files for the next invocation; it establishes continuity wiring, not losslessness or automatic verbatim reload. See [MEM-RTE-knowledge-context](memory.md#mem-rte-knowledge-context), [RT-RTE-skill-disclosure](runtime.md#rt-rte-skill-disclosure) and [RT-RTE-context-summary](runtime.md#rt-rte-context-summary).

Recovery has other consumers. Replay reconstructs preceding task outputs for resumed task context. Flow UUID reload hydrates the latest saved state but does not alone skip completed methods. Runtime checkpoints reconstruct entities/event state and can carry completed-execution information. Default Flow/replay storage is SQLite; default runtime checkpoints are JSON files, with a SQLite alternative. These are reconstruction routes, not semantic claim acceptance or exactly-once external effects. Explicit update/forget/reset changes future availability without retracting prior prompts or checkpoints; inspected read-only checks differ across methods. See [MEM-RTE-output-replay](memory.md#mem-rte-output-replay), [MEM-OBJ-flow-state](memory.md#mem-obj-flow-state), [MEM-RTE-checkpoint-restore](memory.md#mem-rte-checkpoint-restore) and [MEM-RTE-memory-maintenance](memory.md#mem-rte-memory-maintenance).

### Feedback and the limits of improvement claims

The strongest supported contribution is retained-text adaptation with implemented later consumers. Crew training collects initial outputs, human feedback and revised outputs, then a model evaluator produces persisted role-keyed suggestions. Later task prompts append them as imperative instructions. Flow's learn-enabled feedback path distills output/feedback into retained lessons and can use recalled content to rewrite eligible later outputs before human review. Human feedback supplies evaluative input, not approval of every derived suggestion or lesson. Flow review can receive public non-lesson records too: learn_source controls private-record visibility, not exclusive lesson lineage. See [RT-RTE-crew-training](runtime.md#rt-rte-crew-training), [RT-BAP-training-instructions](runtime.md#rt-bap-training-instructions), [MEM-RTE-feedback-lessons](memory.md#mem-rte-feedback-lessons) and [MEM-BAP-feedback-review](memory.md#mem-bap-feedback-review).

Together with task extraction and continuation summaries, these support four wired automatic trace-to-retained-artifact-to-later-consumer chains. That write-route finding does not require provider-weight updates or demonstrated improvement. The unresolved question is whether the retained changes improve future capacity, not whether later-consumer routes exist. The [profile verification](profile-verification.md#verification) accepts these local positives while retaining partial coverage on every comparison axis. No provider parameter update follows from the inspected training path; provider internals remain uninspected in [RT-CMP-agent-llm](runtime.md#rt-cmp-agent-llm).

Independent property conclusions remain bounded. The accepted runtime does not establish theory-builder condition 1 (a formulated theory), condition 2 (decisions depending on that theory's content), condition 3 (content-directed criticism with blame and changed reliance), or condition 4 (the criticism's result shaping another round). Feedback records and suggestions are not enough to infer those properties, nor does missing rationale establish their absence. Criticism of a consumed theory improving future capacity is separately unestablished. Reflection and autonomy are also unestablished by these records, rather than negated by missing runs. See [RT-RTE-crew-training](runtime.md#rt-rte-crew-training) and the [report verification](report-verification.md#verification).

For self-improvement, the training and feedback routes wire evidence-responsive retained changes to later behavioral channels, supporting a marked dispositional pathway, not exercised self-improvement. Over later task/method invocations, subsequent operation causally depending on the change remains unobserved; independently measured successful improvement is also unsupplied. The objective of better later task/output quality would require criteria independent of the generated suggestions and an appropriate comparison. This conclusion is separate from the positive trace-fed write finding and from theory building: [RT-RTE-crew-training](runtime.md#rt-rte-crew-training), [MEM-RTE-feedback-lessons](memory.md#mem-rte-feedback-lessons).

### Scenario-relative assessment and what would change it

For a configured multi-task workflow, the evidence supports selected handoffs, bounded retries and retained-context reuse. For a requirement that only approved results become memory, that all effects pass one policy gate, or that recovery cannot repeat effects, inspected ordering and alternate routes defeat the stronger interpretation. For a requirement of evidence-warranted knowledge production, extraction, relevance ranking and model approval do not suffice. Generated semantic relations remain indeterminate without instances; unknown entailment is not proof of conjecture. This is a comparison against named requirements, not a product ranking or system-wide epistemic grade. See [RT-CLM-tool-veto](runtime.md#rt-clm-tool-veto), [MEM-CLM-retention-limits](memory.md#mem-clm-retention-limits) and the [epistemic bounded conclusion](epistemic.md#bounded-conclusion).

Inspectable executions linking source traces, derived artifacts and later consumer behavior would establish activation within their conditions. Independent task criteria and controlled comparisons could establish benefit and attribute it no more finely than the varied treatment. Persisted acceptance evidence and delivered provenance/caveats could support stronger warrant claims. A changed save/gate order or implemented withdrawal/compensation could alter the rejected-output retention assessment. Current test scoring reports model opinions; the CLI evaluation gate maps an opaque hosted done/passed verdict to process status, without supplied remote judgment or deployed CI evidence. Neither currently closes these gaps: [EPI-RTE-test-scoring](epistemic.md#epi-rte-test-scoring), [EPI-RTE-eval-gate](epistemic.md#epi-rte-eval-gate).
