# nao synthesis

## Bounded synthesis

### From project context to an analytics conversation

nao is an enclosing analytics runtime, not only a memory extractor or a tool exposed to another agent. Its CLI builds project context; its backend constructs model instructions, runs a model-and-tool loop, streams answers and retains conversations. The assessed whole-system boundary includes context maintenance, alternate callers and evaluators. Evidence is inspected implementation and attributed design in SRC-1, `https://github.com/getnao/nao`, at commit `0085625a8fd22e4f404b6a3971d153f6b6699479`, with an analysis cutoff of 2026-10-14. No target code, tests, models or services were executed. Whole-system scope does not mean exhaustive inspection. External providers, warehouse contents, repository governance and deployed infrastructure are not frozen. See [the boundary and Source register](boundary.md#boundary-and-evidence).

An ordinary web request passes authentication, role, budget and chat-ownership checks before nao reloads history and constructs an agent. Code owns admission, grants, context preparation and persistence. The selected remote model chooses exposed tools and composes the answer; nao dispatches calls to database, storage, MCP or execution adapters. These responsibilities are separated in [RT-RTE-web-chat](runtime.md#rt-rte-web-chat) and [RT-OBJ-tool-context](runtime.md#rt-obj-tool-context). There is no reference-answer oracle in ordinary chat.

Default instructions combine project rules, active user memories, context inventories and available skills. A complete prompt override can replace that composition, while user-group restrictions are appended separately. Natural-language instructions direct the model; they are not executable access controls. The ordinary write tool permits storage/story outputs and rejects project-context edits, but separate synchronization and deployment routes can replace context. Thus read-only describes a tool boundary, not immutable project guidance. See [RT-OBJ-system-prompt](runtime.md#rt-obj-system-prompt), [RT-BAP-project-guidance](runtime.md#rt-bap-project-guidance) and [RT-CLM-context-readonly](runtime.md#rt-clm-context-readonly).

SQL tools supply reusable evidence rather than verified interpretations. Full rows enter a cache while ordinary model rendering defaults to 40 visible rows; explicit paging can recover more. Reruns replace results under a query ID and suppress stale bodies. These mechanisms preserve selected values and lineage, not source-data truth or business-metric fidelity. Local SQL can derive results conditionally on its inputs and semantics; no supplied query instance establishes a warranted new external-world claim. Generated answers remain semantically unclassified between restatement, derivation and conjecture without concrete candidate evidence. See [EPI-RTE-query-results](epistemic.md#epi-rte-query-results) and [the epistemic assessment](epistemic.md#bounded-conclusion).

The effect envelope depends on configuration and caller. SQL validation rejects disallowed writes on the inspected executeQuery path, not every conceivable mutation. Monty Python and network-enabled Boxlite shell/Python execution have different adapter controls; sandbox availability, experimental flags, secrets and deployment determine the actual grant. No universal human confirmation barrier or isolation invariant follows. [The runtime's forcing-route account](runtime.md#forcing-routes-and-limits-of-guarantees) retains those conditions.

Delegation also has distinct contracts. A beta-gated explore task receives fresh instructions plus an explicit task and returns only its report to the parent model, while sharing ToolContext. It isolates conversation visibility, not the permission principal. MCP ask_nao instead encloses a durable background chat and can return a polling handle after its synchronous response budget. Direct MCP tools are another, host-driven route. Automations run under their owner and can add outbound integration tools; checking that required tools were called establishes completion bookkeeping, not answer truth or exactly-once external delivery. See [RT-RTE-explore-task](runtime.md#rt-rte-explore-task), [RT-RTE-mcp-chat](runtime.md#rt-rte-mcp-chat) and [RT-RTE-automation-run](runtime.md#rt-rte-automation-run).

### What survives a conversation

The strongest supported learning-related contribution is implemented trace-fed revision of later model inputs. It has three distinct families: extracted user guidance, continuation summaries and retained diagnostic findings. Their automatic writes and later consumers are wired, but improved capacity for future action is not demonstrated. [Profile verification](profile-verification.md#verification) confirms bounded existence findings, not complete inventories or observed benefit.

User-memory extraction runs asynchronously after request dispatch, not after checking the current answer. It samples at most 17 recent user/assistant text messages, with character caps, and asks a separate model for persistent directives and profile facts. Code normalizes output and filters empty content and invalid supersession references before committing it without per-item human approval. Those are structural admission checks, not factual acceptance. See [MEM-RTE-memory-extraction](memory.md#mem-rte-memory-extraction) and [EPI-RTE-memory-admission](epistemic.md#epi-rte-memory-admission).

Memory rows are user-scoped rather than project-keyed, despite project enablement controls. Default prompts automatically supply active category/content, excluding current-chat rows, prioritizing rules and newer entries, and applying a 1000-token content budget. The consumer receives neither original evidence nor reasons. This is identity/order/budget selection, not task-targeted semantic retrieval. Overrides or disablement can omit delivery. Supersession retains an inactive predecessor; explicit deletion and disabling differ, and deleting a successor does not automatically restore its predecessor. See [MEM-OBJ-memories](memory.md#mem-obj-memories), [MEM-BAP-user-memory](memory.md#mem-bap-user-memory) and [MEM-RTE-memory-maintenance](memory.md#mem-rte-memory-maintenance).

Compaction has a shorter horizon. Above the configured threshold, code replaces the eligible old prefix with a model summary while preserving the system instructions and current-user tail. The summarizer receives image-stripped, backward-budget-selected input: older material can disappear before summarization even though its entire eligible span is replaced. A successful streamed marker enables later reconstruction; nonstreaming generation retains the replacement for subsequent in-process steps without that persistence channel. Summary faithfulness and successful context fit are unobserved. Files use explicit path reads, not automatic pointer following; documents can remain outside the window until requested. See [MEM-RTE-chat-compaction](memory.md#mem-rte-chat-compaction) and [MEM-RTE-saved-files](memory.md#mem-rte-saved-files).

### A connected evaluation workflow

The representative workflow is a CLI analytics test with reference SQL, selected because it connects model work, a second model handoff, executable rejection, bounded repair and delivered reporting. The test author supplies the question and reference SQL. nao runs analytics through nonstreaming generation, then asks a model to write extraction SQL over the fetched result tables. Its prompt receives the question, response messages, expected column names and table descriptions, not expected row values. Code executes that SQL under a local safety policy and offers one repair after execution failure. The CLI then compares extracted rows with reference-query rows and checks tool assertions. A final mismatch records failure; it does not rerun analytics. Results are saved as timestamped JSON and printed summaries, with a failed-batch exit status. This is source-defined delivery, not an observed successful test. See [RT-RTE-test-answer](runtime.md#rt-rte-test-answer) and [the workflow account](workflow.md#workflow-account).

This supplies a genuine bounded acceptance criterion: tool assertions and reference-data comparison must pass on the data-verification branch. It does not independently verify that extraction SQL faithfully encodes the prose answer, that the reference captures the intended business rule, or that both warehouse queries share an atomic snapshot. Sorting and tolerances affect equality; both-empty datasets pass. Assertions-only and no-verification branches have weaker pass meanings. A saved report is neither an automatic deployment gate nor, by retention alone, a later learning input. See [EPI-RTE-test-comparison](epistemic.md#epi-rte-test-comparison) and [the workflow annotation](workflow.md#annotations).

### Feedback, proposed corrections and later guidance

The recommendation route inspects retained usage/feedback and context costs, requests diagnoses and edits from a restricted agent, repairs references, reconciles fingerprints/status/impact and retains findings. Future diagnostic runs receive compact summaries, not automatically all stored reasons. Dismissed fingerprints can veto repeat admission. Optional automatic PR creation uses a disposable clone rather than mutating live context. The status applied can follow either reconciliation resolution or successful PR opening; it proves neither a PR nor merge or deployment. See [RT-RTE-context-recommendation](runtime.md#rt-rte-context-recommendation), [MEM-OBJ-context-recommendation](memory.md#mem-obj-context-recommendation) and [EPI-RTE-finding-reconciliation](epistemic.md#epi-rte-finding-reconciliation).

Live delivery is separate: UI Git pull fast-forwards, while Python refresh and container startup can hard-reset fetched content; CLI sync writes provider outputs and templates. Later agent construction or reads can consume admitted guidance, but successful admission and subsequent dependence are unobserved. Git/configuration guards establish byte admission, not acceptance of a diagnosis or improvement in answers. See [RT-RTE-context-delivery](runtime.md#rt-rte-context-delivery).

The following properties remain independent, as assessed in [the epistemic conclusion](epistemic.md#bounded-conclusion):

- **Theory-builder condition 1, localized content:** diagnosis fields and prompts support causal-candidate formulation, but no actual formulated theory instance is established.
- **Condition 2, consumption:** delivery of findings is wired; decisions depending on the content of a theory are unobserved.
- **Condition 3, content-directed criticism:** prompts request diagnosis and resolution, but no demonstrated blame-correcting criticism and resulting revision or changed reliance is established.
- **Condition 4, iteration:** retained findings can reach another diagnostic round; retained criticism actually shaping that round is unobserved.
- **Learning from criticism:** trace-fed guidance updates are implemented; criticism of a consumed theory improving future capacity is not established.
- **Reflection:** usage/context self-representation and a proposal-to-guidance pathway are wired; exercised two-way causal dependence remains unobserved.
- **Autonomy:** computation performs internal diagnostic and proposal steps. Autonomous completion of external review/live admission, or an autonomous theory builder, is not established.
- **Self-improvement:** the recommendation path offers improvement-directed proposals and separate mechanisms capable of admitting later guidance. No run closes the links from evidence-responsive update through live organizational change to subsequent behavior causally depending on it; successful improvement additionally lacks outcome evidence. User-memory revision and compaction remain positive mechanisms without being upgraded to that conclusion.

For open analytics, the supported result is evidence access, selective context and answer delivery, not certified answers. For reference-SQL evaluation, the supported result is a bounded comparison with explicit failure/recovery semantics. For feedback-directed context maintenance, the supported result is durable diagnostic state and optional review requests, not a demonstrated closed improvement loop. A linked trace of diagnosis, review/admission, changed prompt or context, and subsequent content-dependent behavior would alter the exercised-path assessment. Validated references and extraction-fidelity checks would strengthen evaluation; controlled outcome comparisons would be needed for benefit attribution. Concrete theory/criticism/revision instances would change the individual theory-builder assessments. These requirements follow the gaps in the cited routes, not a product ranking.
