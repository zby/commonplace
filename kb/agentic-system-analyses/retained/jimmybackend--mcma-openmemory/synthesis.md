# MCMA-OpenMemory synthesis

## Bounded synthesis

### Evidence and architectural boundary

MCMA-OpenMemory is a user-controlled, encrypted memory archive with shipped CLI and web consumers and optional model services. Its Librarian and SecurityAgent are deterministic PHP service roles, not evidence of a model-directed worker scheduler. This account covers the repository at commit `556954d95f0d6d6894c5d46ffcc25a907150b0a7`, with an applicability cutoff of 2026-11-08. The whole-system functional boundary includes capture, maintenance, retrieval, model-facing prompts, browser recovery and evaluators. The evidence is source implementation and attributed design, not target execution. There are no supplied observed runs or causal experiments; tests are inspected programs, not passing results. External services and actual deployed configuration remain outside inspection. See SRC-1 in the [boundary and Source register](boundary.md#source-register).

The central distinction is between **retaining content**, **assigning it reuse status**, and **consuming it through a particular route**. An encrypted revision does not make its assertions true. Nor does one validation policy govern all copies or consumers. The library uses content-addressed encrypted objects and a replaceable manifest/root index to locate current revisions. Previous hashes retain lineage. Canonical explicit memories, their knowledge mirrors, interactions, derived navigation and diagnostic objects share this infrastructure but have separate update and consumption policies. See [MEM-OBJ-library-index](memory.md#mem-obj-library-index), [MEM-OBJ-explicit-memory](memory.md#mem-obj-explicit-memory), [MEM-OBJ-knowledge-metadata](memory.md#mem-obj-knowledge-metadata) and [MEM-OBJ-interaction](memory.md#mem-obj-interaction).

### From a request to an answer

The representative workflow is a browser question that needs generation, followed by archive-based interruption recovery. It was selected because it connects request identity, retrieval, context construction, generation, capture and delivery in one shipped path. The browser stores a pending request/conversation identity; the server authenticates the principal, selects the user library and checks for an archived request. Explicit-save and mutation syntax intercept before ordinary asking. Otherwise PHP, not the model, owns next-step selection. Billing-enabled requests add provider reservation and settlement protocols; those wrappers do not cover every possible provider caller. See the [workflow account](workflow.md#workflow-account) and [RT-RTE-web-request](runtime.md#rt-rte-web-request).

For an ordinary non-broad question, reusable exact knowledge can terminate the request. Otherwise configured semantic retrieval embeds the question, ranks actor-visible current-hash candidates and can return a reusable candidate meeting similarity or configured rerank thresholds. No generation call does not necessarily mean no model call: embedding may already have occurred. A recognized broad-recall question follows a different policy: matching confirmed canonical memory can return before strict knowledge assessment, while recognition suppresses exact and semantic direct returns even if canonical recall finds nothing. That latter forcing case qualifies the analysts' simpler exact-first description, as the [report verification](report-verification.md#limits) records. See [RT-RTE-ask-answer](runtime.md#rt-rte-ask-answer) and [MEM-OBJ-semantic-vectors](memory.md#mem-obj-semantic-vectors).

Strict knowledge assessment checks state, confidence, freshness/current requirements and reuse policy. It rejects disputed/retracted and never-direct records; other failures request revalidation. This is an implemented eligibility gate, not an independent investigation of the answer. Provenance count counts supplied entries, not corroborating investigations. Canonical recall instead maps confirmed maturity to verified/0.95 and stale=false without receiving currentRequired. Thus `current=true` is neither a universal freshness guarantee nor a request for fresh external research. Knowledge-only retraction does not establish withdrawal of the canonical source. The source itself qualifies confidence and provenance as metadata, not proof. See [EPI-RTE-knowledge-assessment](epistemic.md#epi-rte-knowledge-assessment), [EPI-CLM-knowledge-policy](epistemic.md#epi-clm-knowledge-policy), [EPI-OBJ-knowledge-record](epistemic.md#epi-obj-knowledge-record) and [EPI-RTE-knowledge-validation](epistemic.md#epi-rte-knowledge-validation).

When no direct route returns, the absence of a configured generator yields provider-required. Otherwise code constructs context and calls one generator, rejecting empty text rather than conducting a factual review or model-selected revision cycle. The CLI is narrower: its ask branch does not supply the three web context builders or archive the interaction. See [RT-RTE-ask-answer](runtime.md#rt-rte-ask-answer) and the [workflow account](workflow.md#workflow-account).

### What reaches the model

Web context builders reload selected durable material rather than compacting an accumulating live agent window. Conversation selection combines recent anchors with lexical relevance and can include unverified turns while excluding disputed/retracted ones. Multi-memory selection uses assessed knowledge and can deliver stale/current-required material as marked revalidation context. Broad recall has its own subject search and quality policies. Item limits, field clipping and byte accounting leave originals in storage for later reads. These budgets do not bound all combined provider messages, wrappers or exact tokenizer output. There is no isolated subagent frame whose return is the sole escaping content. See [RT-RTE-context-supply](runtime.md#rt-rte-context-supply) and its [memory annotation](memory.md#annotations).

The shipped connectors serialize selected reference fields and uncertainty into model input and separately instruct the model not to obey instructions inside memory. This is an implemented instruction policy requiring model cooperation, not an enforcement boundary. The provider receives selected data, not a Library handle. Direct custom provider calls need not use the selectors. Delivery is wired; actual reliance, compliance and benefit are unobserved. See [RT-BAP-memory-reference](runtime.md#rt-bap-memory-reference).

### Capture, correction and later reuse

Generated capture is optional software admission: it defaults to unverified/0.5 and preserves an existing exact record instead of overwriting it merely because generation succeeded. Explicit saving is different. A user supplies save intent and source text; an optional model organizes it; software accepts structurally valid output or falls back to source text. Code then writes confirmed canonical memory and attempts a verified knowledge mirror. Preservation instructions do not constitute a meaning-equivalence check, and the source original is not necessarily the text later returned. See [RT-RTE-ask-answer](runtime.md#rt-rte-ask-answer), [RT-RTE-explicit-capture](runtime.md#rt-rte-explicit-capture) and [RT-OBJ-organizer-instructions](runtime.md#rt-obj-organizer-instructions).

Caller validation, answer replacement, interaction approval and canonical mutation provide distinct correction paths. They change later eligibility or content, but owner-role invocation alone does not establish human deliberation or evidence-consuming factual acceptance. Approval can validate existing knowledge without replacing it with the archived answer. Canonical changes, mirrors, indexes and derivatives are not shown to commit atomically; successful canonical writing can coexist with failed synchronization. Tombstones and retraction withdraw current reliance on covered routes, not historical ciphertext. See [MEM-RTE-knowledge-editing](memory.md#mem-rte-knowledge-editing), [RT-RTE-interaction-approval](runtime.md#rt-rte-interaction-approval) and [RT-RTE-memory-mutation](runtime.md#rt-rte-memory-mutation).

The strongest supported trace-fed contribution is automatic durable organization: archived turns produce discovery state used by later context lookup; optional catalog classification produces retained labels that select thematic destinations. These are implemented trace-fed updates with later consumers, not merely raw log retention. They do not establish improved capacity for future action. Deterministic thematic snippets supply browsing material and are excluded from canonical recall; context traces supply inspection, not an established automatic policy-revision loop. The independently checked [profile verification](profile-verification.md#verification) preserves these distinctions. Supporting records are [MEM-OBJ-conversation-index](memory.md#mem-obj-conversation-index), [EPI-RTE-catalog-classification](epistemic.md#epi-rte-catalog-classification), [MEM-RTE-thematic-sync](memory.md#mem-rte-thematic-sync) and [MEM-RTE-inspector-snapshot](memory.md#mem-rte-inspector-snapshot).

No supplied evidence establishes that criticism of a consumed theory improved future capacity. The accepted account does not establish a formulated-theory route meeting conditions 1–4, and storage or labels cannot substitute for localized theory content, content-dependent decisions, content-directed criticism or retained iteration. It also does not establish reflection's two causal directions, autonomous theory criticism, or exercised self-improvement. These are independent unestablished properties, not consequences of a negative overall grade. The deterministic ownership of this request workflow is supported; it is not evidence of autonomous improvement. Configured inference requests do not update model weights, but opaque external provider state cannot support a system-complete learning negative. See the [epistemic bounded conclusion](epistemic.md#bounded-conclusion), [RT-RTE-ask-answer](runtime.md#rt-rte-ask-answer) and [MEM-RTE-semantic-maintenance](memory.md#mem-rte-semantic-maintenance).

### Delivery and scenario-relative assessment

Server JSON return, knowledge capture and conversation archiving are separate outcomes. The web attempts archive/trace writes even with `remember=false`, and persistence failure need not cancel a successful answer. Browser recovery polls for an archived conversation/request pair without regenerating. Pending means no archive entry was found, not that a computation is running. Recovered answers omit original context and decision fields; best-effort persistence and preflight lookup do not establish exactly-once execution. See [RT-RTE-web-request](runtime.md#rt-rte-web-request) and [WF-RTE-request-recovery](workflow.md#wf-rte-request-recovery).

For recalling user-retained material, the implementation supplies revisioned storage, explicit edits, multiple requested retrieval routes and bounded reference reconstruction. For fresh factual answering or audited review, its labels and similarity gates do not supply the missing factual evaluator, uniform freshness policy or complete replay evidence. Actor-aware permission checks can deny covered operations, but trusted PHP code holding raw APIs and keys is outside that protocol's isolation claim. See [MEM-RTE-library-authoring](memory.md#mem-rte-library-authoring), [EPI-RTE-knowledge-assessment](epistemic.md#epi-rte-knowledge-assessment) and [RT-CLM-permission-scope](runtime.md#rt-clm-permission-scope).

Concrete changes that would alter these assessments include a shared freshness/withdrawal policy across canonical and knowledge consumers; semantic comparison before promoting organized text; transaction or reconciliation evidence across mirrors and indexes; and recoverable decision traces alongside answers. Supplied executions would establish operation only within their conditions. Demonstrating improved capacity or exercised self-improvement would additionally require tracing an evidence-responsive retained change into later behavior, with comparison evidence appropriate to any claimed benefit or attribution. None is established by the present source wiring alone.
