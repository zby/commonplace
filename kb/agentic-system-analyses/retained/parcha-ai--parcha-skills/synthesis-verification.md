## Limits

- Skill-ify, in Discriminating mechanisms and in the scenario "Building durable
  capability from past work". The synthesis says the model "writes a standard
  `SKILL.md` package" and "may also hand the recipe to an external skill
  creator". The records give the opposite order. The procedure invokes the
  harness skill creator when it is installed, and the direct `SKILL.md` write
  is the fallback ([RT-RTE-skillify-admission](runtime.md#rt-rte-skillify-admission)
  progression; the boundary's "only a fallback instruction"). The scenario then
  says, without condition, "The package is written without evaluation,
  approval or provenance". [EPI-ABS-generated-skill-test](epistemic.md#epi-abs-generated-skill-test)
  and [MEM-ABS-skill-provenance](memory.md#mem-abs-skill-provenance) support
  only that the shipped procedure requires none of these. Both records leave
  open whether an installed creator adds them, and so does the synthesis's own
  creator row in Limitations. Readers should not conclude that generated
  skills lack evaluation, approval or provenance when a creator is installed.
  The finding holds for what the package requires and for the direct-write
  fallback.
- Representative workflow: the list of classes "unsearchable through the
  index" includes "host-deleted transcripts". This repeats the gap field of
  [EPI-RTE-empty-result-report](epistemic.md#epi-rte-empty-result-report).
  Memory integration issue 6, concerning
  [RT-OBJ-session-index](runtime.md#rt-obj-session-index) and
  [RT-OBJ-session-transcripts](runtime.md#rt-obj-session-transcripts),
  leaves open whether index entries or snippets survive deletion of their
  source transcripts. The synthesis's own Limitations row states the same
  unknown. Readers should not conclude that host-deleted transcripts are
  unsearchable. Pi sessions, thinking-only traces and redacted lines remain
  unsearchable as declared, so the scenario "Proving that something did not
  happen" still holds.
- Representative workflow: "Nothing persists the query, the rejected
  candidates or the answer." The workflow member scopes this to the skill
  ("The skill writes no record of the answer"). The host transcript retains
  the session, including the query and the answer. As declared, ingest makes
  that session retrievable by later invocations, including the Recall output
  it read back (memory annotation on
  [RT-RTE-index-maintenance](runtime.md#rt-rte-index-maintenance);
  later read-back field of [EPI-RTE-answer-receipt](epistemic.md#epi-rte-answer-receipt)).
  Readers should not conclude that Recall answers are lost after delivery.
  Only the skill's own writes omit them. They can return through host
  transcripts and the declared index.
- Learning, reflection, autonomy and self-improvement: the strongest-contribution
  bullet says "Retained session experience is automatically turned into
  durable artifacts", and it lists Brain captures and skill-ify packages
  among them. Only index ingest is automatic in the ordinary sense. A user
  request starts each capture and each skill-ify run, and the model authors
  the content without per-content approval
  ([RT-RTE-brain-capture](runtime.md#rt-rte-brain-capture),
  [RT-RTE-skillify-admission](runtime.md#rt-rte-skillify-admission); memory
  annotation on [RT-OBJ-generated-skill](runtime.md#rt-obj-generated-skill):
  "user-triggered rather than automatic"). Readers should not conclude that
  Recall captures records or generates skills without a user request.
  "Automatically" holds there only in the sense that no human approves the
  written text.
