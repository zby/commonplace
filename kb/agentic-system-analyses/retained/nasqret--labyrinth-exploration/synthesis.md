# Labyrinth Exploration synthesis

## Bounded synthesis

Labyrinth Exploration is a research skill for open-ended work in mathematics, theoretical science and algorithms. Its measure of progress is a change to the research map: a proof can close a question, and a refutation can rule out a line of inquiry and expose a better question. A model coordinator chooses the work and decides what the project may treat as established. A separate Python engine appends events, checks selected file conditions and builds views. It does not launch agents or referee research. The [evidence boundary](boundary.md#boundary-and-evidence) is the whole shipped skill, engine, browser template, examples and evaluators at commit `019a93da59313e697dc6f28bcfe1588a376c7565` (cutoff 2026-11-23), not the Codex or Claude Code host or any private deployment. SRC-1 provides inspected code, design instructions and retrospective reports, not observed target runs or causal comparisons. See [RT-CLM-map-progress](runtime.md#rt-clm-map-progress) and the [source register](boundary.md#source-register).

### From the project map to a candidate

On a continuation request, the skill directs the coordinator to read the project's status, dashboard and pending work, then pick up to three questions where a small computation or proof step could change the map. The project files keep graph statements, tests and review fields, frontier claims about which values are realized or impossible, best results and their history, and separate events, reports, proofs and raw evidence. Prose carries claims and reasons for interpretation; IDs, statuses and intervals drive fixed program rules. The graph is a file, not a graph database. The host supplies skill loading, model inference, tools, permissions and agent lifecycle; the skill neither pins model versions nor implements a weight update. The ordinary continuation route is not universal: an unknowns readout need not change the map, and an external result can go to review without a new investigation. A [Codex campaign](workflow.md#workflow-account) is the prescribed route when an iteration cannot cover the promising questions. The coordinator supplies each investigator with a precise task, selected proofs and failed approaches, file pointers, a distinct output directory and a share of the session budget. The brief supplies selected material without a worker request; opening the cited files is a separate requested read. A fresh referee is to receive definitions, claims and raw evidence rather than inherited reasoning where the host allows that choice. These are controls on requested context, not a token limit, a filesystem sandbox or evidence of host isolation. Workers return evidence and a final report; the coordinator saves the message verbatim with separate provenance and can log results while review is pending. A missing notification can prompt a transcript lookup. After restart, saved reports preserve content, but old journal IDs do not establish live thread or job state. ### From evidence to authorized use

The review policy is for **established use**, not all use. An unchecked literature lead can guide exploration; using it as a premise calls for comparing the wording and quantifiers to the original. That can preserve the source's warrant within scope, not independently prove its claim. For a new agent or external-model result, an independent referee checks the named proof steps or recomputes counts from the definitions without reusing the author's verification code. If full recomputation is too expensive, a disclosed sample warrants agreement only on the cases compared. Earlier-size code validation is not same-size replay. The referee returns itemized reasons and corrections; the coordinator applies corrections, adds a spot check and decides whether to establish the corrected result, leave a gap pending or reject a false statement. There is no general answer key. A favorable verdict changes review state, not the evidence tier: published or standard facts stay within source scope, local proofs carry their non-peer-reviewed caveat and review state, and certified finite results are facts only at stated sizes with pending same-size replay disclosed where applicable. Computational evidence, conjectures and hunches do not become facts by being retained. For a reviewed result, a writer proposes exact edits and tests them on a copy. Build success checks the document, not fidelity to the verdict; the coordinator compares the draft to the verdict, checks anchors and owns the canonical edits. A refuted conjecture instead leaves a counterexample and lesson for later briefs. The prescribed close rebuilds derived artifacts and hands the user an accessible local dashboard path or authorized private delivery, with results and pending work distinguished. This is a specified end-to-end workflow, not an observed delivery. ### What the engine can establish

The engine can reject an unrecognized event type on its append route, but a recognized type can be logged with an unknown node reference. It does not authenticate the summary or determine who chose its content. An explicit check diagnoses selected references, metadata and conflicting frontier labels. Its test-presence rule covers only open curated conjectures and does not judge test quality. A failed check stops a caller's `check && build`, not standalone build, edits between the two calls or use of an older view. On a well-formed frontier row, standalone projection can count an admissible value labeled both realized and impossible as resolved by giving realized priority. The overlap diagnostic can also report grid-aligned conflicts above the row's upper bound, which projection clips away. Resolved fraction therefore measures the winning input labels, not what has been scientifically established. SRC-1 `templates/lab.py`; [RT-RTE-event-append](runtime.md#rt-rte-event-append), [EPI-RTE-schema-check](epistemic.md#epi-rte-schema-check), [EPI-RTE-conflict-check](epistemic.md#epi-rte-conflict-check), [EPI-RTE-check-exit](epistemic.md#epi-rte-check-exit), [EPI-RTE-frontier-project](epistemic.md#epi-rte-frontier-project).

The distinction matters in two shipped routes. An optional project blueprint is executable Python imported with the caller's privileges before diagnostics; its merged statements can receive default tier and established status without review. Separately, the triangle-count example moves from sampling at size eight to exhaustive enumeration of labeled simple graphs. The result is exact within that finite domain conditional on faithful encoding and computation; a sampled omission alone is not proof of impossibility. With writes enabled and no existing exhaustive marker, the tutorial writer persists computed values alongside preset answer text and illustrative referee metadata. It does not read a verdict or test agreement with the stored conjecture. If interrupted after rewriting the graph, its retry guard can leave the best-results table stale. Neither the writer, direct project edits nor the blueprint route implements the coordinator's review policy. ### What carries forward

The strongest implemented feedback path turns recorded activity into retained context: build selects a file-order event tail for status and includes parsed events in the dashboard payload. Later readers get selected context, not a transcript or a new scientific result. Status omits event evidence locators; the browser timeline sorts timestamps and does not display those locators. Frontier runs can compress reasons, and dense rows can be reduced to bins that keep counts alone. The browser reads embedded HTML data, conditional on the template and insertion marker; it does not fetch the sibling JSON. The shipped example tests reopen that standalone JSON and assert selected fixture fields. That is a software evaluation route, not evidence of an executed test, successful render or research-session JSON use. Page initialization selects board and table content without a row request; restoring a stored tab changes visibility, not which research evidence is delivered. Independently configured document exports can carry current results or status to later readers; Markdown keeps dated prior result text while LaTeX can substitute supplied text and omits history. None is a rollback, and actual document inclusion is unestablished. SRC-1 `templates/lab.py`, `templates/dashboard.html`, `tests/test_lab.py`; [EPI-RTE-status-project](epistemic.md#epi-rte-status-project), [EPI-RTE-snapshot-write](epistemic.md#epi-rte-snapshot-write), [EPI-RTE-json-assertions](epistemic.md#epi-rte-json-assertions), [MEM-RTE-restore-tab](memory.md#mem-rte-restore-tab), [memory read-back](memory.md#read-back).

The protocol also directs a model coordinator to turn counterexamples and criticism into durable lessons or corrections for later investigations. For mathematical conjectures, all four theory-builder conditions are supported **as design**: (1) a localized statement and test, (2) a test chosen according to what the statement says, (3) a named flaw or counterexample that changes the statement or reliance on it, and (4) a retained result of criticism that shapes the next round. The tutorial script does not establish conditions 2–4 merely by implementing a fixed test and overwriting files. Neither the wired event projection nor the prescribed lesson route shows that criticizing a consumed theory improved future capacity. Reflection is independently unestablished: revising the research product is not evidence of a representation of the live method that both tracks changes to it and changes subsequent operation. Autonomous theory building is also unestablished: the procedure allows a co-author to supply review and the records do not establish an end-to-end computational loop. For self-improvement at this shipped boundary across sessions, the records distinguish reported changes to briefs and human releases from research corrections, but do not show the later operation causally depending on an evidence-directed change to the system's own operating method. SRC-1 `references/loop.md`, `references/campaigns.md`, `references/lessons.md`, `MAINTAINING.md`; [RT-RTE-review-integration](runtime.md#rt-rte-review-integration), [RT-RTE-example-update](runtime.md#rt-rte-example-update), [RT-RTE-maintainer-update](runtime.md#rt-rte-maintainer-update), [epistemic conclusion](epistemic.md#bounded-conclusion).

For a research campaign that needs continuity, the design supplies an inspectable record of what to revisit; whether it preserves the relevant reasons depends on which artifact the next worker receives. For a project that requires evidence-backed admission, a status label or checked build cannot substitute for a linked verdict and an account of the exact admitted statement. A gate that consumed that evidence on every material write route would change the enforcement assessment; linked campaign records would establish whether the existing procedure was followed. A comparison that varied the briefing or review mechanism independently would be needed to attribute a benefit to that mechanism. See [report verification](report-verification.md#verification).
