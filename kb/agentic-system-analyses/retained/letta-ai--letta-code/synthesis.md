# Letta Code synthesis

## Bounded synthesis

### From a request to host effects

Letta Code is an enclosing agent runtime that runs conversations, executes admitted client tools and preserves context for later turns. This account covers its shipped CLI, local backend, hosted-service client and maintenance drivers at commit `271f119dcf37d58649a18e6c733386b3c710a456`, with an applicability cutoff of 2026-10-12. The sole source, SRC-1, supplies implementation and doctrine/design. No target, tests or examples were executed; no observed runs or causal experiments were supplied. External Letta service, provider and host-application internals are excluded. A whole-system source boundary is not an exhaustive audit of every shipped route. See [boundary and evidence](boundary.md#boundary-and-evidence) and [Source register](boundary.md#source-register).

In the ordinary headless path, the caller chooses an agent and conversation and supplies a problem. The harness prepares instructions, history, skills and tool schemas. The local backend invokes a provider executor and persists the stream; the hosted alternative delegates inference and server state through an API. The model proposes text and tool arguments, while host code interprets stop reasons and owns continuation. Client-tool calls return to the harness for permission classification, execution or denial, then feed their results into another model round. Assistant text or structured headless output is the terminal product. Agent, conversation, run and tool-context identities serve different purposes; captured tool context prevents later execution from silently using a changed global registry. See [RT-RTE-foreground-turn](runtime.md#rt-rte-foreground-turn), [RT-OBJ-tool-context](runtime.md#rt-obj-tool-context) and [RT-CMP-turn-model](runtime.md#rt-cmp-turn-model).

Admission is not necessarily a human decision. One-shot headless denies requests needing interactive input; bidirectional sessions can receive permission responses. Automatic rules, hooks and unrestricted modes also decide. Hooks can block or rewrite arguments before execution. Permissions license actions, not the truth of their results. Optional kernel shell isolation is off by default, and its covered shell paths do not include in-process mod imports or independently spawned hooks. See [RT-CLM-approval-policy](runtime.md#rt-clm-approval-policy), [EPI-RTE-hook-policy](epistemic.md#epi-rte-hook-policy) and [RT-CLM-shell-isolation](runtime.md#rt-clm-shell-isolation).

Listener execution adds a stronger, conditional recovery protocol: before tool code runs, it durably records an unknown outcome; after settlement, it records the exact result. This distinguishes provably unstarted calls from effects that may already have happened. It does not establish exactly-once execution or rollback, and the ordinary headless path does not acquire this guarantee. App Server and channel ingress provide alternate callers, and schedules enqueue prompts without an active terminal user; queued is not completed. See [RT-RTE-listener-approval](runtime.md#rt-rte-listener-approval), [RT-CLM-effect-checkpoint](runtime.md#rt-clm-effect-checkpoint), [RT-CLM-app-server-auth](runtime.md#rt-clm-app-server-auth) and [RT-RTE-scheduled-prompt](runtime.md#rt-rte-scheduled-prompt).

### Delegation, return and delivery

The representative multi-step workflow is a conditional local, non-memory Task in a live bidirectional headless session. The parent proposes an assignment; Task checks child identity and conversation scope, captures parent scope, registers background state and returns a launch receipt. The child runs its own conversation. Its CLI defaults use unrestricted permissions with inherited disallows and configured filters, not the parent's live approval dialog. These defaults concern Task, not every delegation route. See [RT-RTE-subagent-task](runtime.md#rt-rte-subagent-task) and the [workflow account](workflow.md#workflow-account).

Background settlement records child success or error and routes bounded report text plus an output-file reference to the captured parent. Bidirectional headless turns that notification into queued synthetic user input for a subsequent parent turn. The parent remains responsible for the caller-facing response. Launch, child protocol completion, product verification and final delivery are distinct milestones. A captured result without a completion error is not an independently verified solution. Recognizable truncated result transport can trigger one respawn; that retry does not undo earlier effects. Keeping the input session live is necessary for this selected notification-to-continuation path; successful one-shot asynchronous delivery is not inferred. See [workflow account](workflow.md#workflow-account) and [RT-RTE-foreground-turn](runtime.md#rt-rte-foreground-turn).

### What persists and reaches the next decision

Local memory has several consumers rather than one visibility rule. Automatic core compilation reads committed Git HEAD: in the v2 layout, root Markdown bodies become standing context and child indexes provide directory pointers. A changed committed revision can enter an ongoing conversation as a memory-update message. Requested Memory reads and Skill loading instead read working-tree files. Consequently, commitment controls automatic core projection, not all tool-fed context. Skill discovery advertises metadata; requested loading injects full procedure text separately. History loading pushes selected prior conversation context, while transcript search returns requested bounded results. See [MEM-RTE-core-projection](memory.md#mem-rte-core-projection), [MEM-CLM-visibility-boundary](memory.md#mem-clm-visibility-boundary), [MEM-RTE-deferred-read](memory.md#mem-rte-deferred-read), [MEM-RTE-skill-loading](memory.md#mem-rte-skill-loading) and [MEM-RTE-transcript-search](memory.md#mem-rte-transcript-search).

Git admission checks layout, metadata, protected paths and character budgets. These are structural constraints, not provider-token guarantees or factual acceptance. A false body assertion can pass valid frontmatter. Hooks are bypassable, and destructive backup restore is a separate directory-replacement route. The actual force of memory prose is model-interpreted context or instruction; retained policy and progress metadata have fixed program consumers. Root `ARCHIVE.md` remains core, so the shipped archival placement instruction does not itself reduce automatic exposure. See [MEM-RTE-memory-admission](memory.md#mem-rte-memory-admission), [EPI-RTE-frontmatter-check](epistemic.md#epi-rte-frontmatter-check), [EPI-RTE-commit-admission](epistemic.md#epi-rte-commit-admission), [EPI-RTE-memory-restore](epistemic.md#epi-rte-memory-restore), [MEM-BAP-memory-context](memory.md#mem-bap-memory-context) and [MEM-CLM-archive-projection](memory.md#mem-clm-archive-projection).

Two automatic trace-fed maintenance chains are wired. Compaction supplies bounded conversation and tool activity to an auxiliary model, trims/clips its output, and persists a summary plus retained tail for later provider calls. It reduces active context without an inspected fidelity oracle. Reflection supplies selected transcript slices and current memory to a background worker in a memory worktree. Instructions request lasting facts, contradiction correction and reusable skills. Clean successful proposals can merge mechanically; optional explicit integration is another agent conversation, not necessarily human review. Failed integration leaves source input eligible for retry; successful no-change reflection can consume it. Reasons are requested in reports and commits, but normal core and skill consumers read bodies rather than those explanations. See [MEM-RTE-transcript-compaction](memory.md#mem-rte-transcript-compaction), [EPI-RTE-summary-generation](epistemic.md#epi-rte-summary-generation), [MEM-RTE-reflection-integration](memory.md#mem-rte-reflection-integration), [EPI-RTE-reflection-guidance](epistemic.md#epi-rte-reflection-guidance) and [MEM-BAP-reflection-progress](memory.md#mem-bap-reflection-progress).

These chains establish local wired trace-fed durable updates, not improved capacity or parametric training. Requested reflection curation remains doctrine-strength; summary semantics remain indeterminate. Optional arena selection affords a human-facing winner or tie choice with loser discard, but no enforced factual criterion or demonstrated later learning from its log. Shared attachment controls discovery eligibility; detach leaves bytes on disk. Hosted non-skill memory remains opaque. See [MEM-RTE-arena-selection](memory.md#mem-rte-arena-selection), [MEM-RTE-repository-sync](memory.md#mem-rte-repository-sync), [MEM-OBJ-hosted-memory](memory.md#mem-obj-hosted-memory) and [profile verification](profile-verification.md#verification).

### Evidence-responsive change and assessment

The strongest inspected improvement-directed contribution is the separate mod-learning builder. Configured scenarios evaluate captured output/trace markers, exit and timeout; reports feed later proposal rounds, passing candidates are preferred, and promotion can copy selected executable code to a configured path. This is evidence-responsive successor selection for scenario conformance. Live activation is a separate mod-loading route, not a consequence proved by copying. Settings patches and release updates provide other organization-change mechanisms but do not themselves judge improvement. See [EPI-RTE-mod-evaluation](epistemic.md#epi-rte-mod-evaluation), [EPI-RTE-mod-selection](epistemic.md#epi-rte-mod-selection), [RT-RTE-extension-load](runtime.md#rt-rte-extension-load), [RT-RTE-settings-patch](runtime.md#rt-rte-settings-patch) and [RT-RTE-package-update](runtime.md#rt-rte-package-update).

For continuity across long conversations, the architecture supplies durable text and explicit later-consumer channels, with lossy summary and requested retrieval alternatives. For delegated work, it supplies asynchronous settlement and parent continuation, not generic product verification. For tested executable adaptation, the builder supplies bounded evaluation and selection, not a demonstrated component effect or transfer beyond configured scenarios. These are scenario-relative capacities, not a product ranking. The public claim of long-horizon learning through self-rewriting exceeds the supplied evidence for beneficial future action. See [EPI-CLM-long-horizons](epistemic.md#epi-clm-long-horizons) and the [epistemic bounded conclusion](epistemic.md#bounded-conclusion).

The independent properties remain separate:

- **Theory-builder conditions 1–4:** the accepted account does not establish an actual formulated theory instance, decisions depending on its content, content-directed criticism with blame and changed reliance, or a next round shaped by that criticism. These remain unestablished, not evidenced absent. Mod scores and retained reports do not substitute for those conditions.
- **Learning from criticism of a consumed theory:** retained traces and evaluation-responsive iteration are positive contributions, but no supplied comparison establishes improved future capacity through such criticism.
- **Reflection:** instructions request review of the agent's experience and memory, and updates can return to later behavior through wired context channels. This supports requested self-representation and update capacity; observed representation-mediated effects remain uninspected.
- **Autonomy:** software and models can launch, propose and mechanically integrate without per-edit human approval on the inspected maintenance paths. This does not establish computation performing every semantic operation of an autonomous theory builder; optional arena choice is a different admission path.
- **Self-improvement:** the mod builder supports a dormant improvement-directed, evaluation-responsive change pathway at configured-scenario scope. Memory reflection wires trace-informed updates to later context. Neither establishes exercised self-improvement over sessions: actual evidence-to-update dependence and subsequent operation causally depending on the live change are not supplied. Successful improvement requires separate outcome evidence.

These distinctions follow the [epistemic bounded conclusion](epistemic.md#bounded-conclusion), [EPI-RTE-mod-selection](epistemic.md#epi-rte-mod-selection), [MEM-RTE-reflection-integration](memory.md#mem-rte-reflection-integration) and [report verification](report-verification.md#verification). Unassessed relevant paths prevent unqualified system-wide negatives. A candidate-to-evaluation-to-live-load trace with later operation would change the activation assessment; controlled outcome comparisons would address benefit. Concrete memory candidates, preserved criticisms and their later consumers would address theory-building and semantic acceptance. Correcting root archival placement or changing compiler selection would alter the context-load finding, whereas merely renaming a file would not.
