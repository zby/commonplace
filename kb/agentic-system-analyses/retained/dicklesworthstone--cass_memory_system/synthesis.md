# cass_memory_system synthesis

## Bounded synthesis

### From coding experience to later guidance

cass_memory_system (CM, invoked as `cm` or `cass-memory`) implements a durable route from coding-session records to guidance offered during later work. It also updates the standing of existing rules from feedback. These are source-wired contributions, not merely raw-log storage. Whether they improve future action remains unresolved: no execution trace, populated deployment corpus or causal comparison was supplied. The evidence is implementation and target-authored doctrine from `https://github.com/Dicklesworthstone/cass_memory_system` at commit `8aca3bbb6732321dca041b32c155617784687897`, with applicability cutoff 2026-10-13. Tests were inspected, not run. The whole-system boundary includes shipped production, maintenance, admission and consumption paths, but not external cass indexing, model internals or enclosing-agent execution ([boundary](boundary.md#boundary-and-evidence), SRC-1 [Source register](boundary.md#source-register)).

CM is a memory service for a coding agent, not that agent's task planner. Its CLI supplies retrieval, reflection and maintenance; an HTTP JSON-RPC server dispatches context and mutation tools; installed session-end hooks can initiate reflection. Code owns memory progression and selection. Models supply summaries, proposed changes and some judgments. The external caller owns the next coding action and may ignore returned rules ([RT-RTE-http-tools](runtime.md#rt-rte-http-tools), [RT-RTE-reflection-update](runtime.md#rt-rte-reflection-update), [RT-RTE-context-read](runtime.md#rt-rte-context-read); SRC-1 `src/commands/serve.ts`, `src/orchestrator.ts`, `src/commands/context.ts`).

The representative shipped workflow is `cm reflect --session <transcript> --json`, followed by a later context request. It connects acquisition, model handoffs, admission, durable delivery and recovery; it does not complete the original coding task. CM exports and sanitizes session content, persists a JSON diary, and supplies selected diary fields, existing rules and up to three related-history snippets to a reflector. Existing-rule and history strings receive separate 20,000-character prompt limits. The model returns structured deltas rather than an unrestricted modification of storage. Repeated proposal passes reuse the same formatted rule snapshot; they are not demonstrated criticism-and-revision rounds ([workflow account](workflow.md#workflow-account), [workflow annotation](workflow.md#annotations), [MEM-OBJ-diary-entry](memory.md#mem-obj-diary-entry); SRC-1 `src/diary.ts`, `src/reflect.ts`, `src/llm.ts`).

### Admission is consequential but not universal validation

Some reflection additions encounter a real evidence-consuming decision. CM counts success/failure language in retrieved historical snippets and can request a model's support/contradiction judgment. The result can reject or permit an addition for reusable playbook guidance. An evidence-accepted addition that survives curation can retain its originating-session link and proposal reason, be saved, and enter later reflection or task context. This conditional checking, acceptance and lifecycle integration is implemented; absence of a run trace does not negate that architecture ([EPI-RTE-evidence-check](epistemic.md#epi-rte-evidence-check), [EPI-RTE-validation-disposition](epistemic.md#epi-rte-validation-disposition); SRC-1 `src/validate.ts`, `src/orchestrator.ts`, `src/curate.ts`, `src/playbook.ts`).

The criterion is historical textual support, not independently verified rule-caused success. Non-add deltas, disabled validation and short additions bypass the gate; a draft with no success signal can pass without a validator call. Model-refined wording can replace an addition without an independent recheck. Curation rejects malformed additions and handles duplicates, but contradiction detection only warns. Contrary directives are excluded from duplicate matching rather than rejected. Therefore validity, saved content and warranted content are distinct, and the public claim of validation before every rule joins is too broad ([EPI-CLM-scientific-validation](epistemic.md#epi-clm-scientific-validation), [RT-RTE-reflection-update](runtime.md#rt-rte-reflection-update), [MEM-RTE-rule-curation](memory.md#mem-rte-rule-curation); SRC-1 `README.md`, `src/validate.ts`, `src/curate.ts`).

Other entry points make this distinction material. Onboarding delegates semantic extraction to the caller; ordinary additions have optional quality checks. Imports and starters can admit content and asserted standing without reflection's historical gate. Starting any of these workflows does not establish human approval of each item. Reflection admission is computational; the trauma initializer separately asks a human to approve a scanned batch. Generic add, mark, import and maintenance caller identity remains unresolved ([RT-RTE-onboard-add](runtime.md#rt-rte-onboard-add), [MEM-RTE-portable-admission](memory.md#mem-rte-portable-admission), [MEM-RTE-trauma-admission](memory.md#mem-rte-trauma-admission); SRC-1 `src/commands/playbook.ts`, `src/commands/init.ts`).

### Durable delivery and selective reuse

Reflection serializes cooperating runs for a workspace, then reloads fresh playbooks under ordered merge locks before saving. Saves precede processed-session marking. Growth watermarks, partial proposal progress and failure cooldowns support incremental work and retry. They do not form a transaction across repository/global playbooks, processed logs and post-merge outcomes. A detached hook's PID means initiation, not durable delivery; even dry-run can persist a diary before returning proposed deltas. Delivery means saved changes are available to later readers, not that an agent used them successfully ([RT-RTE-reflection-update](runtime.md#rt-rte-reflection-update), [workflow account](workflow.md#workflow-account); SRC-1 `src/orchestrator.ts`, `src/tracking.ts`, `src/commands/hook.ts`).

For `cm context "<task>" --json`, code reloads merged YAML playbooks, filters active workspace-applicable rules, ranks with lexical and optional embedding relevance plus feedback influence, and selects a compact briefing. The estimated token budget covers projected bullets, not warnings, history, the task or the enclosing model window; the first relevant bullet can exceed it. Semantic or cass failures can leave lexical or playbook-only context. Omitted rules remain stored for later requests. This is controlled supply of external context, not trimming of an agent's accumulated conversation ([RT-RTE-context-read](runtime.md#rt-rte-context-read), [MEM-OBJ-embedding-cache](memory.md#mem-obj-embedding-cache); SRC-1 `src/commands/context.ts`, `src/semantic.ts`).

The briefing contains rule words, IDs, standing and shortened reasoning, but not full feedback events, source-session arrays or embeddings. Additions can preserve reasons; replacements can leave them stale, merges use synthetic lineage, and the next reflector's existing-rule view omits them. Explicit `why`, resources and export paths offer different, sometimes fuller views. They bypass task-context selection guarantees. An exported agent instruction file affords later host guidance, but neither its actual loading nor its later read direction is established ([MEM-OBJ-reasoning](memory.md#mem-obj-reasoning), [MEM-RTE-provenance-read](memory.md#mem-rte-provenance-read); SRC-1 `src/reflect.ts`, `src/utils.ts`, `src/commands/why.ts`, `src/commands/project.ts`). Requested context returns are pull; automatic supply of retained material to the reflector and fixed control consumers is a separate operation, not unsolicited rule injection into every coding session ([profile verification](profile-verification.md#verification)).

### Feedback, withdrawal and stronger control channels

Rule text and reliance can change independently. Direct labels and automatic session-outcome grading persist events that affect scores, maturity and active eligibility. A delivery log can backfill displayed rule IDs, but display does not prove use. Broad-harm safeguards and abstention limit grading policy without establishing causal helpfulness. Eligible harmful positive rules can be converted into avoidance text; this is a durable policy rewrite, not an explained finding that the converse works. Fast diary status also defaults to success without success/error indicators, an unsupported outcome conjecture rather than faithful extraction ([RT-RTE-feedback-update](runtime.md#rt-rte-feedback-update), [MEM-RTE-outcome-feedback](memory.md#mem-rte-outcome-feedback), [EPI-RTE-curator-inversion](epistemic.md#epi-rte-curator-inversion), [EPI-RTE-diary-inference](epistemic.md#epi-rte-diary-inference); SRC-1 `src/outcome.ts`, `src/curate.ts`, `src/diary.ts`).

Withdrawal can retain blocked content so loaders suppress exact or high-token-overlap copies under other IDs. Undo and support scrubbing change eligibility, not historical truth, and do not necessarily update exported files or every legacy blocklist. Trauma entries provide a different channel: active regexes drive generated host/Git checks, while their natural-language messages explain denial. The pre-tool route covers Bash commands, allows other tool names and malformed input, skips invalid regexes and fails open on storage errors. Effective prevention requires installation and host enforcement; it is not a universal sandbox. CLI context adds a separate nonblocking trauma warning not implemented by the shared HTTP context generator ([MEM-RTE-rule-withdrawal](memory.md#mem-rte-rule-withdrawal), [MEM-OBJ-blocked-entry](memory.md#mem-obj-blocked-entry), [RT-RTE-trauma-guard](runtime.md#rt-rte-trauma-guard), [memory context annotation](memory.md#annotations); SRC-1 `src/playbook.ts`, `src/trauma_guard_script.ts`, `src/commands/context.ts`).

### Assessment at this boundary

For later coding guidance, CM provides connected automatic trace-to-rule and trace-to-standing paths with durable consumers. That establishes wired trace learning in the write-route sense, not improved capacity for future action. The inspected benchmark compares authored expected-ID ranking fixtures against a reconstructed incumbent; the learning-loop test uses stubbed proposals. Neither supplies observed improvement, generated-rule truth or component-level causal benefit ([MEM-CLM-evaluation-limits](memory.md#mem-clm-evaluation-limits), [EPI-RTE-retrieval-benchmark](epistemic.md#epi-rte-retrieval-benchmark); SRC-1 `test/learning-loop.e2e.test.ts`, `test/context-retrieval-benchmark.test.ts`).

The runtime's independent theory assessments remain: condition 1, localized content, is **afforded** through whole-rule addressability, with actual theory instances unsupplied; condition 2, content-dependent consumption, is **claimed** rather than demonstrated by delivery; condition 3, content-directed criticism, is **claimed** through rule-specific criticism requests without a claim/result/blame/revision trace; condition 4, retained criticism shaping another round, is **uninspected**. Criticism of a consumed theory improving future capacity is separately **uninspected**. Reflection has an implemented session/rule-feedback representation, update and return path; reflective revision of CM's own method and autonomous theory building remain **uninspected**. Computational admission alone does not establish every internal theory-building operation ([RT-RTE-reflection-update](runtime.md#rt-rte-reflection-update); SRC-1 `src/llm.ts`, `src/reflect.ts`).

At the horizon of later CM invocations, retained guidance and standing can change CM's own proposal inputs and selection, rather than remaining solely external products. This supports a dispositional, improvement-directed self-change pathway toward more useful future guidance. Exercised self-improvement is not established: no subsequent operation trace shows causal dependence on a particular evidence-responsive update, and successful improvement needs separate outcomes. Reflection, automation and persistence do not close that link. CM changes data, not inspected executable methods or model weights; configured generation and embedding names do not pin immutable provider versions ([RT-RTE-reflection-update](runtime.md#rt-rte-reflection-update), [MEM-RTE-outcome-feedback](memory.md#mem-rte-outcome-feedback), [RT-CMP-generation-model](runtime.md#rt-cmp-generation-model), [RT-CMP-embedding-model](runtime.md#rt-cmp-embedding-model); SRC-1 `src/orchestrator.ts`, `src/llm.ts`, `src/semantic.ts`).

A candidate-to-verdict-to-save-to-read trace would establish exercised admission and reuse; a criticism episode retained and demonstrably shaping the next round would change the theory assessment. A controlled comparison of later task performance with independently varied updates would address useful learning at that comparison's granularity. An independent refinement recheck or a genuinely enforced contradiction gate would change admission guarantees, but neither is present in the inspected handoffs. Installed-host traces across named tools would resolve activation, not justify universal safety. All ten memory-profile axes retain partial coverage, so the local mechanisms above support no complete-value comparison or system-wide epistemic grade ([report verification](report-verification.md#verification), [profile verification](profile-verification.md#verification)). No additional source reads were made for this synthesis.
