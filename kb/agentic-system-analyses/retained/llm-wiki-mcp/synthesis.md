# LLM-WIKI-MCP synthesis

## Bounded synthesis

### From local sources to reusable knowledge

LLM-WIKI-MCP is a local knowledge system with CLI, Python and MCP interfaces. It maintains Markdown pages, indexes them in SQLite, retrieves selected passages and can request answers from an Ollama-compatible model. This account covers the shipped producers, maintenance commands, callers and readers at commit **25efb7631082fa3732723fee08e24d39b43311fa**, with an applicability cutoff of **2026-10-15**. The evidence is SRC-1 implementation and separately attributed doctrine/design, as registered in the [boundary](boundary.md#source-register). No target code, tests, examples or provider requests were executed. The account establishes implementation wiring, not successful deployment, observed answers or causal benefit. It uses accepted member records; no frozen-source rereads were needed.

The claimed operating sequence is ingest, preserve provenance, retrieve wiki knowledge and supply local agents with context. Markdown is the authoritative storage substrate for retrieval, not an assurance that its statements are true. Caller bodies, extracted sources, seeds, clipped transcripts, decision entries and structural repairs can all enter pages. Original authorship and source warrant remain unresolved without a deployment corpus. See [EPI-CLM-wiki-substrate](epistemic.md#epi-clm-wiki-substrate), [MEM-OBJ-wiki](memory.md#mem-obj-wiki) and [MEM-RTE-transcript-decision](memory.md#mem-rte-transcript-decision).

Admission is operational rather than factual: existing-title checks, overwrite modes and apply flags decide whether writes occur. Starting an import or approving a batch does not establish a human decision accepting every resulting statement. The provenance-aware importer compares source hashes and datestamps before replacement; the one-shot CLI has a separate import path. Provenance stores update metadata, not complete old source payloads or source endorsement. An unchanged source can be skipped even if its separately generated page was deleted. See [RT-RTE-knowledge-write](runtime.md#rt-rte-knowledge-write) and [MEM-OBJ-provenance](memory.md#mem-obj-provenance).

Derived sidecar notes distinguish this system from a page-only index. Despite their AI label, their inspected producer counts terms and renders link suggestions in a fixed template, without model inference. Old-note vocabulary can feed later iterations. Notes influence ranking and may supply snippets before any suggested link is promoted into a canonical page. The suggestion label therefore limits editorial status, not retrieval influence; neither semantic acceptance nor better retrieval follows from it. See [MEM-OBJ-notes](memory.md#mem-obj-notes) and [EPI-RTE-note-template](epistemic.md#epi-rte-note-template).

### From a question to delivered text

The representative workflow is an interactive subject-question `/ask` in agentic mode. A user supplies the question; code resolves intent, selects evidence tools, ranks page/note matches, expands selected pages and constructs the prompt. The model supplies answer prose, not the next tool choice. The final planner falls back after an unresolved base-function call, so older, richer planner definitions do not establish the active plan. This is sequential local orchestration, not delegated workers or an enclosing autonomous agent runtime. See [RT-RTE-agentic-ask](runtime.md#rt-rte-agentic-ask) and the [workflow account](workflow.md#workflow-account).

The first prompt combines shipped answer guidance, operational self-context, recent conversation and selected source/tool evidence. Selection and truncation intervene between collecting evidence and model visibility. Recent-history Markdown takes up to eight turns and cuts historical answers to 900 characters before its section budget applies. A separate history-tool channel can serialize sanitized full rows, including stored prompts, up to 6000 characters before source allocation and whole-pack trimming. The dedicated history budget and history-token estimate consequently do not bound all historical exposure. Tail trimming preferentially loses later source/tool evidence. These are copied prompt contents, not isolated agent frames or automatically dereferenced file pointers. See [RT-OBJ-context-pack](runtime.md#rt-obj-context-pack) and [RT-CLM-context-budget](runtime.md#rt-clm-context-budget).

For ordinary subject questions, the configured endpoint receives that prompt. Basic operational questions can instead receive deterministic answers. A dry run stops before synthesis and turn recording, but is not a zero-filesystem-effect guarantee: initialization and configuration access can already write state. A blank normalized model answer triggers expanded retrieval and a separately constructed second prompt, then deterministic fallback if needed. The first pack's estimated-text budget does not govern that second prompt. The tool-call setting is also not a strict total-work bound. See [RT-RTE-agentic-ask](runtime.md#rt-rte-agentic-ask) and [RT-CLM-context-budget](runtime.md#rt-clm-context-budget).

Blankness is an availability check, not a factual evaluator. A nonempty false answer can pass. Generic fallback selects source lines, but a distinct readiness-keyword branch can assert that a project is broadly ready for release without requiring supporting pages. This is an implementation-supported counterexample to treating every fallback as extractive evidence summary, not an observed bad answer. By contrast, the context-window diagnostic explicitly withholds an exact native-model-capacity claim. These local differences prevent a single epistemic verdict. See [EPI-RTE-answer-check](epistemic.md#epi-rte-answer-check), [EPI-RTE-fallback-compose](epistemic.md#epi-rte-fallback-compose) and [EPI-RTE-diagnostic-check](epistemic.md#epi-rte-diagnostic-check).

The API returns an answer dictionary; the shell prints a truthy answer regardless of provider `ok` or persistence success. A fallback answer can coexist with first-call failure status. Even when the second request supplies the answer, the recorded and exposed prompt remains the first prompt, so debug visibility is not full replay provenance. Delivery, model success, subject resolution and durable recording are separate outcomes. See [RT-RTE-agentic-ask](runtime.md#rt-rte-agentic-ask) and the [workflow annotation](workflow.md#annotations).

Alternate callers materially change this progression. Release plain ask has a different evidence prompt; direct plain invocation does not itself record, whereas unified dispatch can. One-shot CLI ask uses store retrieval/generation, not the agentic history pack. Store ask accepts model/host/temperature overrides; the release adapter accepts temperature but omits it from its request. MCP dispatch exposes reads, generation, configuration and mutation, but registry membership is not host authorization. The ask nonmutation instruction and code-restricted evidence path are not a product-wide write prohibition; history/config effects remain possible. See [RT-RTE-plain-ask](runtime.md#rt-rte-plain-ask), [RT-RTE-store-ask](runtime.md#rt-rte-store-ask), [RT-RTE-mcp-dispatch](runtime.md#rt-rte-mcp-dispatch) and [RT-CLM-ask-nonmutation](runtime.md#rt-clm-ask-nonmutation).

### From retained turns to later behavior

The strongest supported experience-reuse contribution is an implemented trace-to-durable-context pathway. Automatic history compaction reduces recorded conversations into retained answer excerpts; a separate recursive-context reader can return that archive. Transcript clipping likewise produces indexed pages available for later retrieval. These qualify as automatic trace-fed memory transformations, independently of whether they improve competence. The unresolved question is whether later behavior actually depends on these reductions and becomes better: no execution or intervention comparison establishes that. See [MEM-RTE-history-compaction](memory.md#mem-rte-history-compaction), [MEM-RTE-recursive-context](memory.md#mem-rte-recursive-context), [MEM-RTE-transcript-decision](memory.md#mem-rte-transcript-decision) and [profile verification](profile-verification.md#verification).

Live ask history also affects later work directly: prior questions can change follow-up query resolution, and selected answers can enter later prompts as advisory context, not immutable truth. Compression examines at most 500 live rows, appends shortened older answers to the archive and rewrites live history with a recent tail. Older rows outside that selection can disappear without joining the new archive reduction. Exact prompts and full reasons are not preserved by the reduction. The final agentic pack does not automatically read the compressed archive; its explicit recursive-context tool returns memory to a host without establishing subsequent model delivery. CLI session copies separately support history display after persistence failures, not proven model reload. See [MEM-OBJ-ask-history](memory.md#mem-obj-ask-history), [MEM-RTE-history-compaction](memory.md#mem-rte-history-compaction), [MEM-RTE-recursive-context](memory.md#mem-rte-recursive-context) and [MEM-RTE-cli-history](memory.md#mem-rte-cli-history).

History controls are not comprehensive retention controls. Metrics can independently retain sanitized provider answer/raw-response metadata, including second-pass results, even when history append is disabled, if recording reaches the metrics write. Compaction does not remove those copies. Explicit metrics, usage and self-access tools return recent complete rows; the final pack does not automatically include these diagnostic tools. Thus diagnostic exposure is real wiring, but not normal model-history delivery or exact prompt reconstruction. See [MEM-OBJ-runtime-traces](memory.md#mem-obj-runtime-traces).

Maintenance changes future access without establishing factual acceptance. Structural lint and fixture assertions have bounded evaluators; applied repair changes navigation, not source warrant. Delete/rename changes active pages and reindexes, but does not retract sidecars, provenance, historic prompts, metrics or external copies. Tombstones preserve some bytes, not a general rollback. Configuration controls future endpoint, mode and budgets; documentation consolidation concatenates mapped documents and can archive inputs. Neither establishes autonomous self-modification or improvement. See [EPI-RTE-structure-check](epistemic.md#epi-rte-structure-check), [EPI-RTE-regression-check](epistemic.md#epi-rte-regression-check), [MEM-RTE-page-withdrawal](memory.md#mem-rte-page-withdrawal), [RT-RTE-runtime-config](runtime.md#rt-rte-runtime-config) and [RT-RTE-docs-consolidate](runtime.md#rt-rte-docs-consolidate).

### Assessment and what would change it

For a local corpus question, the supported capability is selected, budgeted evidence delivery with optional model prose and availability recovery. It is not factual acceptance: the inspected active answer/write paths do not establish an evidence-consuming acceptance decision naming a factual criterion, intended use and scope. For conversational continuity, recent-history routing and prompt reuse are wired, while archive use follows a different exposed route. For forgetting or replay, the independent retention surfaces and first/second-prompt mismatch prevent comprehensive guarantees. These are scenario-relative findings, not product rankings.

Trace-fed memory reuse does not establish improved capacity through criticism of a consumed theory. The accepted runtime does not establish a formulated theory route meeting theory-builder conditions 1–4; arbitrary retained prose and delivery are insufficient to assign those conditions positively. Content-directed criticism and retained iterative revision remain unestablished in the named routes. This is not an absence claim about opaque model reasoning. Operational self-context alone also does not establish reflection's two causal directions. Code autonomously performs selected steps after a request, but that does not establish an autonomous theory builder or self-scheduled system. Self-improvement is independently unestablished: the records do not establish objective-responsive determination of an organizational update followed by later operation causally depending on it. These unresolved properties do not negate the positive memory pathways. See [RT-RTE-agentic-ask](runtime.md#rt-rte-agentic-ask), [RT-RTE-runtime-config](runtime.md#rt-rte-runtime-config), [RT-CMP-ollama-model](runtime.md#rt-cmp-ollama-model) and [EPI-RTE-history-reshape](epistemic.md#epi-rte-history-reshape).

Paired traces connecting retained artifacts, actual answer-producing requests and later consumers would establish bounded operation and improve replay assessment. A factual evaluator with a consequential acceptance/rejection consumer would change the acceptance account. Separate comparisons varying history, sidecars or budgeting would be needed to attribute benefit to each. Objective-linked update records plus later dependent operation would be needed for exercised self-improvement; outcome evidence would separately establish success. Tracing schema consumers would narrow the instruction-surface uncertainty. None of these missing results is supplied by test source, command history or a successful write.
