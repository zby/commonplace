# Zikkaron synthesis

## Bounded synthesis

Zikkaron implements persistent memory and context selection for an external conversational host, principally Claude Code. Its strongest supported adaptive contribution is automatic conversion of recorded activity into durable text and selection state that later invocations can consume. This is more than raw-log storage. It is not evidence that those changes improve future task performance. The account covers the whole shipped system at Git revision `dda34a5d903d04ecb5517af214d437873c833302`, with an applicability cutoff of 2026-10-15. Its evidence is static implementation, design statements and attributed outcome claims from SRC-1; no target execution, model response, completed benchmark or causal experiment was supplied. External host processing, dependencies, model artifacts and datasets are outside the frozen source. See the [boundary and Source register](boundary.md#source-register), [RT-RTE-trace-consolidation](runtime.md#rt-rte-trace-consolidation) and [MEM-RTE-maintenance-cycle](memory.md#mem-rte-maintenance-cycle). This synthesis uses accepted member records and makes no additional source reads.

### From host request to retained state

The CLI starts an MCP service, initializes storage and retrieval, launches maintenance and attempts to install host instructions and event hooks. The service decides memory admission, transformation and selection; Claude Code still owns conversational next-action generation, tool choice and interpretation of returned text. Installed prose requests startup recall and task-outcome recording, while installed event commands can launch independent capture and retrieval scripts. Neither installation nor registration proves host execution or compliance. See [RT-RTE-install-integration](runtime.md#rt-rte-install-integration), [RT-OBJ-zikkaron-section](runtime.md#rt-obj-zikkaron-section) and [RT-OBJ-hooks-config](runtime.md#rt-obj-hooks-config).

An explicit `remember` request proposes text, tags and a directory label. A predictive gate can reject it by a numerical novelty policy, with keyword/tag bypasses and a continuity discount. After admission, curation can concatenate a near duplicate, link a related item or create a row. This is computational admission, not a factual judgment or necessarily a human-approved edit. Anchors, project seeds, captured actions and derived maintenance products have different entry paths. Consequently, the claim to store only prediction errors is neither a storage-wide invariant nor a truth guarantee. See [RT-RTE-remember-recall](runtime.md#rt-rte-remember-recall), [MEM-RTE-curation-write](memory.md#mem-rte-curation-write), [RT-RTE-seed-admission](runtime.md#rt-rte-seed-admission) and [RT-CLM-write-gate](runtime.md#rt-clm-write-gate).

SQLite holds readable memory text alongside separate embeddings, graph relations, provenance labels and fixed-code control fields. These parts have different consequences: text supplies context, numerical representations influence similarity, and symbolic fields govern eligibility or priority. Directory and agent labels do not authenticate principals. Local model inference is wired, but exact external weight revisions are unpinned; use-dependent matrices and codebooks are distinct from pretrained models. See [MEM-OBJ-memories](memory.md#mem-obj-memories), [MEM-OBJ-selection-state](memory.md#mem-obj-selection-state), [RT-CMP-embedding-engine](runtime.md#rt-cmp-embedding-engine), [RT-CMP-hopfield-memory](runtime.md#rt-cmp-hopfield-memory) and [RT-CMP-cognitive-map](runtime.md#rt-cmp-cognitive-map).

### Maintenance changes what future work can receive

Post-tool capture records selected action summaries. Maintenance groups actions by directory and time, producing an activity memory only for groups of at least three; fetched smaller groups are nevertheless marked processed. Sensory episodes supply another retained input. Subsequent maintenance can abstract recurring patterns, change importance and relations, compress text, or create synthetic statements and narratives. These are automatic trace-fed writes with later consumers, not evidence of complete activity capture or successful learning. See [RT-RTE-trace-consolidation](runtime.md#rt-rte-trace-consolidation), [MEM-OBJ-episodes](memory.md#mem-obj-episodes), [MEM-RTE-maintenance-cycle](memory.md#mem-rte-maintenance-cycle) and [MEM-RTE-narrative-story](memory.md#mem-rte-narrative-story).

Some checks have real force but narrow scope. Semantic promotion skips a cluster when members differ in lexical negation presence, and can reject duplicate schemas. This veto does not establish semantic consistency or truth of the generated abstraction. Memify can turn weighted co-occurrence into a stronger modified-together assertion; heat-based weight increases mean the threshold need not count actual modifications. Generated conjectures can therefore become ordinary retrievable memories without an established evidence-consuming truth-acceptance decision. This does not establish a system-complete absence of acceptance: named domain, sleep and graph internals remain partly unassessed. See [EPI-RTE-cls-consistency](epistemic.md#epi-rte-cls-consistency), [EPI-RTE-cls-promotion](epistemic.md#epi-rte-cls-promotion), [EPI-RTE-synthetic-facts](epistemic.md#epi-rte-synthetic-facts) and the [epistemic coverage boundary](epistemic.md#source-and-claim-boundary).

Recall itself can revise future memory. After selecting the current response, reconsolidation may append the query to retained text or archive old content and insert the query as a new memory. The latter branch does not disable the original row; a question is not corrective evidence. Usefulness feedback changes confidence and stability rather than independently corroborating facts. File validation checks reference freshness, sometimes returning valid when no file reference exists. These mechanisms change later reliance or selection without warranting the stored propositions. See [MEM-RTE-recall-revision](memory.md#mem-rte-recall-revision), [EPI-RTE-feedback-update](epistemic.md#epi-rte-feedback-update) and [EPI-RTE-file-validation](epistemic.md#epi-rte-file-validation).

### Selection, delivery and recovery are separate routes

Requested recall combines configured retrieval signals, reranking, rules and context packing. Separate prompt/session hooks select retained material without a foreground recall request. Project context, hierarchical recall, story output and prospective reminders add other consumers. The external model receives selected text by value, not a reference preserving a discarded context frame. Zikkaron does not own host-window eviction. Service rules can enforce filtering at their retriever consumer, but direct SQL hooks and replay do not inherit that barrier. See [RT-RTE-context-selection](runtime.md#rt-rte-context-selection), [RT-RTE-hook-context](runtime.md#rt-rte-hook-context), [MEM-RTE-project-context](memory.md#mem-rte-project-context), [MEM-RTE-hierarchy-read](memory.md#mem-rte-hierarchy-read), [MEM-RTE-trigger-delivery](memory.md#mem-rte-trigger-delivery) and [RT-BAP-retrieval-rules](runtime.md#rt-bap-retrieval-rules).

Selection can introduce unsupported assumptions even without changing delivered prose. One optional ranking branch maps a camping mention to an enjoyment assertion; the static counterexample “Alice dislikes camping” demonstrates non-entailment. The inferred passage influences the original memory's rank, not necessarily its displayed content. Profile and belief rows have concrete readers, but ordinary belief-producer invocation was not established. Moreover, synthetic profile/belief dictionaries can lack `heat`, which the service wrapper reads unconditionally. Direct retriever/benchmark consumption remains implemented; reliable structured-result delivery through MCP recall is not established. See [EPI-RTE-inferred-ranking](epistemic.md#epi-rte-inferred-ranking), [MEM-OBJ-derived-beliefs](memory.md#mem-obj-derived-beliefs) and the [report-verification limit](report-verification.md#limits).

For continuity across compaction, drain updates an epoch/checkpoint or creates a placeholder; it does not acquire the host's whole conversation. Restore assembles a global active checkpoint, bounded anchors and recent memories, project material and optional predictions. Micro-checkpoints may retain only a 150-character task label. Global checkpoint replacement and global sections prevent a project-isolation guarantee. Missing hook execution or differing DB paths can split capture from consumption; swallowed errors preserve continuation rather than guarantee recovery. See [RT-RTE-replay-context](runtime.md#rt-rte-replay-context), [RT-RTE-hook-context](runtime.md#rt-rte-hook-context) and [RT-CLM-context-replay](runtime.md#rt-clm-context-replay).

Recovery and withdrawal also depend on the route. One compressor archives originals and respects protection; independent sleep compression lacks those local safeguards. Ordinary consumers do not automatically reload archived reasons. Forget deletes the primary row and selected dependents, but not every separately derived profile, belief, trigger or narrative, nor text already delivered to a host. Thus neither universal protection nor complete semantic retraction follows. See [MEM-RTE-compression-write](memory.md#mem-rte-compression-write), [MEM-OBJ-memory-archives](memory.md#mem-obj-memory-archives) and [MEM-RTE-withdrawal-path](memory.md#mem-rte-withdrawal-path).

### Evaluation and the improvement question

The representative multi-step workflow is the shipped LoCoMo evaluator, not an invented ordinary host task. An operator selects data and settings; Python owns progression. Recorded turns are automatically reformulated into retained rows, retrieval supplies selected dated text to generation, and a separate judge receives the question, gold answer and generated answer. Gold is withheld from the generation handoff. F1 and model judgments feed samples and aggregates, with optional JSON delivery. A wrong answer changes the score, not report eligibility or a repair loop. Generation/judge failures substitute values and continue; other stages lack that same recovery wrapper. See [RT-RTE-evaluation-mode](runtime.md#rt-rte-evaluation-mode), [EPI-RTE-answer-judgment](epistemic.md#epi-rte-answer-judgment) and the [workflow account](workflow.md#workflow-account).

Benchmark preparation itself is another wired trace-to-retained-context pathway: its original inputs are conversational session logs. This positive is independent of whether saved judgments later update production policy, which remains unestablished. Tool-origin updates and compaction-event checkpoint updates are additional distinct pathways. These architectural positives survive the unresolved mixed-origin and library branches; they do not establish observed activation or benefit. See [RT-RTE-trace-consolidation](runtime.md#rt-rte-trace-consolidation), [RT-RTE-replay-context](runtime.md#rt-rte-replay-context), [RT-RTE-evaluation-mode](runtime.md#rt-rte-evaluation-mode) and the [profile verification](profile-verification.md#verification).

Improved capacity for future action remains unestablished at the memory-engine boundary. For the claimed memify self-improvement pathway, the horizon is maintenance cycles followed by later retrieval, and the independent proposed objective is useful future retrieval. State changes and later consumers are wired. Evidence that objective-bearing outcomes determine these updates, followed by subsequent operation causally depending on them, is not established. The four-link exercised self-improvement attribution therefore remains open; the source's label does not close it. No criticism-of-consumed-theory-to-capacity-gain chain is established either. The accepted runtime does not supply a formulated-theory assessment sufficient to assign theory-builder conditions 1–4 separately; none is inferred from storage, rule execution, scores or repeated cycles. Reflection and autonomous theory building likewise remain unestablished as system properties, independently of the code-owned automation already described. See [EPI-CLM-derived-facts](epistemic.md#epi-clm-derived-facts), [EPI-RTE-feedback-update](epistemic.md#epi-rte-feedback-update) and the [bounded epistemic conclusion](epistemic.md#bounded-conclusion).

For a persistent-context scenario, the supported result is plural, adaptive selection of retained material, not exact conversation replay or globally enforced project-local knowledge. For a QA measurement scenario, the supported result is a concrete retrieval/generation/scoring pipeline, not reproduced performance or a component-effect estimate. README outcome claims remain attributed reports, with a disclosed reader-model difference confounding the QA contrast. Host traces linking capture, update and later consumption would establish operation; controlled comparisons holding the reader and data fixed could test capacity gain. Evidence-consuming acceptance records could change the knowledge assessment. Scoped checkpoint selection, shared DB configuration, structured-result normalization and consistent protection/withdrawal handling would change the corresponding architectural limits, but would still require execution evidence for reliability claims. See [EPI-CLM-benchmark-benefit](epistemic.md#epi-clm-benchmark-benefit), [RT-RTE-replay-context](runtime.md#rt-rte-replay-context) and [report verification](report-verification.md#verification).
