# Swamp synthesis

## Bounded synthesis

### From a task to executable automation

Swamp is an agent-facing automation layer, not an enclosing agent inference runtime. It supplies task briefs and skills to external harnesses, then executes the typed behaviors and workflows those agents operate. Its advertised work is reviewable, shareable and accurate operational automation. Reviewability has concrete implementation support; accuracy remains bounded by particular checks rather than demonstrated as a general outcome. The evidence is SRC-1, `https://github.com/swamp-club/swamp`, at commit `380e3c307164501c7d705f7707a864f4612b2785`, with cutoff 2026-10-15. The whole-system functional boundary includes shipped callers, consumers and repository-local improvement workflows. Evidence consists of inspected code and source-native instructions; no target execution or causal experiment was supplied. External harness inference, conversation management, providers and hosted-service implementations are outside the frozen source. See the [boundary and source register](boundary.md#boundary-and-evidence) and [RT-CLM-agent-workflows](runtime.md#rt-clm-agent-workflows).

A launch loads task state, checks launchability and brief ownership, writes the brief, enrolls a harness and opens a terminal. The handoff asks the agent to read one named task and an onboarding skill. The skill directs discovery, creation, validation, target confirmation, execution and output inspection. These are agent instructions, not an enforced conversational state machine. On resume, some harnesses continue the most recent conversation in the folder; Swamp does not establish a task-specific conversation binding or own its compaction policy. [RT-RTE-agent-launch](runtime.md#rt-rte-agent-launch), [RT-BAP-agent-instructions](runtime.md#rt-bap-agent-instructions).

The agent chooses a behavior method and arguments. Swamp resolves the definition, validates method arguments and invokes the implementation with data, vault and execution services. In source-native terminology these are “model” methods, but they need not invoke language models. A symbolic YAML workflow instead gives the scheduler next-step ownership through dependencies, conditions and expressions. Run state is saved before the started event and at material transitions; stored progress supports later continuation. A last-evaluated replay path uses an expanded retained form rather than necessarily re-evaluating current authored source. [RT-RTE-behavior-run](runtime.md#rt-rte-behavior-run), [RT-RTE-workflow-run](runtime.md#rt-rte-workflow-run), [RT-OBJ-workflow-run](runtime.md#rt-obj-workflow-run).

Typed execution is not host containment. Local methods run in the host process, shell methods execute authored commands, and extension import occurs before export validation. Collective allowlisting and registration checks admit capabilities structurally, not as proven-safe code. Remote placement moves method execution to a worker, skips checks requiring worker-local state and rejects rollback-on-failure. A configured approval gate blocks ordinary waiting-run resumption, but parallel siblings may already have acted. Server authorization differs from local caller-supplied approval identity. Thus schema validation, selected preflight checks and optional gates provide local protocols, not universal human consent or rollback of external effects. [RT-RTE-extension-load](runtime.md#rt-rte-extension-load), [RT-RTE-worker-dispatch](runtime.md#rt-rte-worker-dispatch), [RT-RTE-gate-resume](runtime.md#rt-rte-gate-resume), [EPI-RTE-preflight-check](epistemic.md#epi-rte-preflight-check).

### From results to later work

Swamp retains versioned resource/file content, workflow checkpoints, issue resources, reports and selected command events. Local content files and YAML access metadata are distinct; arbitrary payload bytes are not classified by a readable report pointing to them. Resources can contain natural-language guidance and symbolic fields with different consumers. Method argument mismatches reject execution, whereas resource-schema failure warns rather than rejects storage. [MEM-OBJ-data-content](memory.md#mem-obj-data-content), [MEM-RTE-resource-storage](memory.md#mem-rte-resource-storage).

The inspected read-back paths are requests: resource names and versions, CEL predicates/projections, report tags, time windows and explicit continuation. Data query is unlimited by default; count limits are not model-token budgets. A later consumer sees the selected projection, not everything physically retained. Reports deliberately omit argument values, and issue-plan review omits several rationale-bearing fields even though full JSON remains separately queryable. Retention is also conditional: infinite duration does not override finite version history, and cleanup can remove older evidence. These mechanisms support inspectable state reuse, not demonstrated recall sufficiency or automatic context injection. [MEM-RTE-data-query](memory.md#mem-rte-data-query), [MEM-OBJ-method-report](memory.md#mem-obj-method-report), [MEM-OBJ-plan-main](memory.md#mem-obj-plan-main), [MEM-RTE-data-cleanup](memory.md#mem-rte-data-cleanup).

The repository-local issue procedure gives criticism a consequential path. Caller-supplied feedback and revised plan fields are persisted, findings retain descriptions and resolution notes, and later sessions are instructed to query phase and resume the appropriate procedure. A selected local approval preflight checks that plan and review exist, their versions match and no unresolved critical/high finding remains. Those retained fields can veto approval; they do not establish the truth of criticism, actual remediation or conversational consent. The iteration method copies supplied revisions rather than reasoning about incorporation. Its latest-per-name feedback enumeration also fails to reconstruct every historical round. [MEM-RTE-plan-iteration](memory.md#mem-rte-plan-iteration), [MEM-RTE-lifecycle-checks](memory.md#mem-rte-lifecycle-checks), [EPI-RTE-issue-clearance](epistemic.md#epi-rte-issue-clearance), [RT-RTE-issue-admission](runtime.md#rt-rte-issue-admission).

This is not the only lifecycle producer. Report verification found the shipped retroactive `fast_forward` route, which writes a plan, empty adversarial findings, conformance entries and implementing phase for already-completed work. Consequently review existence cannot establish a criticism episode, and not every implementation transition can be assumed to traverse ordinary approval. This limits inventory completeness without invalidating the selected preflight predicate. [Report-verification limit](report-verification.md#limits), [MEM-OBJ-review-findings](memory.md#mem-obj-review-findings).

### Representative delivery: commit review

The joined `verify-reviews` workflow is a concrete multi-step use, not a hypothetical composition of capabilities. Given a commit, setup creates a detached run-keyed worktree, initializes Swamp and restores initialization edits. Change detection obtains a merge-base diff and filename list. Code review runs unconditionally after successful detection; path guards select additional reviewers, with concurrency four. Selected reviewers receive the full diff by pathname, criteria and reachable repository files—not proof that those files were read. Each review launches a separate external Claude process with selected read tools. Only reviewer prose and shell/gate results return through the execution outputs, keeping full review conversations outside the caller's frame. Swamp does not thereby control the provider's context window or pin exact weights. [RT-RTE-review-verdict](runtime.md#rt-rte-review-verdict), [RT-CMP-agent-models](runtime.md#rt-cmp-agent-models), [workflow account](workflow.md#workflow-account).

Pipeline failure or a non-pass parsed result rejects a review step. Recognized provider errors take precedence; otherwise the first matching line-initial pass/fail marker decides, even after a preface or before a contradictory later marker. The parser therefore accepts a protocol, not a reference answer about code quality. Cleanup is best effort. The selected workflow delivers review prose, diagnostics and run outcomes, not a merged change; it has no automatic repair-and-re-review loop. After rejection, the caller owns repair and rerun. [RT-RTE-review-verdict](runtime.md#rt-rte-review-verdict), [workflow account](workflow.md#workflow-account).

Other verification paths have different licenses. Skill evaluations test trigger/guide/tool-choice labels and external review scores; combined-rate acceptance does not imply every phase passes or generated answers are true. Verification summaries reshape recorded outcomes. The aggregate attestation derives a gate from counted step statuses and source count, permitting skips. CI checks subject, gate and supplied hashes, while stale time and missing hashes can be warnings rather than vetoes. These are evidence-relative derivation and operational admission, not semantic acceptance of every code claim or independently authenticated execution. [EPI-RTE-skill-evals](epistemic.md#epi-rte-skill-evals), [EPI-RTE-report-summary](epistemic.md#epi-rte-report-summary), [EPI-RTE-attestation-build](epistemic.md#epi-rte-attestation-build), [EPI-RTE-attestation-ci](epistemic.md#epi-rte-attestation-ci).

### Learning and assessment boundary

The strongest supported learning-related contribution is automatic execution-feedback-to-durable-report production with later report/data consumers. Method and verification summaries provide a wired trace-learning route in the comparison's write-route sense, using tool traces as input. This requires neither new knowledge nor parameter updates. It does not demonstrate improved capacity. Raw audit capture, unchanged checkpoints and nonpersisted activity displays do not automatically establish additional qualifying updates. [MEM-RTE-report-retrieval](memory.md#mem-rte-report-retrieval), [EPI-RTE-report-summary](epistemic.md#epi-rte-report-summary), [profile verification](profile-verification.md#verification).

Retained criticism also has an instructed revision consumer, separate from the revised plan's downstream guidance. Whether criticism of a consumed theory improves capacity for future action remains unestablished: no concrete theory/criticism/revision episode or comparison closes that claim. Theory-builder condition 1 (localized theory content) is not established merely by a plan schema; condition 2 needs content-dependent decisions, not delivery; condition 3 needs a specific challenged claim, blame and changed reliance; condition 4 needs the criticism's result shaping another round. The records do not establish those four conditions for a formulated theory, although recording, revision and clearance capacities are supported. Reflection and autonomous theory building likewise remain unestablished, not evidenced absent. No exercised self-improvement is established at the shipped-system boundary: retained reports, editable capabilities and review gates do not show evidence determining an update to Swamp's own organization followed by later operation causally depending on it. [MEM-RTE-plan-iteration](memory.md#mem-rte-plan-iteration), [epistemic bounded conclusion](epistemic.md#bounded-conclusion), [RT-RTE-extension-load](runtime.md#rt-rte-extension-load).

For repeatable automation, the distinguishing support is symbolic scheduling, typed arguments, provenance and inspectable continuation. For issue work across sessions, it is explicit retained state plus requested reload, qualified by lossy displays and incomplete feedback accumulation. For pre-PR review, it is parallel delegated inspection with a computational rejection protocol, not measured defect detection. Execution traces would establish activation; content-linked criticism and revision episodes could establish theory use; controlled comparisons would be needed for accuracy or capacity benefit. A traced update to Swamp's own live behavior-determining artifacts and subsequent dependent operation could change the self-improvement assessment. These conclusions remain scenario-relative rather than a product ranking.
