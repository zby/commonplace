# MDCP synthesis

## Bounded synthesis

### From request to a documentation contract

MDCP is a repository-based documentation and context system, delivered as an agent skill plus a deterministic compile/check toolchain. This account covers its shipped documentation loop at commit **1a198715a4da72dd89bad93f84cf5d4b3ab56b01**, with analysis cutoff **2026-11-08**. SRC-1 supplies inspected implementation and declared workflows, not an observed agent run or causal experiment. The whole-system functional boundary includes authoring, maintenance, downstream publication and optional maintainer evaluation; it does not imply exhaustive inspection. The external agent host supplies inference, tools, conversational state and scheduling. MDCP's archive/rename notice is in scope, but the successor Merlon Docs is not. See the [boundary and source register](boundary.md#boundary-and-evidence).

The operational starting point is a task interpreted by a host agent, not an MDCP scheduler. The installed skill directs the agent to choose one workflow, discover relevant project documentation through host search or guide indexes, and open one source shard at a time. Vendor skill policy and mutable project shards are separate objects: the former governs the work; the latter retain project intent, contracts and explanations for later work. Their force is interpreted guidance, not filesystem interception or guaranteed compliance. See [RT-OBJ-mdcp](runtime.md#rt-obj-mdcp), [MEM-OBJ-shards](memory.md#mem-obj-shards) and [RT-BAP-skill-host](runtime.md#rt-bap-skill-host).

The representative feature workflow connects intake to delivery in one shipped procedure. The agent scopes a work item, plans commit groups, creates a branch, edits audience-appropriate shards and indexes before product code, implements/tests against that contract, reconciles documentation with as-built behavior, validates and submits for review. Human review is conditional: headless defaults permit reversible work to continue, while destructive work, real scope changes and exclusively human input require stopping. Delivery means review submission, not acceptance, merge, release or deployment. Handoffs are chiefly between phases owned by one agent; optional host isolation does not establish an MDCP-managed worker protocol. See [RT-RTE-feature-work](runtime.md#rt-rte-feature-work) and the [workflow account](workflow.md#workflow-account).

### Selective context, durable content and derived publication

MDCP's context mechanism is selective source reading. One-shard/one-workflow guidance limits requested loading qualitatively; it does not implement cumulative token accounting, eviction, conversational compaction or a child-return schema. An optional host fork can keep work in a separate context, but MDCP does not specify what crosses back. Documents remain available for another explicit search/read; an index link does not itself keep linked content in the model window. See [RT-CLM-context-discipline](runtime.md#rt-clm-context-discipline) and the memory annotation on [RT-RTE-feature-work](runtime.md#rt-rte-feature-work).

There is positive, bounded evidence for the size rationale. The repository's reported static dataset gives a median feature shard of 864 estimated tokens against a 61,941-token monolith: about 1.4% by estimated tokens and 1.5% by characters. This compares one feature shard with that repository's whole monolith, not task-matched alternatives. It supports the conditional claim that reading one shard instead of that monolith can reduce supplied text. It does not measure actual agent selection, total prompt overhead, search cost, recall, task quality or exercised savings. The dataset's date does not establish a measurement run on the frozen commit. See [EPI-OBJ-context-size](epistemic.md#epi-obj-context-size), [EPI-RTE-context-size](epistemic.md#epi-rte-context-size) and [EPI-CLM-context-size](epistemic.md#epi-clm-context-size).

Persistence is primarily Markdown files, normally versioned in Git. Current shards can be replaced or deleted; ADRs preserve superseded decisions, and the research overlay explicitly preserves dated observations while linking evidence to durable positions and then normative clauses. An observation is not itself a rule. These links afford rationale inspection without guaranteeing that a later agent reads the reasons before following a clause. See [MEM-RTE-shard-authoring](memory.md#mem-rte-shard-authoring) and [MEM-OBJ-research](memory.md#mem-obj-research).

Compilation follows a different selector from task relevance: config, manifest links, in-scope transitive Markdown links and directory fallback determine its inputs. It reshapes selected content, rewrites location-dependent links and persists guides/monoliths and a heading registry. The registry has concrete later CLI and site consumers; it is access metadata, not a store of supporting arguments. The compilation-only shard cache is process-local working state, unlike persisted documents or optimizer state crossing later inference invocations. Derived pages and guides are not independent corroboration of their sources. See [RT-RTE-compile-check](runtime.md#rt-rte-compile-check), [MEM-OBJ-compiled](memory.md#mem-obj-compiled), [MEM-OBJ-refs](memory.md#mem-obj-refs) and [MEM-OBJ-shard-cache](memory.md#mem-obj-shard-cache).

### Checking and repair have local authority

The toolchain supplies real mechanical rejection, not general prose-truth acceptance. In `check`, orphan findings reject before compilation. Otherwise outputs and refs can be written before later failures. Repair belongs to the caller; backups and Git are recovery options, not an all-output transaction. A pass covers selected enabled checks: links can be disabled or downgraded to warnings, Vale skipped, optional missing peers tolerated and coverage left non-strict. Direct core calls, mechanical shard import, peer fixes and registered callbacks do not share one universal approval gate. See [RT-RTE-compile-check](runtime.md#rt-rte-compile-check), [RT-RTE-shard-import](runtime.md#rt-rte-shard-import), [MEM-RTE-peer-fix](memory.md#mem-rte-peer-fix) and [RT-RTE-hook-extension](runtime.md#rt-rte-hook-extension).

Some checks do evaluate narrow truth-apt propositions. The optional path probe tests recognized path existence under specified roots and exemptions; it does not assess file behavior. The code-evidence hook derives a first lexical occurrence location, which can point to a comment before a declaration; existing line fragments are preserved rather than verified. Insert expansion imports text without accepting its truth. Arbitrary callbacks and external peer mutations prevent generalizing default assembly's reshaping behavior to every transformation. See [EPI-RTE-path-probe](epistemic.md#epi-rte-path-probe), [EPI-RTE-code-evidence](epistemic.md#epi-rte-code-evidence) and [EPI-RTE-inline-inserts](epistemic.md#epi-rte-inline-inserts).

Semantic checking is prescribed separately. Review signals direct attention to sprawl; the host workflow chooses merge, split, move, reword, link, delete or leave, with a reason. Research guidance requires method, scope and caveats, and disclosure when a clause lacks evidence. These are evidence-sensitive prescriptions, not inspected instances of accepting a particular novel claim or integrating it after acceptance. CI can reject selected failures and generated-output diffs, but deployed mandatory merge protection and successful release remain unverified. See [RT-RTE-doc-review](runtime.md#rt-rte-doc-review), [EPI-CLM-research-warrant](epistemic.md#epi-clm-research-warrant) and [RT-RTE-release-admission](runtime.md#rt-rte-release-admission).

### Feedback changes candidates before it changes production

The strongest supported learning-related contribution is a wired, bounded maintainer feedback loop. The vendored trigger optimizer compares Claude-subprocess skill invocation against expected labels, retains failures/scores/history, requests revised descriptions and uses candidates in later evaluations. This is automatic trace-fed revision of retained behavior-shaping text, not merely log archival. The next inference inputs receive candidate and feedback state automatically; ordinary project-shard reads remain requested pulls. Trigger agreement is the evaluated objective, not successful task execution or prose truth. Test fields are hidden from proposal history, but selecting the best candidate using test scores means that set is not an untouched final evaluation. The returned description still requires a separate author action to update production frontmatter. See [RT-RTE-skill-evaluation](runtime.md#rt-rte-skill-evaluation) and [EPI-OBJ-skill-description](epistemic.md#epi-obj-skill-description).

The following properties therefore remain distinct:

- **Theory-builder conditions 1–4:** doc-review guidance supports claimed localized rules and requested content-dependent use (conditions 1 and 2), while completed content-directed criticism and retained criticism shaping another round (3 and 4) remain uninspected. The optimizer affords localized candidate policy, wires its delivery and candidate/result reuse, but scores and revision requests do not establish formulated criticism with blame or criticism-led iteration. It does not establish all four conditions.
- **Improved future capacity through criticism:** no comparison establishes that criticism of consumed guidance improved capacity. Wired feedback-driven revision is a supported partial contribution, not demonstrated learning benefit.
- **Reflection:** the optimizer wires a bounded feedback capacity representing trigger outcomes and affecting the next evaluated description. Exercised production reflection is not established. Recurrence-driven changes to review thresholds, glossary or Vale rules are prescribed, not observed.
- **Autonomy:** computation proposes and selects within the bounded optimizer, but autonomous theory building or autonomous end-to-end production revision is not established. The separate installation decision remains outside automatic selection.
- **Self-improvement:** candidate changes can reach later evaluation inputs, but no supplied execution establishes exercised evidence-responsive organizational change and subsequent behavior causally depending on it. Production installation and its downstream causal effect are additionally unobserved. No exercised production self-improvement or successful improvement is attributed.

These assessments follow the separate property findings in [RT-RTE-doc-review](runtime.md#rt-rte-doc-review) and [RT-RTE-skill-evaluation](runtime.md#rt-rte-skill-evaluation); missing outcome evidence does not erase their inspected capacities.

For a task requiring small, durable project contracts and reproducible publication, the supported design is selective host reads plus deterministic derivation and conditional checks. For a task requiring enforced context limits, reliable recall, accepted research conclusions or autonomous semantic repair, this evidence does not establish those guarantees. Recorded task traces linking shard selection, edits, checks and later consumption would change the exercised-workflow assessment. A task-matched context comparison would address savings and quality; a retained criticism/revision/next-round chain would address theory building; installation and subsequent causal-use evidence would address production self-improvement. Broader guarantees would also require controls covering the alternate write/read routes, rather than stronger wording about the ordinary protocol. The [report verification](report-verification.md#verification) and [profile verification](profile-verification.md#verification) retain no blockers or additional declared limits; the scoped evidence gaps below remain.
