# JEPA-Anything synthesis

## Bounded synthesis

### From task intent to a candidate contract

JEPA-Anything is a model-assisted **task-design builder**, not an enclosing agent runtime or a trained world-model service. Its shipped Skill asks a host model to convert a user's world-model intent into a configuration and inspectable code skeleton. The host supplies inference, project inspection, tool execution and next-step decisions. Python tools check declarations and render interfaces; the numerical library supplies reusable tensor operations. This account covers the shipped Skill, validator, generator, generated consumers, numerical support, synthetic recipe and checkpoint verifier at commit `c6e6c88f3ef75a4ce7acd660d6fa5779d995512c`, with cutoff 2026-10-15. The sole source, SRC-1, supplies implementation and doctrine/design evidence. No target execution, host trace or causal experiment supports this run. See the [boundary and Source register](boundary.md#boundary-and-evidence) and [EPI-CLM-world-model-compiler](epistemic.md#epi-clm-world-model-compiler).

For a representative history-to-future rollout task, the host is instructed to establish the system instance, available history and actions, target horizon and intended consumer. It should recover facts from the project before questioning the user. Unrecoverable facts that could change the task or introduce target leakage require clarification; JEPA-specific architecture choices instead remain the host's proposal responsibility. Rollout intent selects the `repeated_transition` interface. Provisional choices and a task summary belong in compiler assumptions, not in a claim of measured success. This is a source-defined workflow, not an observed conversion: [RT-RTE-task-compilation](runtime.md#rt-rte-task-compilation), its [workflow annotations](workflow.md#annotations), and [MEM-OBJ-compiler-assumptions](memory.md#mem-obj-compiler-assumptions).

The host receives natural-language methodology and produces a symbolic configuration. The latter describes causal inputs, architecture, dimensions, losses, baselines, audits, use mode and planned comparisons. Planned claims must remain planned. Neither task declarations nor proposed defaults acquire empirical warrant merely by entering this mapping. Without a concrete task/design trace, the analysis cannot determine which proposed statements are faithful imports, entailed consequences or conjectures. See [RT-OBJ-design-protocol](runtime.md#rt-obj-design-protocol), [RT-OBJ-design-config](runtime.md#rt-obj-design-config), [EPI-OBJ-claims](epistemic.md#epi-obj-claims) and the [epistemic route assessment](epistemic.md#authority-route-ledger).

### Deterministic criticism, admission and delivery

The validator returns diagnostic codes, paths, messages, counts and a validity bit. The Skill asks the host to repair every error and repeat validation. The validator supplies fixed declaration predicates, not an oracle for the best architecture or an implemented model-repair scheduler. The host owns revision; mandatory per-field human approval is not part of the requested loop. This separation is supported by [EPI-RTE-design-diagnostics](epistemic.md#epi-rte-design-diagnostics) and [RT-RTE-task-compilation](runtime.md#rt-rte-task-compilation).

The generator CLI independently validates its input before rendering. A valid report admits a declared-complete design for skeleton generation; it does not accept scientific claims. Skipping standalone validation does not bypass this CLI check. However, the direct Python renderer accepts a supplied report without revalidating or requiring its validity. The guarantee is therefore CLI-specific, not universal. Both paths check destination availability; a non-empty destination is refused. Rendering uses a temporary sibling directory and cleans it on exceptions, but supplies neither versioned rollback after promotion nor a concurrent-writer or filesystem-isolation guarantee. See [RT-RTE-scaffold-admission](runtime.md#rt-rte-scaffold-admission).

Rendering transfers selected configuration fields into literals in fixed templates and saves the normalized configuration, validation feedback, generated code/documentation and file list. This specializes declarations rather than adding scientific support. Later imports and invoked functions consume the executable constants. Copied assumptions remain inspectable, but their retention does not establish a later model reader of their meaning. The feedback and file list likewise do not inherit executable authority from sharing a directory with code. See [EPI-RTE-template-specialization](epistemic.md#epi-rte-template-specialization), [RT-OBJ-scaffold-manifest](runtime.md#rt-obj-scaffold-manifest), [RT-BAP-generated-contract](runtime.md#rt-bap-generated-contract) and [MEM-OBJ-compiler-assumptions](memory.md#mem-obj-compiler-assumptions).

The requested next step is generated contract testing, followed by a user handoff explaining the task-to-design mapping, paths, validator result, use mode, adapter/encoder proposal, dimensions and unresolved assumptions. Tests use fabricated values and callbacks; the adapter remains a stub and the model an interface protocol. Generator completion is an intermediate result, not evidence that tests passed or that the host delivered the requested account. The source supplies no implemented delivery gate tied to test success or specific failed-test recovery procedure. These distinctions are retained in the [workflow account](workflow.md#workflow-account) and its annotations on [RT-RTE-task-compilation](runtime.md#rt-rte-task-compilation).

### What later execution can rely on

Generated contracts have real but local force. Mode constants select terminal readout, factor analysis or repeated transition. The dispatcher calls caller-supplied callbacks and, for rollout, returns selected horizon states. It checks required exogenous inputs step by step, but does not require the separate geometry, activity, capacity or claim-envelope helpers before callback execution. Callback effects are not sandboxed or rolled back; an earlier callback may already have run when a later step fails. Horizon entries are not copied snapshots if a callback mutates and returns the same object. See [RT-RTE-state-consumption](runtime.md#rt-rte-state-consumption) and its [memory annotation](memory.md#annotations).

The audit helpers distinguish several kinds of conformity. Claim-envelope checks compare result metadata with planned comparisons; activity, capacity and geometry helpers test caller-supplied numerical envelopes. Invoked exceptions can stop that caller, but passing does not authenticate measurement origin or establish statistical support. Generated tests can satisfy the envelope by copying planned metadata. In contrast, core numerical audits actually compute tensor rank, conditioning and reconstruction properties. Their conclusions are stronger about those inputs, but remain numerical, not evidence of predictive quality or semantic factors. See [EPI-RTE-evidence-envelope](epistemic.md#epi-rte-evidence-envelope), [EPI-RTE-measurement-checks](epistemic.md#epi-rte-measurement-checks), [EPI-RTE-numerical-audits](epistemic.md#epi-rte-numerical-audits) and [RT-CLM-validation-scope](runtime.md#rt-clm-validation-scope).

Repository evaluators do not bridge that evidential gap. The synthetic recipe computes activity from oracle state coordinates rather than learned encoders. The current checkpoint manifest describes an unpublished fixture with no payload or executed training. Its future published-file branch checks locally staged bytes and metadata, not model quality, downloading or loading. Make/CI consumes check statuses, but no successful run is supplied. See [RT-RTE-structural-checks](runtime.md#rt-rte-structural-checks) and [MEM-OBJ-checkpoint-manifest](memory.md#mem-obj-checkpoint-manifest).

### Retained history and independent improvement properties

The strongest supported feedback contribution is a requested chain from validator execution feedback through host repair to a retained design and later-consumed generated contracts. The [profile verification](profile-verification.md#verification) accepts this as **claimed trace learning** in the limited sense of feedback-fed durable artifact revision. It is not observed beneficial learning, revised Skill methodology or compiler self-improvement. The unresolved question is whether this chain operates reliably and improves future capacity, rather than merely changing an external product. No comparison establishing that benefit was performed. Its supporting routes are [RT-RTE-task-compilation](runtime.md#rt-rte-task-compilation), [EPI-RTE-design-diagnostics](epistemic.md#epi-rte-design-diagnostics), [RT-RTE-scaffold-admission](runtime.md#rt-rte-scaffold-admission) and [RT-BAP-generated-contract](runtime.md#rt-bap-generated-contract).

There is also genuine implemented numerical history. Welford count, mean and M2 summarize previous factor batches and enter a later differentiable activity penalty; reset forgets all history. EMA updates retain mixtures of encoder state for later target encoding. Learnable projection rows can change through external optimization and explicit scheduled QR retraction; configuring retraction alone does not schedule it. These afford adaptation but establish no executed optimizer, durable numerical reload or improved prediction. Sample origins and original encoder training remain unresolved. Host session memory, compaction and context budgeting remain external. See [MEM-OBJ-online-variance-tracker](memory.md#mem-obj-online-variance-tracker), [MEM-RTE-streaming-monitor](memory.md#mem-rte-streaming-monitor), [MEM-CMP-target-encoder](memory.md#mem-cmp-target-encoder) and [RT-RTE-core-projection](runtime.md#rt-rte-core-projection).

The runtime's theory assessment keeps each property separate. For the host compilation route, condition 1, localized theory content, is **afforded** by inspectable method statements and equations. Condition 2, content-dependent consumption, is **claimed**, not observed. Condition 3, content-directed criticism and revision, is **claimed** through diagnostic repair, without an observed trace of blame attribution. Condition 4, retained criticism shaping another round, is **claimed** through requested revalidation. Criticism of the consumed methodology improving future capacity is unestablished. Reflection is not established: the represented subject is the external task, not an evidenced feedback-controlled self-representation of this compiler. Autonomous theory building is unestablished despite requested computational proposal and repair. At this builder boundary, exercised self-improvement is also unestablished: no supported chain shows feedback changing the compiler's own organization and subsequent operation causally depending on that change. These are independent findings, not a ladder or a single verdict. See [RT-RTE-task-compilation](runtime.md#rt-rte-task-compilation).

For the scenario of producing an inspectable implementation contract, the supported contribution is a declared host workflow backed by executable declaration gates, fixed-template generation and local interface checks. For the different scenario of obtaining a trained or scientifically supported world model, those outputs are insufficient. A pinned host trace connecting request, diagnostics, revisions, generated files, tests and handoff would change the operation assessment. Provenance-linked measurements and held-out task evaluations would change the performance assessment; controlled interventions would be needed to isolate component effects. A retained-method update consumed in later compiler operation would be necessary to reassess self-improvement, independently of whether the external design improved. No additional source reads were made for this synthesis.
