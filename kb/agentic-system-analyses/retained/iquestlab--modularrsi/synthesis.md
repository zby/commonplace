# ModularRSI synthesis

## Bounded synthesis

### An improvement plane with its own downstream solver

ModularRSI wires execution experience to changes in its own executable harness. Its strongest supported contribution is a complete implementation path from selected task evidence through isolated editing and admission to a generation that later solver tasks can consume. This establishes improvement-directed self-change capacity, not that a particular edit improved future capacity or caused a later success. The product is a Python strategy library, not updated foundation-model weights. See [RT-RTE-generation-change](runtime.md#rt-rte-generation-change) and [RT-OBJ-module-library](runtime.md#rt-obj-module-library).

The evidence is SRC-1, the IQuestLab/ModularRSI repository frozen at **b5c72c36b0d08ff93f00ee202a8fbdebe849dfb9**, with an applicability cutoff of **2026-10-18**. The whole-system functional boundary includes the improvement drivers, their retained state, candidate gates, solver, and supporting Harbor execution paths. It is not an assessment of Harbor as a separate product. The accepted reports are code-grounded accounts of implementation and shipped instructions. No target code, tests or model calls were executed, and individual bundled evaluation trials were not inspected. Available sanitized evaluation artifacts are not a full training history. External provider internals and unfrozen task contents remain outside the evidence; available but unread variants and trials are not access failures. See the [boundary and Source register](boundary.md#boundary-and-evidence).

The README reports accuracy and transfer gains, including Terminal-Bench accuracy moving from 47.57% to 52.43% for its stated model. Those numbers remain attributed source reports, not independent measurements or component-effect estimates from this analysis: [RT-CLM-harness-improvement](runtime.md#rt-clm-harness-improvement).

### From configured support tasks to proposed interventions

An operator supplies model access, support tasks, resource settings and a module lock, then starts evolution. Phase0 hands this bounded curriculum to the online driver. The driver snapshots the installed library, initializes or resumes generation state, and launches task groups using a captured generation. Initial dynamic composition selects five slots—agent loop, observation, context management, tools and verification—and an optional helper subset. Later rolls can replay the first bundle. The dynamic composer judges task text against filtered module descriptions without verifier rewards; software validates the returned names. Descriptions are model-interpreted capability claims, whereas the chosen implementations are executable policy. Static, cached and forced selection are distinct alternatives. See [RT-RTE-bundle-selection](runtime.md#rt-rte-bundle-selection) and [RT-BAP-description-selection](runtime.md#rt-bap-description-selection).

The selected loop owns solver progression. In the baseline, model output supplies commands, software parses them, tools execute terminal actions or helper callbacks, observations return to chat, and the selected verification strategy decides when interaction ends. The baseline's repeated model completion signals are not independent correctness checks. Harbor subsequently runs the task-provided verifier and returns reward or error. That reward supplies the reference outcome used by evolution; its adequacy remains bounded by the external task tests. See [RT-RTE-solver-task](runtime.md#rt-rte-solver-task).

Completed groups trigger background reflection while solver launches continue. A window can therefore contain evidence from earlier generations; shared task identity does not create a controlled experiment. Investigators receive selected summaries, permitted trajectories and staged code in separate sessions. The requested diagnosis compares passing and failing attempts where available and asks whether a concrete module intervention would plausibly change the outcome. This is an ampliative causal conjecture: the proposed intervention was not applied in those unchanged-code comparisons. The implementation establishes that the question is asked, not that actual generated explanations are sound. See [EPI-OBJ-contrast-finding](epistemic.md#epi-obj-contrast-finding) and [RT-RTE-generation-change](runtime.md#rt-rte-generation-change).

Findings and proposals retain those reasons across windows. Model responsibility, intervention-equivalence and successor-coverage judgments govern organization of proposed work; symbolic dispositions, support counts, attempts and leases govern eligibility, priority and recovery. These are not acceptance of the causal diagnosis as true. Software can select still-open proposals later, but a retryable unattached finding is merely nonterminal: the inspected online caller does not schedule its resupply. Historical passing-trial pointers can reconstruct earlier contrast evidence if the referent survives and still passes. See [MEM-RTE-evidence-brief](memory.md#mem-rte-evidence-brief), [EPI-RTE-finding-disposition](epistemic.md#epi-rte-finding-disposition) and [MEM-RTE-history-contrast](memory.md#mem-rte-history-contrast).

### Isolated builds, bounded checks and delivery

The representative workflow is one two-lane evolution window, not a reconstructed successful training episode. Software selects up to one incumbent and one novelty proposal; a lane may remain empty. Each editor receives only its assigned proposal, causal hypothesis and supporting finding displays in an independent staging tree from the same parent. Missing evidence is disclosed, and each finding display is capped at 6000 characters. Full investigator histories do not merge into editor context. See the [workflow account](workflow.md#workflow-account) and [MEM-RTE-evidence-brief](memory.md#mem-rte-evidence-brief).

Candidate admission checks committed edits, smoke/static contracts, action shape and niche, model review, required variant identification, and forced activation/crash sanity. These stages have different licenses. A substantive structured reviewer acceptance is an evidence-consuming, fallible judgment that the executable proposal is worth trying in the bounded experiment, considering trajectory-linked mechanism and task-specific overfit. An explicit rejection can veto. However, reviewer timeout or exception passes as skipped; missing verdicts can initially pass before breaker handling. Sanity-crash repair can subsequently alter reviewed bytes without renewed review/action/niche stages. There is no invariant that a reviewer approved every promoted final tree. See [EPI-RTE-review-decision](epistemic.md#epi-rte-review-decision) and [RT-RTE-generation-change](runtime.md#rt-rte-generation-change).

Forced sanity establishes required activation and checks classified code breaks. Task failure or infrastructure timeout alone need not reject a candidate, parent reward is reference logging rather than an admission threshold, and the ordinary-routing probe never gates. Passing therefore means neither reward superiority nor likely ordinary selection. A reviewer-classified implementation defect can instead trigger one fresh build from the parent with a repair brief; rejection of the direction does not earn that branch. Preparation failure and started work have different lease/attempt consequences. These are implemented criticism-delivery and recovery mechanisms, not observations of correct criticism or successful recovery. See [RT-RTE-generation-change](runtime.md#rt-rte-generation-change) and the [workflow account](workflow.md#workflow-account).

Passing lanes can become numbered generations. If both pass, the default order promotes the incumbent first and rebases the second; conflicts reject it, while successful rebases rerun tree-dependent checks. Filesystem promotion and archive synchronization are not one transaction: sync failure leaves the generation standing. Delivery means the driver receives the new generation path and uses it for later launches, not that already-running tasks switch implementations. Evaluation-only invocation loads a selected frozen library without running this improvement loop. See [RT-RTE-generation-change](runtime.md#rt-rte-generation-change) and [RT-RTE-solver-task](runtime.md#rt-rte-solver-task).

The retained library has direct Python authority. Discovery imports eligible files before ordinary variant selection, and selected factories and methods subsequently control solver behavior. Editor path and module-lock guards mediate supported file actions; they do not sandbox imported candidate Python. Task-environment isolation does not establish isolation of local candidate imports. See [RT-BAP-module-execution](runtime.md#rt-bap-module-execution).

### What persists and what later reliance means

The principal durable behavior artifact is executable code. Findings and causal hypotheses supply upstream reference and editing guidance; eligibility metadata supplies fixed-rule routing, ranking and vetoes; descriptions inform composition. Historical reasons survive separately in backlog state and need not accompany code into solver context. Journals and manifests must not be conflated with those live consumers. The editor-memory formatter exists, but the searched shipped callers establish no compact-history invocation or evolution-log injection into editors. The boundary's ambiguous description of editor use therefore supports no joint inference of automatic journal delivery. See [MEM-OBJ-proposal-record](memory.md#mem-obj-proposal-record), [MEM-BAP-backlog-control](memory.md#mem-bap-backlog-control) and [MEM-ABS-editor-readback](memory.md#mem-abs-editor-readback).

Outcome confirmation provides another real adaptation route. It computes candidate-versus-baseline pass-rate differences on recorded shared tasks and can mark regressors superseded, affecting ordinary later dynamic selection. Defaults require at least three shared tasks and a deficit exceeding 0.34. This arithmetic does not independently vary components or establish transfer. Retirement is best-effort selection withdrawal, not file deletion or universal revocation of static/cache/forced paths. Confirmation consumes task/bundle/reward tuples; their granularity does not establish the richer linked-trajectory source used by diagnosis. See [EPI-RTE-paired-confirmation](epistemic.md#epi-rte-paired-confirmation) and [MEM-OBJ-archive-entry](memory.md#mem-obj-archive-entry).

Within a solver task, compression is also a retained-context route: budget/overflow rules trigger model summary, questions and answers that reach a later invocation. Tail message pairs can be removed before summarization, so neither summary labels nor saved trajectory references guarantee complete evidence or automatic reload. Installed and released baseline fallback behavior differs. Observation clipping and bounded scrollback impose further limits; editor file/range reads offer a separate request-driven reload capability. Optional solver skill-catalog injection remains an incomplete instruction-discovery inventory, not an established learned-memory route. See [RT-RTE-context-handoff](runtime.md#rt-rte-context-handoff), the [memory annotations](memory.md#annotations) and the [report-verification limit](report-verification.md#limits).

Under the memory comparison's write-route criterion, diagnosis-to-code, automatic continuation production and outcome-fed archive revision qualify as wired trace learning. That term identifies automatic trace-fed retention with a later behavior-shaping consumer, not demonstrated improved capacity. At the next inference call, a QA handoff supplies context and guidance, not an evidenced parameter update. Initial provenance, additional strategy mechanisms, provider state and unestablished receiving consumers keep comparison coverage partial. See [profile verification](profile-verification.md#verification) and [MEM-RTE-evidence-brief](memory.md#mem-rte-evidence-brief).

### Independent property assessments and what would change them

At the builder-plus-solver boundary over successive task launches, the following assessments remain separate. Their supporting account is [RT-RTE-generation-change](runtime.md#rt-rte-generation-change), with the review-specific mechanism in [EPI-RTE-review-decision](epistemic.md#epi-rte-review-decision).

| Property | Supported assessment | Unresolved question |
|---|---|---|
| Theory-builder condition 1: localized content | Afforded through hypothesis/delta fields and named whole strategies. | Actual formulated theory content was not inspected. |
| Condition 2: consumption | Wired: hypothesis content is explicitly supplied in implementation/review decisions. | Actual semantic dependence and model compliance remain uninspected. |
| Condition 3: content-directed criticism | Afforded through counterfactual diagnosis and proposal-versus-implementation blame. | No actual sound content-directed criticism was inspected. |
| Condition 4: iteration | Wired through retained support, later briefs and bounded criticism-fed rebuilds. | Actual iterative criticism of a formulated theory remains uninspected. |
| Learning as improved future capacity | A retained evidence-to-code-to-later-consumer path exists. | Whether criticism of a consumed theory improved capacity, and its cause, remain uninspected. |
| Reflection | Wired: represented bundles, actions and outcomes can mediate later harness revision. | Accurate self-diagnosis and observed exercise remain uninspected. |
| Reflective theory builder | Uninspected. | The evidence does not establish criticism and revision of the investigative/editor method texts themselves. |
| Autonomous theory builder | Afforded within the configured curriculum: computation supplies diagnosis, selection, editing, review and promotion. | Reliable performance of every internal theoretical operation is not established. |
| Self-improvement | Dispositional improvement-directed self-change is wired for task success, with efficiency secondary. | Link 4—subsequent operation causally depending on a particular edit—is uninspected; exercised self-improvement and successful improvement are unestablished. |

For the scenario of a configured support-task experiment, the system supplies a live, evidence-responsive harness-change architecture with bounded admission and recovery. For the scenario of frozen downstream evaluation, it supplies a selected executable product, not continuing improvement. Neither scenario's implementation alone establishes causal gains. An inspectable evolution episode linking evidence, criticism, exact admitted bytes and later change-dependent operation would alter the exercised-path assessment. Matched outcome comparisons could establish benefit at the treatment granularity actually varied; individual module attribution needs independent variation of that module. Fail-closed substantive review, review renewed after repair, revision-bound replay and stronger execution isolation would change the corresponding architectural guarantees rather than retroactively establish past success. See [RT-RTE-generation-change](runtime.md#rt-rte-generation-change), [RT-RTE-bundle-selection](runtime.md#rt-rte-bundle-selection) and [RT-BAP-module-execution](runtime.md#rt-bap-module-execution).
