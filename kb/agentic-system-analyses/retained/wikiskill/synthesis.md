# WikiSkill synthesis

## Bounded synthesis

WikiSkill implements an experience-to-instruction adaptation loop: retain task outcomes, ask a Maintainer for reusable Wiki lessons, ask a separate Proposer for revised instructions, and let software decide whether those instructions replace the incumbent. Its strongest supported contribution is this persistent, evaluator-gated path from experience to later instruction delivery, including trace-fed updates on inspected research paths. Whether the delivered changes improve future capacity remains unestablished. WikiSkill changes text and control state, not the external models' weights ([RT-RTE-product-round](runtime.md#rt-rte-product-round), [MEM-OBJ-research-evidence](memory.md#mem-obj-research-evidence), [RT-BAP-skill-consumption](runtime.md#rt-bap-skill-consumption), [RT-CMP-host-model](runtime.md#rt-cmp-host-model), [RT-CMP-research-model](runtime.md#rt-cmp-research-model)).

This is a code-grounded analysis of the independent implementation at `https://github.com/Stahl-G/WikiSkill`, commit `da6984caca09d5f81b2336cf3067b59c0c18bb1e`, with an applicability cutoff of 2026-10-15. SRC-1 supplies implementation, doctrine and attributed operation; no target execution, tests, provider calls or fresh experiments were performed. The whole-system functional boundary includes product CLI/MCP, native handoffs, feedback comparison, research controllers, role assets and deployment. It does not freeze the host's subagent machinery, model services, arbitrary user evaluators, BriefLoop or the original paper implementation. Whole-system scope is not complete behavioral inspection: additional callable research controllers remain incompletely characterized ([boundary and evidence](boundary.md#boundary-and-evidence), [Source register](boundary.md#source-register), [report-verification limits](report-verification.md#limits)).

### From a recurring task to recorded experience

The ordinary product is a host-driven controller, not an enclosing agent runtime. The user and foreground coordinator choose examples, criterion, starting skill and budget. WikiSkill fixes workspace conditions, issues requests and reconstructs progress from a hash-linked event journal. The host chooses inference and tools, executes requests and supplies results. CLI and MCP reach the same product functions. Research execution differs: the evolution engine and isolated Spreadsheet study launch Codex through their own execution paths ([RT-OBJ-product-journal](runtime.md#rt-obj-product-journal), [RT-RTE-product-round](runtime.md#rt-rte-product-round), [RT-RTE-research-evolve](runtime.md#rt-rte-research-evolve), [RT-RTE-isolated-study](runtime.md#rt-rte-isolated-study)).

The representative source-supported workflow is baseline validation → training → maintenance → proposal → candidate validation → retained result. It connects the ordinary request to both persistent lessons and a separately selected successor. Tasks must finish before maintenance; maintenance commits before proposal. In native mode, WikiSkill stages role instructions and payloads, the host creates a fresh child, and the coordinator binds its returned ID, waits and collects a result-file pointer. Executors receive the filtered task and selected skill, not the learning Wiki or saved baseline answers. Fresh context is a host protocol, not attested filesystem isolation: privileged host tools may reach other workspace files. Direct APIs also do not inherit every containment check of native collection ([workflow account](workflow.md#workflow-account), [RT-RTE-native-handoff](runtime.md#rt-rte-native-handoff)).

Task outputs, optional traces and score/feedback rows persist separately from journal integrity metadata. A configured scorer receives the full task, including reference information, and saved output; without one, the caller supplies a finite score. Authorization fingerprints the scorer's direct files, not every imported dependency, and the scorer runs with normal host permissions. Score validation therefore establishes admissible numeric input, not a truthful or valid evaluator. Journal checks establish local consistency against recorded hashes, not protection against a writer changing both content and metadata ([MEM-OBJ-experience](memory.md#mem-obj-experience), [RT-RTE-product-round](runtime.md#rt-rte-product-round), [RT-OBJ-product-journal](runtime.md#rt-obj-product-journal), [RT-CLM-mcp-separation](runtime.md#rt-clm-mcp-separation)).

### From experience to Wiki, then to a candidate

Product maintenance receives completed current-round training records, all current patterns, original feedback, incumbent skill and gate history. It admits named lessons with nonblank content and source IDs drawn from training, feedback or existing patterns. This preserves local lineage, including lesson-to-lesson derivation, without checking that a lesson follows from its sources. Pattern retention precedes skill evaluation. Reusing a name replaces its current value; old journal versions remain. Product-generated Markdown is a view: later authoring contexts consume replayed mappings, not edited page bytes ([MEM-OBJ-patterns](memory.md#mem-obj-patterns), [MEM-OBJ-feedback](memory.md#mem-obj-feedback)).

The Proposer receives the committed Wiki and returns a full nonempty skill or `no_action`. Instructions request applicability, exclusions, concrete procedures, evidence and counterexamples. Product admission does not semantically validate those features or authenticate computational authorship. No separate human decision approving each pattern or candidate is required. Wiki content supplies evidence and guidance to learning authors; skill text supplies instructions to task executors under existing host policy, not additional permissions ([MEM-OBJ-skill](memory.md#mem-obj-skill), [MEM-BAP-wiki-authors](memory.md#mem-bap-wiki-authors), [RT-BAP-role-guidance](runtime.md#rt-bap-role-guidance), [RT-BAP-skill-consumption](runtime.md#rt-bap-skill-consumption)).

Research uses a distinct Markdown Wiki, selected execution views and impact records. Default maintenance samples up to five failures and three successes, supplies stdout/event tails and the Wiki snapshot, and stages fuller evidence for optional reads. Default proposal stages up to twelve eligible traces and supplies index/impact summaries. Paper-style views middle-trim long traces; study reference feedback is paged. These are bounded context selectors, not lossless delivery or demonstrated foreground-chat compaction. Automatic bundles coexist with model-requested exact-file reads. Product context has no inspected token cap ([MEM-OBJ-research-evidence](memory.md#mem-obj-research-evidence), [MEM-OBJ-research-wiki](memory.md#mem-obj-research-wiki), [memory read-back](memory.md#read-back)).

Reasons can survive as original notes, source links, Wiki narratives, purposes, proposal rationale and gate history without reaching every later consumer. Native numeric history omits candidate bodies and notes. Default research proposal gets a shortened impact rendering with fuller files optionally available. Paper mappings retain named SKILL/PURPOSE pairs, but task injection joins only SKILL bodies. Structural patch and trace-read checks constrain editing and evidence access; they do not establish comprehension, semantic fidelity or explanatory criticism. The paper adapters require injected invocation transport; default CLI activation is not established ([MEM-OBJ-skill-impact](memory.md#mem-obj-skill-impact), [MEM-OBJ-paper-skills](memory.md#mem-obj-paper-skills), [MEM-RTE-paper-adapters](memory.md#mem-rte-paper-adapters), [EPI-RTE-paper-contract](epistemic.md#epi-rte-paper-contract)).

### Selection, recovery and delivery

Admission depends on the operating mode, not a universal improvement rule:

- **Numeric product:** candidate mean score must improve on the incumbent by strictly more than the configured direction-adjusted threshold. Baseline and candidate reuse validation cases; this is not an independent held-out generalization result ([RT-RTE-product-round](runtime.md#rt-rte-product-round)).
- **Feedback-first:** ordinary feedback requires more better than worse cases and no regressions. Explicit human requirements allow all ties only when every required check is fulfilled, no case is worse and no regression is reported. Verdicts, evidence and human-origin declarations are caller reports, not authenticated observations. Initialization without an explicit skill can clear the active inherited skill while retaining inherited knowledge ([RT-RTE-feedback-gate](runtime.md#rt-rte-feedback-gate), [MEM-OBJ-feedback](memory.md#mem-obj-feedback), [memory annotations](memory.md#annotations)).
- **Research:** the named evolution engine requires higher mean validation accuracy; the isolated one-round Spreadsheet study requires a higher correct count. The latter freezes final artifacts without scheduling a second learning round or subsequent deployment. Its additional tool and OS controls must not be attributed to the ordinary product ([RT-RTE-research-evolve](runtime.md#rt-rte-research-evolve), [RT-RTE-isolated-study](runtime.md#rt-rte-isolated-study)).

Rejection retains the incumbent but generally leaves committed Wiki learning and proposal evidence available. Thus rejecting instructions is not retracting their supporting lessons. Scorer failure preserves execution output, blocks progression and requires coordinator diagnosis and explicit retry; native recovery can reuse that execution and delegation instead of launching another child. Research resume uses distinct outcome, maintenance and proposal checkpoints. These controls preserve comparisons and reduce repeat work on their named paths, not across every shipped caller ([workflow recovery](workflow.md#failure-recovery-and-delivered-result), [RT-RTE-native-handoff](runtime.md#rt-rte-native-handoff), [RT-RTE-research-evolve](runtime.md#rt-rte-research-evolve)).

Completion exposes retained skill, Wiki and history; it does not mean improvement occurred. Shipped guidance treats rejection/no-action as valid results and calls for Wiki/report delivery when no skill was retained. Export and installation copy retained bytes; replacement and restoration use explicit flags, backups and hash checks. They neither prove host reload nor erase the originating Wiki. MCP omits privileged approval/install tools, but this separation constrains only a client restricted to that surface, not an agent with arbitrary shell access ([workflow account](workflow.md#workflow-account), [RT-RTE-skill-install](runtime.md#rt-rte-skill-install), [RT-CLM-mcp-separation](runtime.md#rt-clm-mcp-separation)).

### What the loop establishes

For a bounded task curriculum with a credible evaluator, the implementation supports selecting instructions against that evaluator and retaining experience for later authors. For requirement-led revision, it supports a different objective: reported fulfillment without regression, potentially without score gain. Neither comparison accepts every explanatory claim in a Wiki or skill. Exact-label scoring, structural contracts and snapshot recomputation have narrower licenses: reference agreement, valid edits/read preconditions and internal numerical/hash consistency respectively. Snapshot verification does not rerun tasks or control candidate admission ([EPI-CLM-wiki-lessons](epistemic.md#epi-clm-wiki-lessons), [EPI-RTE-label-score](epistemic.md#epi-rte-label-score), [EPI-RTE-paper-contract](epistemic.md#epi-rte-paper-contract), [EPI-RTE-snapshot-check](epistemic.md#epi-rte-snapshot-check)).

The theory-builder findings are separate, not a combined grade:

| Property | Supported finding and unresolved question |
|---|---|
| Condition 1: localized theory content | Afforded by whole skill text and scoped procedural guidance; no inspected actual proposal establishes that condition in operation. |
| Condition 2: content-dependent consumption | Skill delivery/injection is wired; decisions depending on what a theory says remain uninspected. |
| Condition 3: content-directed criticism | Evidence, counterexamples and localized revision afford criticism; actual claim/result/blame articulation and resulting changed reliance remain uninspected. |
| Condition 4: criticism shaping another round | Wiki, accepted skills and impact history have wired later-consumer paths in multi-round routes; iteration of formulated criticism remains uninspected. The isolated study supplies a Maintainer-to-Proposer bridge, not another criticized skill generation. |

These condition-level bounds follow [RT-RTE-product-round](runtime.md#rt-rte-product-round), [RT-RTE-feedback-gate](runtime.md#rt-rte-feedback-gate), [RT-RTE-research-evolve](runtime.md#rt-rte-research-evolve), [RT-RTE-isolated-study](runtime.md#rt-rte-isolated-study) and [MEM-RTE-paper-adapters](memory.md#mem-rte-paper-adapters). Addressability ranges from full skill/named-pattern replacement to unique local patches; it does not guarantee individually evaluated assumptions.

**Learning:** automatic trace-fed durable updates with later consumers are wired, but improved future capacity—particularly improvement caused by criticism of a consumed theory—is uninspected. **Reflection:** selected execution records can update procedural representations, which can reach later instruction paths; realized representation-mediated behavioral change and reflective theory building remain uninspected. **Autonomy:** computational author roles and software gates do not establish that computation actually performed every internal theory-building operation. These independent limits do not negate the implemented adaptation paths ([MEM-OBJ-research-evidence](memory.md#mem-obj-research-evidence), [MEM-RTE-paper-adapters](memory.md#mem-rte-paper-adapters), [RT-RTE-product-round](runtime.md#rt-rte-product-round)).

**Self-improvement:** within the controller-plus-retained-instructions boundary, over configured rounds and explicitly inherited workspaces, the system implements an improvement-directed self-change pathway toward an independently specified task metric or requirement objective. This is a dispositional architectural finding, not exercised or successful self-improvement: evidence is supplied to update authors, software can change retained instructions, and those instructions enter later delivery channels. Actual evidence-responsive model determination and subsequent behavior causally depending on the changed content remain unobserved. Installation alone does not close those links ([RT-RTE-product-round](runtime.md#rt-rte-product-round), [RT-RTE-feedback-gate](runtime.md#rt-rte-feedback-gate), [RT-BAP-skill-consumption](runtime.md#rt-bap-skill-consumption), [RT-RTE-skill-install](runtime.md#rt-rte-skill-install)).

Linked inputs, actual lessons/proposals, evaluator results and later executor traces would alter the assessment of semantic transformation, criticism and exercised change. Independent later-task evaluation would address future-capacity claims; independent variation of Wiki maintenance, criticism or isolation would be needed for component attribution. System changes that semantically check lesson support, deliver retained reasons to the relevant consumer, or enforce host isolation would change the corresponding guarantees only once their paths were inspected. None follows from the present gate or role instructions ([epistemic bounded conclusion](epistemic.md#bounded-conclusion), [RT-RTE-native-handoff](runtime.md#rt-rte-native-handoff), [MEM-OBJ-skill-impact](memory.md#mem-obj-skill-impact)).
