# LLM Project Wiki synthesis

## Bounded synthesis

LLM Project Wiki is a prompt package for creating and maintaining a project-specific Obsidian reference through Claude Code. The reviewed boundary is the complete two-file repository, `README.md` and `SETUP_PROMPT.md`, at commit `1fdfba9129a46afd18aa68a83f12d6716ab694c6`, with applicability cutoff 2026-10-14. SRC-1 supplies doctrine/design and a README account of example output, not an inspected generated installation, execution trace or experiment. “Whole-system” therefore means the shipped prompt package, not Claude Code or a consuming project. The [boundary and Source register](boundary.md#source-register) fix those distinctions. This synthesis uses the accepted members without additional source reads.

### Constructing the reference and its future callers

A user pastes setup into Claude Code at a project root. The foreground model owns the progression: inspect project instructions, memories and structure; answer prerequisite project questions; scaffold a vault; generate and run a source-copying script; build pages domain by domain; wire project rules and commands; log and self-audit. An existing literal `Obsidian Vault/` directory instead selects surgical audit and repair. The requested parallel reads do not establish separate agents, isolated contexts or an aggregation protocol. Filesystem and shell effects depend on the excluded host, and no installed permission or isolation envelope is supplied ([RT-RTE-vault-bootstrap](runtime.md#rt-rte-vault-bootstrap), [RT-RTE-gap-audit](runtime.md#rt-rte-gap-audit), [workflow account](workflow.md#workflow-account)).

The intended persistent product separates imported Sources snapshots from compiled Wiki pages. Pages contain project descriptions, exact signatures and schemas, non-obvious constraints, cross-references and decision rationales with rejected alternatives. Index navigation, page metadata, templates, schema, a health dashboard and activity/gap logs support later selection and maintenance. These are specified files; Wiki and Sources are also intended to be Git-tracked. Model admission is not per-page human approval: starting setup and later committing its output are distinct from accepting each write ([MEM-OBJ-sources](memory.md#mem-obj-sources), [MEM-OBJ-wiki](memory.md#mem-obj-wiki), [MEM-OBJ-index](memory.md#mem-obj-index), [RT-OBJ-schema](runtime.md#rt-obj-schema)).

Delivery is the generated installation and support files, not a verified answer set. The final self-audit follows page writing and bootstrap logging, and permits a gap note instead of a completed entity page. It is model-owned checking, not an independent admission barrier or transactional rollback ([RT-RTE-vault-bootstrap](runtime.md#rt-rte-vault-bootstrap), [workflow account](workflow.md#workflow-account)).

### Selecting context and repairing knowledge gaps

For a later question or edit, generated project rules request index lookup, relevant Wiki reads, then memory/source fallback when the wiki is insufficient; targeted edits and audits also permit source access. The “Semantic Lookup” table is model-interpreted intent navigation, not a specified embedding search. Requested reads form a pull chain: file content enters the model context by value. No token budget, trimming, isolated worker-return mechanism or compaction/reload protocol is specified. How the host discovers and delivers generated live rules remains uninspected, so these page reads do not establish that every included delivery path is pull-only ([RT-RTE-wiki-lookup](runtime.md#rt-rte-wiki-lookup), [MEM-OBJ-index](memory.md#mem-obj-index), [RT-BAP-project-rules](runtime.md#rt-bap-project-rules), [RT-BAP-maintenance-rules](runtime.md#rt-bap-maintenance-rules)).

The important maintenance distinction is **copying versus interpretation**. Invoked sync copies project memory, rules and docs into Sources; it does not refresh Wiki pages. Ingest then selects paths using `git diff HEAD~1 --name-only`, maps references, reads source and page, revises sections, resolves open gaps, creates new pages and logs the operation. Task-time insufficiency can therefore produce a retained one-sentence diagnosis that later guides a durable page revision and subsequent lookup. This is a claimed experience-fed update, not observed learning, raw session extraction or parameter training. The original trace-source category and other project-memory provenance remain unresolved ([RT-RTE-source-sync](runtime.md#rt-rte-source-sync), [RT-RTE-diff-ingest](runtime.md#rt-rte-diff-ingest), [MEM-OBJ-log](memory.md#mem-obj-log)).

Several conditions limit freshness. Copy errors can be suppressed despite a completion message. A one-comparison diff is not an inventory of all stale state. Dry-run stops before dependent-page grep, so it need not preview the page-level write set. Edit-time stale marking is a documented model instruction, not an inspected hook. The special status consumer falls back when stale, but ordinary lookup has no explicit general stale-rejection gate. Broader audit can compare source inventories and timestamps, inspect actual code, repair pages and fix the script itself; it is a later invoked recovery path, not automatic failure handling. Deletion propagation and obsolete-page withdrawal are unspecified ([RT-RTE-source-sync](runtime.md#rt-rte-source-sync), [RT-RTE-diff-ingest](runtime.md#rt-rte-diff-ingest), [RT-RTE-gap-audit](runtime.md#rt-rte-gap-audit), [MEM-CLM-retention-limits](memory.md#mem-clm-retention-limits)).

### What checks and repairs establish

Wiki-first rules give pages operational priority, not a truth license or access-control prohibition. The Sources label is a reference-layer policy rather than literal immutability: sync and manual recovery change its files. Warning headers ask the model not to obey three archived instruction copies; they do not establish host instruction isolation and do not cover all Memory/Rules copies ([RT-CLM-wiki-first](runtime.md#rt-clm-wiki-first), [RT-CLM-sources-immutability](runtime.md#rt-clm-sources-immutability)).

The design does request source reconciliation, task-sufficiency judgments and structural checks. Their licenses differ. Frontmatter grep checks three key strings, not valid YAML or the required `sources` field; link/index examples use prefix or substring matches, not complete graph validation. Broader model review could exceed these examples. Neither these diagnostics nor answering without source access establishes semantic correctness. No recorded evidence-consuming epistemic acceptance decision was found in the shipped files; operational admission, retention and cross-linking do not establish accepted new knowledge. Absent source/page pairs also leave copying, entailment and conjecture unresolved for particular page claims ([EPI-RTE-schema-check](epistemic.md#epi-rte-schema-check), [EPI-RTE-link-check](epistemic.md#epi-rte-link-check), [EPI-OBJ-wiki-pages](epistemic.md#epi-obj-wiki-pages), [EPI-CLM-answer-coverage](epistemic.md#epi-clm-answer-coverage), [epistemic bounded conclusion](epistemic.md#bounded-conclusion)).

The strongest improvement-related contribution is a specified repair pathway for the generated installation's own behavior-guiding files. Audit diagnoses incomplete copying or maintenance wiring and can revise scripts, commands, schema and project rules for future sessions. Its independent objective is complete, fresh coverage and closed maintenance wiring across sessions. Reflection and improvement-directed self-change are **claimed**, not exercised: no generated revision, live loading or subsequent change-dependent behavior closes the causal chain. Successful improvement is unestablished, and this pathway does not revise the shipped setup prompt ([RT-RTE-gap-audit](runtime.md#rt-rte-gap-audit), [RT-BAP-project-rules](runtime.md#rt-bap-project-rules), [RT-BAP-maintenance-rules](runtime.md#rt-bap-maintenance-rules)).

The theory-builder conditions remain independent. Condition 1, localized maintenance-rule content, and condition 2, decisions depending on that content, have **claimed** status. Condition 3, content-directed criticism naming claim, result and blame, and condition 4, criticism-dependent iteration, remain **uninspected**. Structural repair does not itself establish criticism of the wiki-first premise. Whether criticism of a consumed theory improved capacity for future action is likewise **uninspected**. Reflective and autonomous theory-builder status are **uninspected**; computational patching alone does not establish every internal theory-building operation. These uncertainties do not negate the specified experience-fed page repair or method-file self-change ([RT-RTE-gap-audit](runtime.md#rt-rte-gap-audit)).

For the scenario of a project session answering from maintained pages, the design supplies a coherent selection and recovery procedure, conditional on accurate compilation, metadata, maintenance invocation and host compliance. For a scenario requiring reliably fresh or warranted answers, those conditions are not demonstrated. An installed vault with source/page comparisons would resolve compilation and coverage questions; traces linking gaps to repairs and later consumers would establish operation; an independently assessed before/after comparison would be needed to attribute better future capacity. Inspectable edit hooks, complete dependency reconciliation and explicit withdrawal rules would materially change freshness guarantees. Current evidence supports intended organization and use, not a product ranking or demonstrated benefit ([EPI-CLM-compiled-knowledge](epistemic.md#epi-clm-compiled-knowledge), [RT-CLM-audit-completeness](runtime.md#rt-clm-audit-completeness)).
