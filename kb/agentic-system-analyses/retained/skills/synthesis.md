# Sentry Skills synthesis

## Bounded synthesis

Sentry Skills is an instruction and helper package for engineering and writing assistance, not an enclosing agent runtime. This analysis covers the repository artifact at commit `d18b7aa8ba878354e5c348310230e652f7690f9c`, with an applicability cutoff of 2026-10-14. Its operational boundary is **complete artifact, partial loop**: external hosts select instructions, call models and execute tools. The evidence is inspected implementation and doctrine/design from SRC-1, not supplied execution traces or causal experiments. No target code, evaluator or service was executed. The [boundary](boundary.md#boundary-and-evidence) and [Source register](boundary.md#source-register) state the inclusions and external dependencies.

### From discovery to action

Installation exposes canonical skills and subagent prompts through plugin/discovery surfaces. A host delivers Markdown instructions to a foreground model or subagent; frontmatter has a separate host-parsed, symbolic consumption path. The model interprets workflow rules and chooses actions. Python helpers perform fixed fetching, transformation, validation or polling. Tool permissions, actual relevance matching, model versions and isolation belong to external hosts. The subagent alias `opus` does not pin a model revision or establish whether parameters change. See [RT-OBJ-skill-md](runtime.md#rt-obj-skill-md), [RT-BAP-skill-consumption](runtime.md#rt-bap-skill-consumption) and [RT-CMP-host-model](runtime.md#rt-cmp-host-model).

Context control follows the same division. Skill authoring prescribes loading only the references needed for the current step, rather than all maintenance material. This is foreground selection, not an implemented token allocator or eviction mechanism. Document reader testing specifies a fresh reader receiving only the draft and question, with a manual fresh-chat alternative. It affords withholding author context, but host frame destruction, compaction and actual isolation are unobserved. See [RT-RTE-skill-revision](runtime.md#rt-rte-skill-revision), its memory annotation, and [MEM-RTE-reader-testing](memory.md#mem-rte-reader-testing).

### A repair cycle and its actual stopping condition

The representative `iterate-pr` workflow connects request, criticism, repair and delivery. With authenticated `gh`, `uv` and target-repository context, the foreground agent fetches CI and review feedback, diagnoses causes, edits code, verifies locally, commits and pushes, then examines new results. Helpers receive PR identities and return selected observations; no model-worker delegation is required. The foreground retains repair and recovery ownership. High/medium feedback is actionable, low-priority feedback requires user choice, and repeated failure after two attempts, unclear feedback or infrastructure problems require consultation. Local failure is a prescribed bar to pushing, not a code-enforced interception. See [RT-RTE-pr-iteration](runtime.md#rt-rte-pr-iteration) and the [workflow account](workflow.md#workflow-account).

The observations are narrower than a complete review transcript. Feedback retrieval is bounded and projects inline threads to their first comment, omitting self-comments and very short bodies. CI failure snippets are bounded; workflow-run matching does not enforce current-head SHA equality. Some fetch failures become empty lists. Instructions therefore require full failed-log inspection and cause identification before editing. Direct `gh` fallback is allowed, so helper classifications are not mandatory control points. These limits constrain what a clean fetched result establishes, independently of whether the repair policy is sensible. See [RT-RTE-pr-iteration](runtime.md#rt-rte-pr-iteration).

The monitor polls deterministically; it does not repair code. Pending non-human checks delay termination, then failures and human gates determine markers. Terminal failures can exit zero. `ALL_CHECKS_PASSED` means no received pending/fail bucket under its classification, not that every check explicitly passed. Full workflow success additionally requires a feedback fetch ten seconds after actionable CI passes and handling the low-priority choice. New actionable feedback reopens repair. Delivery is the pushed repair plus a success, stop or ask-user report, not proof of mergeability. See [RT-RTE-check-monitor](runtime.md#rt-rte-check-monitor) and its [workflow annotation](workflow.md#annotations). Optional replies publish caller-authored claims and classify API acknowledgements; they neither verify those claims nor establish later agent receipt of the replies. See [MEM-RTE-thread-reply](memory.md#mem-rte-thread-reply).

### Checks license different conclusions

The package does not supply one universal evaluator. Its structural validator checks skill format and recognized local references; a size warning is advisory, and passing does not establish semantic quality or security. Security scanning produces mechanical pattern leads, while model-directed context review filters intent and false positives before an advisory installation recommendation. Warden configuration is not inspected enforcement. See [RT-RTE-skill-revision](runtime.md#rt-rte-skill-revision), [EPI-RTE-pattern-scan](epistemic.md#epi-rte-pattern-scan) and [EPI-RTE-security-disposition](epistemic.md#epi-rte-security-disposition).

Likewise, triage approval authorizes only a displayed archive batch; it is a prompt policy, not an argument-level mutation wrapper or proof that classification is correct. Reader testing checks selected comprehension, not document truth. Endpoint documentation requests source/live-response comparison, whose warrant cannot exceed the tested domain. Code simplification requests behavior preservation on both skill and subagent paths without establishing semantic equivalence. These are distinct operational and epistemic scopes, supported by [RT-RTE-issue-triage](runtime.md#rt-rte-issue-triage), [MEM-RTE-reader-testing](memory.md#mem-rte-reader-testing), [EPI-RTE-endpoint-check](epistemic.md#epi-rte-endpoint-check) and [RT-CLM-preserve-functionality](runtime.md#rt-clm-preserve-functionality).

### Evidence can revise the guidance itself

The strongest supported improvement contribution is a prescribed experience-to-guidance route. Skill-writer separates working/holdout examples, interpreted findings, promoted instructions, provenance decisions and a maintenance contract. Model authors can choose deltas without per-change human approval; moving holdouts into the working set requires an explicit user decision. Later maintenance can read retained reasons, while ordinary task consumers normally receive the resulting rules rather than every justification. See [RT-RTE-skill-revision](runtime.md#rt-rte-skill-revision), [MEM-OBJ-working-set](memory.md#mem-obj-working-set), [MEM-OBJ-findings-log](memory.md#mem-obj-findings-log), [MEM-OBJ-sources](memory.md#mem-obj-sources), [MEM-OBJ-spec](memory.md#mem-obj-spec) and [EPI-RTE-example-retention](epistemic.md#epi-rte-example-retention).

This supports a **claimed trace-fed durable behavioral write**, not automatic trace ingestion or demonstrated learning. Actual example origins, populated promotion records and original trace classes are unresolved. Retained experience is an input to revision; revised instructions have a different consumer in later task execution. Configured AXIS generation and model scoring do not install changes. Maintainer adoption requires completed working-set runs, no critical holdout regression, target improvement and the stated validation conditions. Actual reports, decisions and deployed read-back are not supplied. See [RT-RTE-maintainer-eval](runtime.md#rt-rte-maintainer-eval) and the [profile verification](profile-verification.md#verification).

Other retained outputs serve different purposes. Generated project guidance is intended to direct later agents. A SRED Work Summary is explicitly requested by a later organizer as evidence; a saved draft is requested for reader testing. Neither document handoff by itself establishes package self-revision. Host guidance loading affords or declares push, while requested maintenance/document reads are pull; the actual automatic host selector remains unknown. See [MEM-RTE-project-guidance](memory.md#mem-rte-project-guidance), [MEM-RTE-sred-handoff](memory.md#mem-rte-sred-handoff) and [MEM-RTE-reader-testing](memory.md#mem-rte-reader-testing).

For skill-writer, theory-builder condition 1, localized method content, is **afforded**; condition 2, decisions depending on it, is **claimed**; condition 3, content-directed criticism with blame and changed reliance, is **uninspected**; and condition 4, retained criticism shaping another round, is **claimed**, not observed. Learning as improved capacity for future action remains **uninspected**. Reflection is **afforded** through revision of its own method texts, while exercised reflective theory building and autonomous theory building remain **uninspected**. These findings are independent. The package affords dispositional self-improvement toward high-value input coverage with reduced wasted runtime tokens across later installed invocations. Evidence shaping an actual update, its entry into live host authority and subsequent operation causally depending on it are not established; successful improvement is separately unestablished. See [RT-RTE-skill-revision](runtime.md#rt-rte-skill-revision).

For the selected repair scenario, the supported mechanism is a model-owned cycle with explicit verification and escalation policies plus bounded observation helpers. For later guidance revision, it is an evidence-retention and adoption procedure, not an exercised improvement result. A trace linking criticism, revision, admission, installed loading and later changed behavior would strengthen the latter assessment. Controlled comparisons would be needed to attribute benefit to particular rules or helpers. Host enforcement evidence and current-head-complete service observations would change the strength of the former assessment. Additional shipped revision mechanisms already prevent treating the selected skill-writer account as exhaustive, as the [report verification](report-verification.md#limits) explains.
