# SkillWeaver synthesis

## Bounded synthesis

SkillWeaver's strongest supported contribution is a connected route from browser experience to durable changes in its own later action machinery. It synthesizes reusable Python functions, retains their documentation and metadata, and supplies them to later task attempts. A second route changes future practice and visibility through persistent test counters. Both are implemented trace-fed behavior-shaping writes, not demonstrated gains in capacity. The unresolved question is whether subsequent operation depends on those changes and performs better because of them ([RT-RTE-skill-admission](runtime.md#rt-rte-skill-admission), [RT-BAP-library-execution](runtime.md#rt-bap-library-execution), [EPI-RTE-tested-label](epistemic.md#epi-rte-tested-label)). Evidence: SRC-1, `skillweaver/knowledge_base/knowledge_base.py`, `skillweaver/agent.py`, `skillweaver/explore.py`.

The evidence is source inspection of the canonical SkillWeaver repository at commit `f2a63d65d0f6ff46ac30e817cede8797f8f25b97`, with an applicability cutoff of 2026-10-14. The [boundary](boundary.md#boundary-and-evidence) classifies the target as a whole-system builder or improvement plane: exploration, native browser actions, skill admission and persistence, the experimental Browser-Use adapter and benchmark drivers are included. Code supplies implementation evidence; README and prompts supply intent; shipped skill usage logs supply reported operation only. No execution trace or causal comparison is registered. External model services, browser implementations, website/container state and Browser-Use planning are not frozen. The accepted [report verification](report-verification.md#verification) and [profile verification](profile-verification.md#verification) have no remaining blockers or declared limits; that does not remove the records' evidence boundaries. Source identity and layers are registered as SRC-1 in the [Source register](boundary.md#source-register).

### Practice supplies the update evidence

A representative invocation is `python -m skillweaver.explore reddit <out_dir>`. The caller supplies website, models, iteration budget, schedule and optional initial library. Asynchronous workers own browser wrappers but share the knowledge base. Software selects an untested function for practice or asks a model to propose a website task. Locks serialize selection and admission, not entire attempts; another worker can change the shared library while an attempt proceeds. These are not independently isolated delegated agents ([RT-RTE-explore-practice](runtime.md#rt-rte-explore-practice), [workflow account](workflow.md#workflow-account)). Evidence: SRC-1, `skillweaver/explore.py`.

Each native attempt starts fresh action/state lists and disabled names. It selects skill descriptions once, then asks a model for Python actions or termination. Each action sees the current browser observation and formatted earlier actions, rather than every saved screenshot and intermediate tree. Separate relevance, success and synthesis calls receive different selected inputs. This is code-owned working-context selection, not a durable conversation summary. Generated Python is imported and executed in the host process with the full library unless reference-only mode omits it. Selected descriptions and hidden unverified names therefore are presentation controls, not a selected-only capability boundary. Five-response generation retries are best effort, not a final invariant veto ([RT-RTE-native-task](runtime.md#rt-rte-native-task), [MEM-OBJ-traces](memory.md#mem-obj-traces)). Evidence: SRC-1, `skillweaver/attempt_task.py`, `skillweaver/agent.py`.

The attempt returns states and actions. The builder's default text rendering retains the initial observation and action/result fields but omits intermediate state renderings and explicit recovery annotations. It overwrites the task driver's richer readable trajectory; raw artifacts still survive separately. The success model receives this reduced text plus the final screenshot. Synthesis receives the reduced text without that separate screenshot or the success model's reasoning. Thus saved experience is richer than the evidence delivered to the update consumer ([EPI-RTE-trajectory-format](epistemic.md#epi-rte-trajectory-format), [MEM-OBJ-traces](memory.md#mem-obj-traces)). Evidence: SRC-1, `skillweaver/agent.py`, `skillweaver/explore.py`.

### Two branches confer different kinds of reliance

For a test, a matching named-call node anywhere in the last action's source, together with no recorded exception or recovery attempt, triggers a counter increment and bypasses success judgment and synthesis. A call under `if False` can satisfy this predicate without executing the skill. The stored label therefore establishes neither exercised skill use nor website success. Nevertheless, its counter affects later visibility, synthesis inclusion and practice scheduling. Loaded metadata and an exposed blanket-marking method can also supply tested status without replaying tests ([EPI-RTE-test-check](epistemic.md#epi-rte-test-check), [EPI-RTE-tested-label](epistemic.md#epi-rte-tested-label), [MEM-OBJ-metadata](memory.md#mem-obj-metadata)). Evidence: SRC-1, `skillweaver/attempt_task.py`, `skillweaver/explore.py`, `skillweaver/knowledge_base/knowledge_base.py`.

Other attempts reach the success model. Its Boolean is a task-scoped inference from visible evidence, not an independent expected-outcome oracle. Software consumes a positive judgment to accept the episode **as synthesis input**; a negative judgment withholds synthesis. This acceptance does not establish the correctness of a not-yet-generated generalized procedure ([EPI-RTE-success-check](epistemic.md#epi-rte-success-check), [EPI-RTE-success-decision](epistemic.md#epi-rte-success-decision)). Evidence: SRC-1, `skillweaver/knowledge_base/check_success.py`, `skillweaver/explore.py`.

### Installation makes skills durable, not warranted

Synthesis receives task, selected trajectory, semantic text, update instructions and filtered existing function source. Prompts request generalization and usage documentation. Static checks report coding violations and can request up to ten proposals, but exhaustion still reaches application; parse/format errors can instead stop it. Same-name functions replace existing bodies and documentation, omitted names remain, and changed functions' test counts reset. Neither docstring presence nor navigation-text occurrence proves documentation truth, safe replay or website outcomes. Actual generated content may reshape or generalize its inputs; its semantic relation is indeterminate without candidate/input instances. This is operational installation, not integration of an accepted generalized claim ([RT-RTE-skill-admission](runtime.md#rt-rte-skill-admission), [EPI-RTE-code-check](epistemic.md#epi-rte-code-check), [EPI-RTE-skill-merge](epistemic.md#epi-rte-skill-merge)). Evidence: SRC-1, `skillweaver/knowledge_base/knowledge_base.py`, `skillweaver/knowledge_base/code_verification.py`, `skillweaver/templates/kb_procedural_update_base.md`.

Delivery consists of live shared-library mutation and an iteration checkpoint containing code, metadata and semantic text. A checkpoint can also follow a negative success judgment; exceptions before saving can prevent delivery. Diagnostic handling is not transactional rollback, manual prefix reload is not automatic best-checkpoint recovery, and the CLI's zero exit does not prove successful exploration ([workflow account](workflow.md#workflow-account), [RT-RTE-explore-practice](runtime.md#rt-rte-explore-practice)). Evidence: SRC-1, `skillweaver/explore.py`.

Later tasks consume two distinct retained parts: Python bodies execute when invoked, while signatures/docstrings guide relevance selection and model action choices. Ordinary reload restores these parts and metadata, not synthesis reasoning from diagnostics. Loaded semantic text informs proposals and synthesis but is unchanged by the inspected update. Established consumer chains request retained material; optional embedding selection, schema exports and artifact reconstruction remain capabilities without established later-consumer routes. They cannot establish complete pull-only coverage or a push signal ([MEM-OBJ-code](memory.md#mem-obj-code), [MEM-OBJ-docstring](memory.md#mem-obj-docstring), [MEM-OBJ-semantic-knowledge](memory.md#mem-obj-semantic-knowledge), [MEM-RTE-embedding-selection](memory.md#mem-rte-embedding-selection), [profile verification](profile-verification.md#verification)). Evidence: SRC-1, `skillweaver/knowledge_base/knowledge_base.py`.

### Recovery, alternate consumption and assessment

Optional locator recovery can check a model-proposed replacement against type, count and selected-element identity, then retry the original operation. It does not prove user intent, roll back earlier effects or directly repair retained code. Browser-Use instead receives selected callbacks constructed after executing library code; its external planner owns continuation and termination, without inheriting native checking or exception tracking ([RT-RTE-locator-recovery](runtime.md#rt-rte-locator-recovery), [RT-RTE-browser-use](runtime.md#rt-rte-browser-use)). Evidence: SRC-1, `skillweaver/environment/patches.py`, `skillweaver/attempt_task_browser_use.py`, `skillweaver/knowledge_base/knowledge_base.py`.

For bounded website practice, the source supports automatic proposal, execution, episode judgment, installation and later availability. For generalized task correctness or improved future performance, it supplies no observed or causal conclusion. Benchmark checking is a separate path: inspected string/URL rules assess configured representations, and scores feed reporting rather than skill acceptance or rollback. A missing unconditional computer-use import and CLI mismatches obstruct a clean-source evaluation claim, although local scoring code exists ([RT-RTE-benchmark-evaluation](runtime.md#rt-rte-benchmark-evaluation), [RT-ABS-cua-module](runtime.md#rt-abs-cua-module), [EPI-RTE-benchmark-check](epistemic.md#epi-rte-benchmark-check), [EPI-RTE-score-retention](epistemic.md#epi-rte-score-retention)). Evidence: SRC-1, `skillweaver/evaluation/evaluate_single_task.py`, `skillweaver/evaluation/evaluate_benchmark.py`, `skillweaver/evaluation/webarena_evaluators.py`.

The properties remain separate. The inspected builder is computationally autonomous in its internal practice/update roles, without per-skill human approval; this says nothing about reliability or autonomy of an unestablished theory-building loop. Theory-builder conditions 1–4 are not individually established by the supplied runtime account: generalized procedures, delivery, checker feedback and repetition cannot substitute for demonstrated localized theory content, content-dependent decisions, formulated content-directed criticism and retained criticism shaping another round. The records likewise do not establish that criticism of a consumed theory improved future capacity, or that the system is reflective. These are unestablished findings, not evidenced absences. In contrast, the builder-plus-consumer boundary supports an **improvement-directed dispositional self-change path**, with the objective of reusable website automation over later iterations/tasks. It does not establish exercised self-improvement: no trace closes subsequent causal dependence on an update, and no comparison establishes successful improvement. Provider weight changes remain independently uninspected ([RT-RTE-skill-admission](runtime.md#rt-rte-skill-admission), [RT-CLM-self-improvement](runtime.md#rt-clm-self-improvement), [RT-CMP-lm](runtime.md#rt-cmp-lm), [epistemic conclusion](epistemic.md#bounded-conclusion)). Evidence: SRC-1, `skillweaver/knowledge_base/knowledge_base.py`, `skillweaver/explore.py`, `skillweaver/lm.py`.

An update-linked execution trace would change the exercised-operation assessment. A controlled library intervention and comparable tasks could establish benefit at the intervention's actual scope. Runtime call instrumentation and authoritative outcome checks would strengthen tested labels; a final checker veto would change admission strength but still would not prove website semantics. Candidate/episode comparisons and generalized behavioral tests would clarify what synthesis produces and licenses. These are evidence or system changes needed for stronger conclusions, not claims about operation at this pin.
