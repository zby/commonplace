# MemoryOS synthesis

## Bounded synthesis

### From dialogue to retained context

MemoryOS is a memory and context-engineering system for personalized dialogue, not an enclosing autonomous agent runtime. This account covers its shipped Python JSON libraries, bundled MCP server, Flask Playground, ChromaDB variant and separate evaluation workflow at commit `587ed7755c7aed179965792830ff1b5ad9a6fa92`, with an analysis cutoff of 2026-10-16. The evidence is source implementation, declared design and attributed performance claims in SRC-1. No target program, provider, test or example was executed, and no execution trace or causal experiment was supplied. The whole-system functional boundary does not mean exhaustive inspection of every helper or dependency ([boundary](boundary.md#boundary-and-evidence), [Source register](boundary.md#source-register)). This synthesis adds no source inspection.

The ordinary JSON path starts with a caller selecting user and assistant IDs, storage and model configuration. Those IDs select files; they do not authenticate ownership. Python owns progression through retrieval, prompt construction, completion, admission and return. Models propose text for answers and maintenance; they do not select executable tools or direct sub-agents in this route. Worker threads perform fixed retrieval or analysis tasks ([RT-RTE-dialogue-response](runtime.md#rt-rte-dialogue-response)).

Dialogue enters through direct add, generated responses, MCP add or Playground import. Imported assistant text need not have come from MemoryOS's response model. Recent exchanges occupy a bounded deque serialized to JSON. Before an orchestrated append would overflow it, the updater removes old exchanges and migrates them into mid-term sessions. It adds model-generated topic summaries and continuity overviews while generally retaining original dialogue pages. The same batch can enter multiple themes; this is not a verified partition by topic. Merging appends pages without refreshing the established session summary and embedding, leaving an older selection gate over newer content ([RT-RTE-memory-admission](runtime.md#rt-rte-memory-admission), [MEM-OBJ-short-term](memory.md#mem-obj-short-term), [MEM-OBJ-mid-term](memory.md#mem-obj-mid-term)).

Access frequency and heat influence what survives and what is analyzed. After admission, the hottest session can supply unanalyzed pages to two fixed model tasks: one revises the user profile using its previous text, and one extracts user and assistant statements. Code admits a nonempty, non-`none` profile of at least thirty stripped characters and filters empty/none-like knowledge lines. It replaces the profile and appends facts. Force-analysis lowers the threshold but still selects one hottest session; it does not process every eligible page. Analyzed flags can suppress future extraction even when a proposal was skipped. These are eligibility and processing controls, not factual endorsement ([RT-RTE-profile-analysis](runtime.md#rt-rte-profile-analysis), [MEM-OBJ-memory-access](memory.md#mem-obj-memory-access)).

The resulting memory is mixed: natural-language dialogue, summaries, profiles and facts; symbolic IDs, links, counters and flags; and dense numerical embeddings for selection. It lives in files and process collections, with FAISS or ChromaDB providing vector access. Adding embeddings and revising text do not train the inspected encoders or completion models. Their actual resolved weights and provider-side mutability remain outside the evidence ([MEM-OBJ-memory-access](memory.md#mem-obj-memory-access), [MEM-OBJ-chroma-storage](memory.md#mem-obj-chroma-storage), [RT-CMP-openai-client](runtime.md#rt-cmp-openai-client), [RT-CMP-sentence-transformer](runtime.md#rt-cmp-sentence-transformer), [RT-CMP-bgem3-flag-model](runtime.md#rt-cmp-bgem3-flag-model)).

### From retained context to a delivered answer

A representative JSON `get_response` call fans out three retrieval tasks for historical pages, user knowledge and assistant knowledge. Semantic thresholds and bounded ranking choose older material; all recent dialogue and the full user profile bypass query ranking. Defaults bound final pages to seven, candidate sessions to five and each knowledge task to twenty entries, not total input tokens. Each call reconstructs a two-message context rather than growing a provider conversation indefinitely. Older pages remain outside the window and can be copied back later; this is not a stack of isolated agent frames or a model-followable pointer structure ([RT-RTE-dialogue-response](runtime.md#rt-rte-dialogue-response), [workflow account](workflow.md#workflow-account)).

User profile, user facts and history enter the user message. Assistant statements enter system-message role/trait conditioning. These placements give retained content different behavioral channels, but neither placement grants truth or guarantees compliance. Assistant-ID scoping can also span users. Profile reasons may survive in the stored prose and reach later update and response calls; extracted facts do not retain enforced original-page references ([RT-BAP-user-context](runtime.md#rt-bap-user-context), [RT-BAP-assistant-context](runtime.md#rt-bap-assistant-context), [MEM-OBJ-user-profiles](memory.md#mem-obj-user-profiles), [MEM-OBJ-assistant-knowledge](memory.md#mem-obj-assistant-knowledge)).

The provider returns answer text, which is cleaned before storage. Tagged reasoning spans can be deleted without a semantic-preservation check. The orchestrator then admits the query and cleaned response before returning the answer. Delivery means library return, not verified satisfaction, style compliance or durable commit. Retrieval failures become empty context lists. A caught provider exception becomes ordinary error text that can itself be stored as dialogue; an uncaught admission failure can prevent return after generation. Migration removes and saves input before downstream insertion succeeds, and best-effort saves supply no whole-turn rollback ([EPI-RTE-output-cleaning](epistemic.md#epi-rte-output-cleaning), [RT-RTE-dialogue-response](runtime.md#rt-rte-dialogue-response), [RT-RTE-memory-admission](runtime.md#rt-rte-memory-admission), [workflow account](workflow.md#workflow-account)).

Requested generation, MCP retrieval and browser inspection establish pull read-back on the assessed chains. Automatic formatting within a request is not independent unsolicited delivery. Remaining driver/helper coverage prevents a whole-repository pull-only conclusion ([MEM-OBJ-memory-access](memory.md#mem-obj-memory-access), [RT-RTE-mcp-access](runtime.md#rt-rte-mcp-access), [MEM-RTE-profile-display](memory.md#mem-rte-profile-display), [profile verification](profile-verification.md#verification)).

### Material alternatives change the loop

MCP exposes add, retrieve and profile tools. It returns memory data, not the host's final answer, and the host must separately add any resulting dialogue. Its result slicing does not bound full recent history or profile output. The host's downstream prompt channel and reliance remain outside the reviewed target. Playground supplies chat plus import, forced analysis, inspection and destructive clear. Clear changes configuration as well as deleting stores; it is not versioned rollback. Its trait display is not the retained profile or an approval surface: a substring fallback can display High from prose denying High, without writing that assignment back to memory ([RT-RTE-mcp-access](runtime.md#rt-rte-mcp-access), [RT-RTE-playground-control](runtime.md#rt-rte-playground-control), [EPI-RTE-personality-display](epistemic.md#epi-rte-personality-display)).

ChromaDB separates persistent vector collections from metadata saved on close/normal exit. More importantly, new-session insertion aliases the provider's session dictionary and overwrites its freshly created page backup with an object lacking backup pages. This is a source-established producer-to-consumer break before any reload: vector dialogue can remain retrievable, but those initial pages cannot reach backup-only heat extraction or chain-overview enrichment. Later merges can leave backups for newly merged pages without recovering the original backup. Dependency duplicate-ID behavior is a separate unresolved issue. Capacity eviction has another implementation-deduced failure: provider deletion removes the shared entry, then a local second removal raises before cleanup and heap rebuilding. Thus vector persistence cannot be read as a complete working maintenance loop or uninterrupted capacity handling ([RT-RTE-chroma-dialogue](runtime.md#rt-rte-chroma-dialogue), [MEM-OBJ-chroma-storage](memory.md#mem-obj-chroma-storage), [report-verification limit](report-verification.md#limits)).

### What the changes establish, and what would change the assessment

The strongest supported learning contribution is automatic dialogue-fed production of durable summaries, profiles and facts with later selection, update and response consumers. This is wired trace learning from session logs, not merely raw-log retention. It does not establish improved capacity for future action. Profile revision changes retained behavior-shaping content, while the comparison needed to show better future dialogue has not been supplied. The ChromaDB positive rests on summary production and surviving merged-page backups, not intact extraction from initial pages ([RT-RTE-memory-admission](runtime.md#rt-rte-memory-admission), [RT-RTE-profile-analysis](runtime.md#rt-rte-profile-analysis), [MEM-OBJ-chroma-storage](memory.md#mem-obj-chroma-storage), [profile verification](profile-verification.md#verification)).

For repeated dialogue, implementation therefore establishes a route for old experience to condition later answers, including potentially unsupported interpretations. Admission checks target shape, length and eligibility. Summaries, profiles, facts and answers have indeterminate semantic relations without actual candidates and semantic checking. Retention and use do not establish evidence-consuming acceptance of their truth. The inspected maintenance routes establish neither accepted new ampliative knowledge nor lifecycle integration after such acceptance. These are scoped findings, not a system-wide epistemic grade ([epistemic ledger](epistemic.md#authority-route-ledger), [epistemic conclusion](epistemic.md#bounded-conclusion)).

The separate LoCoMo driver imports conversations, derives sample memories, retrieves for questions and saves answers/references for offline token-set F1. It differs from the product algorithm: user-only summary input, separate profile merging, all-assistant-knowledge delivery, and no admission of generated benchmark answers. It reloads existing sample files without guaranteeing a clean start. The lexical scorer does not adjudicate factual truth or feed an inspected method-revision consumer. README-reported F1 and BLEU gains remain attributed claims, not reproduced or causally identified results ([RT-RTE-locomo-evaluation](runtime.md#rt-rte-locomo-evaluation), [MEM-OBJ-evaluation-memory](memory.md#mem-obj-evaluation-memory), [MEM-OBJ-loco-results](memory.md#mem-obj-loco-results), [RT-CLM-dialogue-benefit](runtime.md#rt-clm-dialogue-benefit)).

No content-directed criticism of a consumed theory, retained criticism-driven iteration, or resulting improvement in future capacity is established by the inspected maintenance account. The runtime supplies no separate conditions 1–4 assessment from which to assert full theory-builder status. Fixed computational progression is established, not autonomy of every theory-building role. Likewise, assistant-related memory alone does not establish both causal directions of a reflective self-representation. These properties remain independently unestablished, not inferred absent from missing runs. At this boundary, retained context updates reach live behavior-shaping channels, but evidence-responsive determination against an independently specified improvement objective and subsequent operation causally depending on the change are not established as an exercised self-improvement pathway ([RT-RTE-profile-analysis](runtime.md#rt-rte-profile-analysis), [epistemic conclusion](epistemic.md#bounded-conclusion)).

Concrete evidence could strengthen this account: linked input/update/reload/consumer traces would establish exercised reuse; semantic checks against original dialogue would resolve preservation and factual-admission questions; and controlled before/after dialogue comparisons with component variation would test benefit and its attribution. A self-improvement finding would additionally need objective-bearing evidence shaping the update and subsequent operation depending on it. For ChromaDB, preserving the backup-bearing dictionary entry and removing the second eviction deletion would change the identified implementation barriers; merge/reload and failure traces would still be needed to establish successful operation. These changes would not, by themselves, prove factual warrant or improved dialogue.
