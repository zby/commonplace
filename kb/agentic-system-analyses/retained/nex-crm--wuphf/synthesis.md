# Wuphf synthesis

## Bounded synthesis

### From requests to two execution families

Wuphf is an enclosing agent runtime that combines a shared office broker with a service for building and executing saved tools. The frozen repository calls the product gawkbot. Its claimed work is to turn described workflows into local microapps with tools, schedules, knowledge and human approvals. This account concerns SRC-1, `https://github.com/nex-crm/wuphf`, at commit `88023d4dac7491b6e71dbc1e86d274c435b9cb2c`, with an analysis cutoff of 2026-10-15. The evidence is inspected implementation and attributed design, not execution traces or experiments. The boundary is **complete artifact, partial loop**: the repository is captured, but not every shipped producer, maintainer and consumer has been traced. External CLIs, providers and services are dependencies whose internals were not frozen. See the [boundary and evidence](boundary.md#boundary-and-evidence) and [Source register](boundary.md#source-register).

In ordinary office work, the launcher starts the broker, web interface and background dispatch loops. A message becomes a targeted work packet, enters a bot/task/worktree lane and reaches a selected provider runner. Wuphf owns targeting, queueing, context assembly, process lifecycle and broker state; the external CLI/model owns much of the next-step and tool selection. The compatible-provider alternative instead has a local eight-iteration tool loop and can fall back to text-only operation when its MCP bridge fails. Streamed text, tool effects, final-message fallback and task ledger state are separate outputs. Neither a working directory nor these orchestration controls establishes filesystem containment or exactly-once external effects. See [RT-RTE-office-turn](runtime.md#rt-rte-office-turn) and [RT-RTE-compatible-turn](runtime.md#rt-rte-compatible-turn).

The sidecar family has a different division of labor. A model can propose JavaScript tool code; software checks and stores it; a later worker executes its capability sequence. Saved code therefore controls behavior directly, unlike prose supplied as model context. Supplied workflow specifications have another path: deterministic ordered replay can issue HTTP requests without traversing the tool worker. App publication separately admits app bytes under actor/capability checks, with restoration available but full store validation untraced. These paths should not inherit one another's guarantees. See [RT-OBJ-stored-tool](runtime.md#rt-obj-stored-tool), [RT-BAP-tool-execution](runtime.md#rt-bap-tool-execution), [RT-RTE-spec-replay](runtime.md#rt-rte-spec-replay) and [RT-RTE-app-publication](runtime.md#rt-rte-app-publication).

### A scheduled routine reaches a recorded outcome, not necessarily a completed action

The representative multi-step workflow is a scheduled custom-app routine because its shipped broker producer and service consumer form one inspectable chain. A due job selects the live playbook prompt when present, otherwise stored payload or label, and re-arms recurrence before asynchronous dispatch. App ID scopes data/capabilities; routine slug identifies the schedule/session association; saved tool name and returned session ID are different identities. The service searches saved tools by exact mention or title-word overlap. A match runs without fresh authoring verification; a changed prompt alone does not force new code. See [RT-RTE-scheduled-tool](runtime.md#rt-rte-scheduled-tool) and the [workflow account](workflow.md#workflow-account).

When no tool matches, authoring receives the prompt, app schema and capability guidance. Static capability checks and simulated smoke execution can reject selected failures and trigger one error-informed model repair. They do not compare the result with a reference business answer. The manual build endpoint persists model-authored results only; the routine runner can persist any non-null tool, including fallback code. Same-name replacement increments a version without established retention of the previous code body. See [RT-RTE-tool-authoring](runtime.md#rt-rte-tool-authoring) and [RT-OBJ-stored-tool](runtime.md#rt-obj-stored-tool).

The routine executes with `approved: false`. Named send/browser capability gates can terminate it as `needs_approval`, while permitted app data changes may already have occurred. A gate rejection ends the worker: “paused” narration does not mean a resumable program counter. On an ordinary returned result, the runner appends prompt/outcome messages and writes a Markdown artifact; the service returns status, digest and session ID. Frontend request/display paths make these retained results accessible, without proving human receipt. The broker can record a successful scheduler fire with a partial playbook outcome. Separately, integration deferral may return ordinary successful result text while the action remains pending. Thus dispatch acknowledgement, recorded delivery and requested-action completion are distinct. See [RT-RTE-saved-call](runtime.md#rt-rte-saved-call), [MEM-OBJ-session-transcript](memory.md#mem-obj-session-transcript) and the [workflow annotations](workflow.md#on-rt-rte-scheduled-tool).

Successful scheduled operation also depends on a consequential wiring condition: the inspected broker POST does not attach the optional sidecar bearer authorization. Token-protected configuration can reject the handoff. Its 90-second caller deadline can expire before the worker's ordinary 120-second deadline. Continued recurrence neither resumes the old worker nor compensates prior effects. These are source-supported constraints, not observed deployment failures. See [RT-RTE-scheduled-tool](runtime.md#rt-rte-scheduled-tool).

### Earlier work changes later inputs through several unequal memory routes

Office context is selected rather than a replay of every prior turn. A notification brief can deliver two clipped private notes and up to three distinct shared-page snippets; the Claude fetch has a two-second deadline and frames the material as untrusted reference data. Task packets independently select up to five learning insights and three wiki snippets, while file search supplies up to five article titles/paths with a request to read the relevant bodies. Dependency IDs select upstream task outcomes and proof excerpts. Item limits and clipping are not a universal token budget. A delivered pointer or manifest is not evidence that the body was read or its advice followed. See [MEM-RTE-memory-brief](memory.md#mem-rte-memory-brief), [MEM-RTE-task-knowledge](memory.md#mem-rte-task-knowledge), [MEM-RTE-upstream-results](memory.md#mem-rte-upstream-results) and [MEM-BAP-knowledge-guidance](memory.md#mem-bap-knowledge-guidance).

These automatic packets are push to the receiving model; explicit note queries, learning searches and article reads are pull. Local selection uses lexical relevance, confidence/recency and, when configured, dense embedding ranking. Remote GBrain ranking and storage remain opaque. Private notes live in persisted broker state; learning/fact logs and wiki prose use files and Git; saved tools use per-agent files. Dense vectors, fixed-rule metadata/code and interpreted prose have different consumers. See [MEM-OBJ-private-memory-note](memory.md#mem-obj-private-memory-note), [MEM-OBJ-shared-memory-write](memory.md#mem-obj-shared-memory-write), [MEM-OBJ-learning-record](memory.md#mem-obj-learning-record), [MEM-OBJ-typed-fact](memory.md#mem-obj-typed-fact) and [MEM-CMP-retrieval-embedding](memory.md#mem-cmp-retrieval-embedding).

The strongest supported learning-related contribution is a wired path from completed task activity and verification feedback into durable knowledge selected for later work. A second conditional path uses simulated smoke errors to shape repaired code that can be retained for later execution. Both qualify as automatic trace-fed durable updates; neither demonstrates improved capacity. Raw routine transcripts are instead retained for readers, not established history for future author calls. See [MEM-RTE-task-distillation](memory.md#mem-rte-task-distillation), [MEM-RTE-task-knowledge](memory.md#mem-rte-task-knowledge), [RT-RTE-tool-authoring](runtime.md#rt-rte-tool-authoring) and [profile verification](profile-verification.md#verification).

### Checks constrain reliance only within their actual domains

Completion verification can test command exit, a nonempty matching file or HTTP 2xx. Required failure can block completion; optional failure or no specification can permit continuation. A passing result gates trusted learning capture, but entity associations/article regeneration occur before that gate. Copying a title and details under “Verified outcome” does not verify those narratives, explain success or establish transfer. See [EPI-RTE-task-check](epistemic.md#epi-rte-task-check), [EPI-RTE-task-admission](epistemic.md#epi-rte-task-admission) and [MEM-RTE-task-distillation](memory.md#mem-rte-task-distillation).

Artifact extraction and fact-fed brief rewriting retain source-linked candidates under software checks, not established semantic acceptance. Source-to-fact and fact-to-brief relations remain indeterminate without actual content and support checks. Citation bounds filtering can remove invalid indices while returning unchanged answer prose; it does not verify entailment or require every claim to be cited. Likewise, contradiction judging has a positive, consequential route: a model identifies inconsistency, then a caller can expire one fact or acknowledge both. This changes retained metadata and future lint eligibility, but does not authenticate either proposition or establish withdrawal from every derivative. See [MEM-RTE-artifact-extraction](memory.md#mem-rte-artifact-extraction), [MEM-RTE-brief-synthesis](memory.md#mem-rte-brief-synthesis), [EPI-RTE-query-answer](epistemic.md#epi-rte-query-answer), [EPI-RTE-lint-judge](epistemic.md#epi-rte-lint-judge) and [EPI-RTE-lint-disposal](epistemic.md#epi-rte-lint-disposal).

Operational approval is equally local. Selected task plans require human authorization; named capabilities test a run flag; integration mutation uses broker classification; supplied-spec replay trusts each step's `gated` field. Manual calls can assert approval as a Boolean, and native execution permissions vary by provider/posture. The inspected routes therefore do not establish the universal external-action approval promise. Source-bearing answer structures and citation guidance similarly fall short of universal cited, verified knowledge. These are bounded claim/route mismatches, not observations of unauthorized actions or uncited user-facing outputs. See [RT-RTE-plan-approval](runtime.md#rt-rte-plan-approval), [RT-CLM-external-approval](runtime.md#rt-clm-external-approval), [EPI-CLM-verified-lookup](epistemic.md#epi-clm-verified-lookup) and [EPI-CLM-cited-knowledge](epistemic.md#epi-clm-cited-knowledge).

### What the mechanisms establish, and what would change the assessment

For recurrent app work, the architecture supports reuse of admitted executable tools, bounded capability gates and accessible recorded outcomes. For later knowledge-assisted tasks, it supports selected reuse of earlier outcomes and derived prose, without establishing retrieval quality or justified reliance. Compression/archive and contradiction disposal have bounded effects; procedural compilation affords later instructions, but full skill assignment/loading remains untraced. See [MEM-RTE-wiki-maintenance](memory.md#mem-rte-wiki-maintenance), [EPI-RTE-playbook-compile](epistemic.md#epi-rte-playbook-compile) and [MEM-RTE-skill-registration](memory.md#mem-rte-skill-registration).

The runtime establishes executable construction and limited repair, not a theory-builder assessment satisfying conditions 1–4. The positive contradiction criticism/disposal mechanism does not by itself establish localized theory consumption, content-directed blame and retained iteration across all four conditions. Whether criticism of a consumed theory improved future capacity remains unestablished. Autonomous scheduled execution is wired; a fully autonomous theory builder is not established. Reflection likewise has no established complete two-way self-representation account in these records. These are independent findings, not deductions from missing runs alone. See [RT-RTE-tool-authoring](runtime.md#rt-rte-tool-authoring) and the epistemic [bounded conclusion](epistemic.md#bounded-conclusion).

Smoke-error repair is an evidence-responsive, improvement-directed standing pathway: error feedback can shape code, retained code enters the runtime's own later execution path, and reducing the checked crash failures is an objective independent of the particular edit. This supports a bounded dispositional account of self-change, not exercised self-improvement or successful improvement. No subsequent execution causally dependent on a repaired tool is supplied. Task-derived future context similarly demonstrates a standing update path, not benefit. Provider parameter learning remains uninspected rather than absent. See [RT-RTE-tool-authoring](runtime.md#rt-rte-tool-authoring), [RT-BAP-tool-execution](runtime.md#rt-bap-tool-execution), [MEM-RTE-task-distillation](memory.md#mem-rte-task-distillation) and [RT-CMP-office-model](runtime.md#rt-cmp-office-model).

A trace linking a specific smoke failure, admitted repair and later dependent execution would change the exercised-self-change assessment; outcome comparison would separately be needed for improved capacity. Representative source-to-fact/brief and answer-to-source checks would change semantic-reliance conclusions. End-to-end evidence under token-protected scheduling, plus authenticated approval and common effect classification across alternate routes, would change the operational guarantee assessment. None is supplied by this run. The report and profile verifications found no blockers or additional declared limits; their acceptance concerns this bounded account, not production success. See [report verification](report-verification.md#verification) and [profile verification](profile-verification.md#verification). No frozen source files were read for this synthesis.
