# Pre-change operability baseline — 2026-08-31

This is the small baseline required before changing the interface. It records
observable command costs rather than claiming that output volume alone measures
operator or agent comprehension.

## Subject state

- Git commit: `fc67fc30ea1dd42451b365c66c884a2535ef94df`
- Package version declared in `pyproject.toml`: `0.1.5`
- Command installation: editable user-level Commonplace installation
- Worktree: not clean; concurrent unrelated source and workshop changes were
  present and were not used as evidence for validation behavior
- Machine-local review state: the current `COMMONPLACE_STORE` default for this
  checkout

Each timed command redirected standard output and standard error to files in
`/tmp`; byte and line counts came from `wc`. Elapsed time came from
`/usr/bin/time`. These measurements are local observations, not performance
budgets.

## Case 2: validation recovery

The existing single-file path already limits output to the target and any
marked tag README pulled into the same validation run. The collection path is
the immediate problem: locating a small number of failures or warnings among
passing artifacts requires receiving every passing block first.

The post-change comparison must use fixtures containing at least one clean
artifact, one warning, one failure, and one collection-structure failure. It
must show that every non-pass result remains inspectable and that an explicit
detailed mode reproduces per-artifact evidence.

## Case 3: lifecycle triage

The audit's contradictions still reproduced before lifecycle validation:

- 18 top-level directories under `kb/work/` were absent from the active-work
  index;
- one backlog task declared all four subtasks complete;
- one recurring task named an output file that did not exist;
- `semantic-search-replacement` remained listed as active; and
- `kb/tasks/active/` contained no task artifact.

The first three are deterministic candidates. The last two require operator
interpretation: an active workshop can still have a live question despite an
obsolete premise, and an empty active-task directory can be healthy.

There was no validator target that summarized these lifecycle conditions.

## Case 4: cold-start situation discovery

No `commonplace-status` command existed. The nearest structured inputs were
separate commands whose complete JSON results had these local costs:

| Command | Exit | Lines | Bytes | Elapsed seconds |
|---|---:|---:|---:|---:|
| `commonplace-warn-selector --json` | 0 | 13,478 | 496,440 | 1.06 |
| `commonplace-review-job-list --status queued --json` | 0 | 1 | 402,364 | 0.28 |
| `commonplace-review-job-list --status failed --json` | 0 | 1 | 547,994 | 0.34 |
| `commonplace-freshness-status --json` | 1 | 195,739 | 8,253,263 | not retained |

The freshness exit status reports stale state rather than command failure. A
cold-start consumer must know which commands to call, understand their distinct
schemas and exit semantics, then reduce roughly 9.7 MB of structured output
before combining it with Git and lifecycle state.

The status pilot should consume these endpoints or their library equivalents
without reproducing their complete payloads. Its acceptance comparison is the
ability to expose the highest-priority current facts and drill-down routes from
one small result, not parity with every underlying row.
